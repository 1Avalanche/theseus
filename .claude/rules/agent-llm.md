# Агент и LLM

- Модели — только из конфига, по ролям (`main`, `summary`, позже `router`). Список `main` = приоритет fallback: haiku-5.5 → gemini-3.1-flash-lite → gpt-5.4-nano. Не хардкодить id моделей в коде.
- Пайплайн имеет шов под роутер-классификатор; в v1 — один агент с инструментами.
- Мягкость: низкая уверенность → уточняющий вопрос; не по теме → вежливо + что умею; отказ — только злоупотребление/квота.
- После успешного tool call ответ рендерит **код по шаблону**. Второй вызов LLM — только если нужен диалог/уточнение.
- Этап 2: свободный текст модели не подтверждает изменение и пользователю не выдаётся. Без вызова инструмента — `reply.not_created`; после попытки без подтверждения — `reply.unconfirmed`. Частично подтверждённые результаты сохраняются в ответе; модель не получает их для повторного создания. Произвольные уточнения и свободный диалог требуют отдельной безопасной реализации этапа 5.
- Списки, даты, подтверждения рендерит код, не модель.
- В промпт всегда: текущее локальное время и таймзона пользователя, имя, грамматический род.
- Все промпты (системный, персона, описания MCP-инструментов, саммари, роутер) — на русском, хранятся в ресурсах, не в коде.
- Wire-контракт OpenRouter проверять по фактическому сериализованному HTTP-телу: `tools[].type` и `messages[].tool_calls[].type` обязаны содержать `function`. Значения по умолчанию Kotlin-свойств не должны исчезать из JSON; для wire-кодека включён `encodeDefaults`. Успешный `tools/list` MCP отдельно не доказывает передачу инструментов модели.
- Промпт собирается из блоков: персона → правила → контекст пользователя → инструменты. Стабильные блоки — первыми (prompt caching).
- Каждый вызов LLM → запись usage в core (модель, токены in/out, стоимость).
- Обработка сообщений одного chatId — строго последовательно.
- История: последние ~20 сообщений + скользящее саммари; результаты инструментов — в сжатом виде; маппинг `номер пункта → id` и `telegram message_id → reminderId`.
