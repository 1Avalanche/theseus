# Деплой, образы, CI

- Образ собирается из дистрибутива `./gradlew installDist`; Gradle в образе и на VPS не запускается. Файлы — `COPY --chmod=…` (jar из Gradle-кеша бывают `600`, пользователь контейнера их не прочитает). Нужен BuildKit (`# syntax=docker/dockerfile:1`).
- Переменные контейнерам — явным списком в `environment` compose, не `env_file`: каждый сервис видит только свои секреты.
- Root-owned bind mount с initdb-скриптами PostgreSQL должен читаться контейнерным пользователем `postgres`: каталог `infra/initdb` — `755`, скрипты — `755`. Права `700` на этот каталог ломают старт (`Permission denied`). Родительский `/opt/theseus` остаётся `700`, env-файлы с секретами — `600`. Проверка локального Compose из репозитория не проверяет права установленного серверного каталога.
- В env-файлах комментарии — только отдельными строками (inline `#` парсеры читают по-разному).
- Секреты приложения — только в env-файлах на VPS; в GitHub — только SSH-доступ к VPS. В `run:` workflow не подставлять `${{ inputs.* }}` напрямую — через `env:` (инъекция в shell).
- Деплой — только через root-owned обработчик и разрешённые digest; workflow не копирует привилегированные файлы. Стенд закреплён за SSH-ключом. Все административные изменения серверной конфигурации и разрешений — под `/opt/theseus/deploy.lock`; сам lock-файл не пересоздавать. Проверять изменения обработчика тестами `deploy/handler/tests`, включая SSH/sudo в одноразовом Ubuntu-контейнере без Docker socket хоста.
- Публикация репозитория не открывает релиз и деплой: ручные workflow — только владелец исходного репозитория из `main`, с проверкой исходного автора и инициатора rerun. SSH-секреты — только в Environments с единственным reviewer-владельцем, разрешённым self-review и отключённым admin bypass. Перед approval показывать неизменяемый artifact ID и SHA-256; после approval не искать кандидата заново. Authorizer сам проверяет происхождение и содержимое артефакта, не исполняя его. Настройки GitHub проверять отдельно от кода workflow.
- При пошаговом продвижении различать approval, разрешение релиза и Deploy. Перед Deploy prod подтвердить итоговую строку `prod: разрешён релиз <sha>` либо наличие `/opt/theseus/releases/prod/<sha>.json`; общего ответа «готово» после approval недостаточно. Отсутствующее разрешение создаётся отдельным Authorize release для нужного стенда.
- Новая переменная окружения → `CoreConfig`/`AgentConfig` + compose + `deploy/env/*.example` + таблица в `docs/operations.md`.
- Изменение compose/Dockerfile/скриптов проверяй локально скиллом `local-stand-check`, а не только чтением.
- Мониторинг: временные пороги и период host-проверки — 10 минут (DECISIONS.md §21), рабочие циклы остаются частыми. Пульс обновляет сама задача, не отдельный `getMe` или таймер. Проверяй `python3 -m unittest discover -s deploy/monitor/tests -v`; тестируй подавление тревог, бюджет рестартов, отказ зависимостей и остановленный test. Монитор использует общий `deploy.lock`, неизвестное состояние не разрешает рестарт. Настроенный внешний канал и его живую проверку подтверждай отдельно от наличия кода.
- Long polling Telegram: HTTP request/socket timeout должен быть больше серверного `getUpdates.timeout`. ktgbotapi 37.1.0 выставляет одинаковые значения; запас добавляется в Ktor после настройки запроса SDK. Регрессия — настоящий SDK-слой с задержанным пустым ответом, а не только mock `TelegramBot.execute`. На test перед продвижением проверить свежий пульс в течение двух минут без входящих сообщений; успешная сборка и активный диалог этой проверки не заменяют.
- Локально (macOS, Docker Desktop): если `docker pull`/`build` виснет на «error getting credentials», запускай с `DOCKER_CONFIG=<tmp>` с `config.json` = `{}` и симлинком `cli-plugins` → `~/.docker/cli-plugins`. В zsh тег пиши `"${m}:local"`: `$m:l…` — модификатор zsh.
