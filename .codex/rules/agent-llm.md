# Агент и LLM

- Модели — только из конфига, по ролям (`main`, `summary`, позже `router`). Утверждённый 2026-11-20 приоритет `main`: haiku-5.5 → qwen3.8-flash → gemini-3.1-flash-lite. GPT исключён из рабочего списка и будущих eval; исторические результаты сохраняются. Не хардкодить id моделей в коде.
- Пайплайн имеет шов под роутер-классификатор; в v1 — один агент с инструментами.
- Мягкость: низкая уверенность → уточняющий вопрос; не по теме → вежливо + что умею; отказ — только злоупотребление/квота.
- После успешного tool call ответ рендерит **код по шаблону**. Второй вызов LLM — только если нужен диалог/уточнение.
- Этап 2: свободный текст модели не подтверждает изменение и пользователю не выдаётся. Без вызова инструмента — `reply.not_created`; после попытки без подтверждения — `reply.unconfirmed`. Частично подтверждённые результаты сохраняются в ответе; модель не получает их для повторного создания. Произвольные уточнения и свободный диалог требуют отдельной безопасной реализации этапа 5.
- Fix 1.1: `/start` и `/help` обрабатываются кодом после проверки доступа, без LLM. Для естественных вопросов о себе и возможностях модель выбирает только `topic` локального `assistant_reply`; текст, имя и неподдерживаемые темы от модели не принимаются. Ответ формируется из ресурсов с фактическими возможностями текущей версии. Приветствие не считается онбордингом со сбором профиля; при отсутствии истории уточнение просит полный запрос.
- Списки, даты, подтверждения рендерит код, не модель.
- Для известной причины отказа/уточнения используй отдельный ресурсный ответ: неверная дата, неподдерживаемый частый повтор, неоднозначная цель, отсутствующий час. Общий «повтори запрос целиком» не заменяет конкретную причину. Карточки показывают действие и последствия; пустые/default-поля wire-контракта пользователю не печатай.
- Онбординг-текст выдавай только при сборе профиля. Приветствие активного пользователя и `/start` — короткие; возможности и общий рассказ о себе — отдельные темы. Общий рассказ собирай кодом из утверждённых частей и единого актуального списка функций; конкретные вопросы о себе учитывают недавний текстовый контекст.
- Нераспознанная задача и неверная тема диалога — уточнение, не технический сбой. Противоречивое «15 вечера» требует `invalid_time`, без угадывания часа и изменения напоминания. Технические ошибки транспорта не маскируй этим уточнением.
- Новое нажатие обработанной карточки сообщает, что она обработана, и снимает клавиатуру; не повторяет старое «Удалил» на отмену. Технический повтор того же Telegram-события сохраняет прежний результат; незавершённое изменение восстанавливает прежний UUID. Проверяй оба порядка: подтверждение → отмена и отмена → подтверждение.
- Неоднозначное описание одной цели не разрешает менять все совпадения. Пакет нескольких изменений существующих целей блокируется до исполнения. Удаление всех без фильтра — один `delete_reminder scope=all`; явно выбранной группы — один `scope=selected` с `reminder_ids`, общей карточкой и атомарной проверкой снимка. Усечённый поиск не даёт права выдавать часть кандидатов за всю группу.
- В промпт всегда: текущее локальное время и таймзона пользователя, имя, грамматический род.
- Все промпты (системный, персона, описания MCP-инструментов, саммари, роутер) — на русском, хранятся в ресурсах, не в коде.
- Wire-контракт OpenRouter проверять по фактическому сериализованному HTTP-телу: `tools[].type` и `messages[].tool_calls[].type` обязаны содержать `function`. Значения по умолчанию Kotlin-свойств не должны исчезать из JSON; для wire-кодека включён `encodeDefaults`. Успешный `tools/list` MCP отдельно не доказывает передачу инструментов модели.
- Промпт собирается из блоков: персона → правила → контекст пользователя → инструменты. Стабильные блоки — первыми (prompt caching).
- Каждый вызов LLM → запись usage в core (модель, токены in/out, стоимость).
- Изменяющий internal REST вызывай только через `OutgoingOperations`: ключ и запрос сохраняются до core; повтор и восстановление используют сохранённую запись. Не назначай новый UUID для сетевого повтора.
- Ключ записи usage относится к фактическому вызову модели, а не только к Telegram update: отдельная генерация — отдельная запись расхода. Технический повтор самой записи расхода сохраняет её UUID.
- Перед LLM сохраняй маркер входящего события без исходного текста. Завершённый ответ используй повторно; незавершённое после рестарта изменение MCP не исполняй заново до появления идемпотентности этапа 4.
- Обработка сообщений одного chatId — строго последовательно.
- История: последние ~20 сообщений + скользящее саммари; результаты инструментов — в сжатом виде; маппинг `номер пункта → id` и `telegram message_id → reminderId`.
- Reply проверяй на обоих источниках: уведомление core и ответ агента «Поставил/Изменил». Для ответа агента сохраняй фактический Telegram message_id после отправки и цель из подтверждённого MCP-журнала; текст ответа не парси. Reply на ответ о серии без указания одного срабатывания относится к серии целиком.
- Этап 5: `about` генерируется отдельным обращением без инструментов по карточке и конкретному вопросу; остальные темы `assistant_reply` остаются ресурсными. Все роли делят бюджет входящего сообщения. Таймаут начатого изменения оставляет исход неопределённым для восстановления прежнего UUID, а не превращается в ответ «не выполнено».
- При изменении промптов или описаний инструментов проверяй бюджет на полном наборе production-ресурсов (регрессия `ConversationMemoryTest`), включая схемы, текущий запрос и саммари. Проверка на коротком тестовом промпте не обнаруживает переполнение до первого вызова модели. При консервативной оценке UTF-8 сначала сокращай повторы инструкций, системные правила не обрезай.
- Для цепочки поиска проверяй и следующий LLM-запрос: полные схемы, история и 10–30 реалистичных карточек. Облегчённый FakeCore с одним пустым инструментом скрывает переполнение после `find_reminders`. Сжатие результата не должно терять кандидатов, поля или значения; техническая причина остановки логируется без пользовательского текста.
- Отказ диалога диагностируй по трассе хода: этап, разрешённые имя инструмента и тема, причина остановки; для OpenRouter — тип ошибки и HTTP-статус. Не логируй произвольные имена/темы модели, аргументы, тела ответов и `exception.message`. Пакет `about` с другими локальными темами проверяй отдельно от пакета с инструментом core: защита изменений не должна блокировать безопасный рассказ о возможностях.
