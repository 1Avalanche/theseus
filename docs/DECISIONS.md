# Theseus — журнал решений

Статус: v1 = напоминания. Схемы БД и контракты v1 утверждены (§11), ходячий скелет — §13.

## 0. Название и язык
- Проект/платформа — **Theseus** (корабль из «Ложной слепоты»): репозиторий, сервисы `theseus-core`, `theseus-agent`, пакеты `…theseus`. Персона агента — **Сири**.
- Всё, кроме кода, — на русском: документация (`docs/`), KDoc, правила и скиллы Claude, промпты LLM, тексты для пользователя, описания PR. Идентификаторы — английский.
- Сообщения коммитов — **на английском**, формат `<scope>: <summary>` с указанием модуля/функционала (заменяет прежнее «коммиты на русском»).
- Документация обязательна и обновляется вместе с кодом.
- Правила и скиллы, выявленные в работе, сразу добавляются в `.claude/rules` / `.claude/skills`.
- Поиск по коду для Claude — через MCP-сервер индекса IDE (плагин IntelliJ), grep — запасной вариант.

## 1. Платформа и инфраструктура
- Язык: Kotlin. Один репозиторий, многомодульный Gradle. Юнит-тесты обязательны.
- VPS, Docker Compose, `restart: unless-stopped` + healthcheck.
- БД: PostgreSQL. Миграции — Flyway; перед миграцией — автодамп; изменения схемы аддитивные.
- LLM: OpenRouter (OpenAI-совместимый API, tool calling).
- Telegram: long polling (без webhook/домена/TLS).
- Масштаб: до 30 пользователей.
- VPS: 2 ГБ RAM (данные владельца, 2026-11-02). Порог объединения сервисов (< 1,5 ГБ) не достигнут — core и agent остаются отдельными процессами. Бюджет памяти (ориентир, проверяется на этапе 2):

  | Что | RSS |
  |---|---|
  | ОС + Docker | ~300 МБ |
  | PostgreSQL (`shared_buffers` 128 МБ) | ~200–250 МБ |
  | core (JVM, `-Xmx256m`) | ~400 МБ |
  | agent (JVM, `-Xmx256m`) | ~400 МБ |
  | запас (бэкап, пики, тестовый стенд по требованию — §12) | ~650 МБ |

  - Лимиты памяти — у каждого контейнера в compose (`mem_limit`), heap JVM — явно; swap-файл 1–2 ГБ как страховка от OOM.
  - Gradle на VPS не запускается: образы собираются вне сервера, VPS только скачивает и запускает их.

## 2. Архитектура
- Два сервиса:
  - **core** — домен, БД, планировщик, уведомления.
  - **agent** — Telegram-бот + LLM-пайплайн.
- core — гибрид:
  - **MCP** — только инструменты, видимые LLM (операции над напоминаниями и т.п.).
  - **REST (internal)** — системные вызовы агента (пользователи, доступ, инвайты, usage, квоты) и будущие не-ИИ клиенты.
  - Оба — тонкие адаптеры над общими application-сервисами.
- Контекст пользователя: агент передаёт `userId` + сервисный токен в заголовке/`_meta`, **никогда** через аргументы LLM.
- Планировщик — в core, корутина, опрос БД каждые 30–60 с; статус `PENDING → SENT`; при старте — досыл просроченных.
- Уведомления: интерфейс `Notifier` в core; v1 — `TelegramNotifier` (Bot API `sendMessage`).
- История диалога — в отдельной схеме агента в том же Postgres (миграции агента — свои).

## 3. Принцип
- **Всё, что можно сделать детерминированно (код, скрипты, пайплайны), делается кодом.**
- LLM: понимание естественного языка, извлечение сущностей, уточняющие вопросы, семантическое сопоставление, диалог.
- Код: даты/таймзоны/RRULE, валидация, кандидаты на дубли, рендер списков, онбординг, кнопки, snooze, права.

## 4. Доступ и пользователи
- Пользователь = Telegram chatId.
- Админ — chatId из конфига. Команды админа в боте: `/invite`, `/users`, `/revoke`, `/restore` (добавлена в §11), `/stats`.
- Инвайт: одноразовый код + TTL (~72 ч), ссылка `t.me/<bot>?start=<код>`; при активации — уведомление админу. **Без** подтверждения кнопкой.
- **При генерации инвайта админ указывает грамматический род пользователя** (м / ж / не указан). Не указан → агент избегает гендерно окрашенных форм. Менять позже — через профиль.
- Незарегистрированные chatId отсекаются без вызова LLM.
- Онбординг — детерминированный FSM: имя (кнопка с `first_name` или текст) → таймзона. Без онбординга агент не работает.
- Таймзоны по умолчанию (кнопки): **Москва, Екатеринбург, Другая** (геолокация или город → IANA, с подтверждением). Список — в конфиге.
- Хранение: таймзона — IANA-строка в профиле; время — `timestamptz` (UTC).

## 5. Учёт и квоты
- core хранит usage по каждому LLM-запросу (модель, токены in/out, стоимость из ответа OpenRouter).
- Квоты закладываются в модель данных и API, **в v1 выключены**.

## 6. Агент
- Пайплайн с швом под роутер-классификатор; **v1 — один агент с инструментами** (классификация и уточнения — внутри него). Роутер подключается с появлением второго домена.
- Мягкость: низкая уверенность → уточняющий вопрос; не по теме → вежливо + что умею; жёсткий отказ — только злоупотребление/квота.
- Диалог:
  - последние ~20 сообщений + скользящее саммари; новая «сессия» после паузы в несколько часов;
  - результаты инструментов в истории (сжато);
  - нумерация пунктов списков → `номер → reminderId` в состоянии сессии;
  - связь `telegram message_id → reminderId` (reply на уведомление);
  - `typing`, inline-кнопки для подтверждений, сериализация обработки по chatId.

## 7. Напоминания — сценарии
1. Создать (разовое / повторяющееся), проверка дублей в core → `possible_duplicate` → подтверждение → `force`.
2. Изменить / перенести (для серии: одно срабатывание или вся серия).
3. Удалить (подтверждение; для серии: одно или вся серия).
4. Показать все активные / за период (рендер кодом, нумерация).
5. Найти (core отдаёт кандидатов, LLM сопоставляет по смыслу; позже — pgvector).
6. Snooze с уведомления (+15 мин / +1 ч / завтра), без LLM.
7. Пропустить одно срабатывание серии.
8. Пауза / возобновление серии (в т.ч. «до даты») — **в v1**.
- Повторы: RRULE (RFC 5545) + IANA-таймзона + локальное время; следующее срабатывание считается библиотекой в локальной таймзоне. LLM заполняет структуру (freq, interval, byDay, time, until), RRULE собирает код.
- Время без указания часа → дефолт (напр. 09:00, конфиг).

## 8. Персона «Сири»
- Имя Сири, мужской род («я поставил»), общение на «ты».
- Прототип — Сири Китон («Ложная слепота», П. Уоттс). Берём наблюдательность, точность, сдержанную иронию; не берём холодность.
- Факты о себе — **только из карточки персонажа** (файл, составляет владелец); вне карточки — уклоняется в образе.
- **Спойлеры: говорит только о себе, финал не раскрывает.**
- Образ меняет тон, не поведение: функция важнее образа.
- Детерминированные ответы (онбординг, подтверждения, уведомления) — шаблоны в голосе Сири, в ресурсах.
- Карточка — короткая (~300–500 токенов), отдельный версионируемый файл; промпт собирается из блоков.

## 9. Выбор LLM
- Модель — параметр конфига (по ролям: `main`, `summary`, позже `router`); агент не завязан на провайдера.
- Критерии: русский язык, надёжный tool calling / structured output, низкая латентность, prompt caching. Без reasoning/thinking-моделей.
- В конфиге все три модели, порядок = приоритет (OpenRouter `models` fallback):
  1. `anthropic/claude-haiku-5.5` — **основная** (0.10/0.50 $/1M на 2026-11-02, перепроверить — похоже на промо);
  2. `google/gemini-3.1-flash-lite` (0.25/1.50);
  3. `openai/gpt-5.4-nano` (0.20/1.25).
- summary: самая дешёвая адекватная модель из списка.
- Eval-набор (50–100 русских запросов, детерминированная проверка аргументов tool calls) — подтверждает выбор и служит регрессией при смене модели/промпта.
- Приватность: в OpenRouter ограничить провайдеров / запретить data collection.
- Ответ после успешного tool call — шаблоном (кодом), второй вызов LLM только когда нужен диалог.

## 11. Контракты v1 (этап 1, утверждено владельцем 2026-11-02)
Документы: схема БД — `docs/database.md`, MCP — `docs/api/mcp.md`, REST — `docs/api/rest.md`, eval — `docs/eval.md`.

### Данные
- `users.id` (bigint) — единственный `userId` между сервисами; chatId — атрибут пользователя. Роль `USER`/`ADMIN` хранится в core: админ создаётся core при старте из конфига; роль защищает админа от `/revoke`.
- Автор инвайта не хранится (решение владельца, 2026-11-02): админ один и задан конфигом, аудит ничего не даёт, а проверка «создаёт админ» в core опиралась бы на id, который подставляет сам агент. Права админа проверяет агент по chatId, core доверяет сервисному токену. При нескольких админах — добавить nullable-колонку новой миграцией.
- Инвайт: хранится SHA-256 кода, не код; состояние (`ACTIVE`/`USED`/`EXPIRED`/`REVOKED`) вычисляется из времён, а не хранится.
- Напоминание и серия — одна таблица: `start_local` + `timezone` + `recurrence_rule` (строка RRULE; null — разовое) + производное `next_fire_at` (UTC) для планировщика. Таймзона — снимок на момент создания.
- Статус напоминания `ACTIVE`/`PAUSED`/`DONE`/`DELETED` + журнал отправок `reminder_deliveries` (`SENT`/`FAILED`, unique по срабатыванию). **Уточняет** «`PENDING → SENT`» из §2: для серии статус «отправлено» имеет смысл только у срабатывания, поэтому он в журнале.
- Пропуск/перенос одного срабатывания серии: `excluded_occurrences` у серии + (для переноса) разовое напоминание с `parent_id`. Аналог EXDATE/RECURRENCE-ID из RFC 5545 без отдельной таблицы исключений.
- Snooze — поле `snoozed_until`, `next_fire_at = min(расписание, snooze)`; повторный snooze заменяет предыдущий.
- Маппинг `telegram message_id → reminderId` для reply хранит **core** (`reminder_deliveries.telegram_message_id`): уведомления отправляет core, агент этих id не видит. Уточняет §6; маппинг `номер пункта → id` остаётся в состоянии сессии агента.
- Агент: `dialog_sessions` (саммари, состояние сессии), `dialog_messages` (хранение 30 дней), `pending_actions` (подтверждения по кнопкам), `onboarding_state`. Каждый сервис — своя схема и своя роль БД.
- Отзыв доступа обратим (решение владельца, 2026-11-02): `REVOKED → ACTIVE` (или `ONBOARDING`, если онбординг не завершён) командой админа `/restore` — дополняет список команд §4. Во время отзыва срабатывания пропускаются, после восстановления не досылаются.
- Мягкое удаление напоминаний; тексты запросов к LLM в `llm_usage` не хранятся.

### MCP
- Транспорт Streamable HTTP без сессий; токен — заголовок, пользователь — `_meta["theseus/user_id"]`.
- Девять инструментов: `create_reminder`, `list_reminders`, `find_reminders`, `get_reminder`, `update_reminder`, `delete_reminder`, `snooze_reminder`, `pause_reminder`, `resume_reminder`. Пропуск срабатывания — `delete_reminder` с `scope=occurrence`, без отдельного инструмента: меньше инструментов — надёжнее выбор модели.
- Модель передаёт время «как сказал пользователь» (`When`: `date`/`time`/`after`), локальными строками; всё вычисление (ближайшее будущее, сдвиги, таймзона, DST, «в прошлом») — core. Повторение — структура `Recurrence`, RRULE собирает core. Частота чаще раза в день в v1 не поддерживается.
- Поля JSON — `snake_case` и в MCP, и в REST: одно соглашение на все внешние контракты.
- Дубли: кандидат = похожий текст **и** пересекающееся расписание; пороги в конфиге. `possible_duplicate` — успешный ответ, не ошибка.
- Подтверждение удаления — кодом агента: вызов `delete_reminder` от модели перехватывается, показывается карточка с кнопками (`pending_actions`), в core уходит только после нажатия.
- Ошибки — `isError` + JSON `{code, message}`; `message` по-русски для модели; чужие id неотличимы от несуществующих.

### REST
- `/internal/v1`, Bearer сервисный токен, `GET /health` без авторизации.
- Пользователи (поиск по chatId до LLM, активация инвайта, профиль/онбординг, список, отзыв), инвайты, usage + статистика, квота (в v1 всегда `enabled: false`), snooze по кнопке, поиск напоминания по reply.
- Кнопки уведомлений: `callback_data = snz:<delivery_id>:<15m|1h|tmr>`; нажатие → REST snooze без LLM.

### Eval
- 97 кейсов в `agent/eval/reminders.jsonl` + фикстуры. Время сравнивается после разрешения кодом core (`$resolves_to`), повторения — после нормализации (`$normalizes_to`): разные записи одного смысла равноценны.

### Открытые вопросы этапа 1
- Смена таймзоны пользователя: пересчитывать ли существующие серии (сейчас — нет, снимок таймзоны в напоминании).
- «До 10-го» в паузе: возобновлять 10-го или 11-го (в eval допустимы оба).
- Время по умолчанию для «утром»/«вечером» без часа — сейчас одно (09:00) для всех.

## 12. Стенды, CI и деплой (решение владельца, 2026-11-02)

### Стенды
- Два стенда на одном VPS: **prod** и **test**. Каждый — свои процессы core и agent и свой Telegram-бот: тест проверяется «в бою» на реальном Telegram и OpenRouter, не трогая пользователей.
- Один `docker-compose.yml`, два compose-проекта с разными env-файлами: `theseus-prod`, `theseus-test`. Различия — только конфиг: токен бота, имя БД, роли БД, теги образов, chatId админа.
- **PostgreSQL — один на оба стенда**, в отдельном compose-проекте `theseus-infra`; базы `theseus_prod` и `theseus_test`, у каждого стенда свои роли без доступа к чужой базе. Второй контейнер Postgres стоил бы ~250 МБ из 2 ГБ.
- Ключ OpenRouter — **один** на оба стенда. Расходы стендов различаются по `llm_usage` в их базах.
- В тестовой базе — только тестовые данные, копия прода туда не заливается (приватность).
- Тестовый стенд поднимается **по требованию** (деплоем на тест) и гасится после проверки (`docker compose -p theseus-test down`): prod и test вместе занимают ~1,9 ГБ из 2 ГБ, без запаса на бэкап и пики. Swap 1–2 ГБ — обязательно. Нужен постоянный тест — VPS на 4 ГБ, а не урезание heap.

  | Что | МБ |
  |---|---|
  | ОС + Docker | ~300 |
  | PostgreSQL | ~280 |
  | prod core + agent (heap 256 МБ) | ~800 |
  | test core + agent (heap 128 МБ) | ~550 |

### Репозиторий и CI
- Репозиторий — **GitHub** (приватный). Основная ветка — `main`, работа — в `develop`.
- CI (`./gradlew build`: тесты, ktlint, detekt) — автоматически на push и PR. Это только проверка, **не деплой**.
- Образы core и agent — GitHub Container Registry (`ghcr.io`), тег — SHA коммита. На VPS Gradle не запускается.

### Деплой
- **Только вручную**: GitHub Actions `workflow_dispatch`, параметры — стенд (`test` \| `prod`) и ref (по умолчанию `main`). Никакого автодеплоя при слиянии в ветку: деплой — осознанное действие, а не побочный эффект merge.
- Workflow: ref → SHA → если образа `:<sha>` нет в registry — сборка + тесты + push; затем SSH на VPS: дамп БД стенда → `docker compose pull` → `up -d` (Flyway мигрирует при старте) → ожидание healthcheck; не поднялся — workflow падает.
- **Продвижение, а не пересборка**: тест и прод из одного SHA получают один и тот же образ — на прод уходит ровно то, что проверено на тесте.
- prod деплоится только из `main` (правило GitHub Environment `prod`); test — из любой ветки (проверить ветку до слияния).
- Одновременно — не больше одного деплоя на стенд (`concurrency`).
- Секреты деплоя — в GitHub Environments `test`/`prod`: SSH-ключ отдельного пользователя `deploy` на VPS (только docker compose в каталоге проекта, без sudo). Секреты приложения (токены ботов, OpenRouter, сервисный токен) — только в env-файлах на VPS, в GitHub не хранятся.

## 13. Ходячий скелет (этап 2, 2026-11-03)

### Упрощения этапа 2 (снимаются на этапах 3–5)

### Код
- Доставка уведомлений — «как минимум один раз»: отправка, затем одной транзакцией запись в `reminder_deliveries` (`insert … on conflict do nothing`) и `DONE`. Падение между ними даёт повтор после рестарта — лучше дубль, чем потеря. Ошибки Telegram 400/403 — постоянные (`FAILED`, напоминание закрыто), остальные (сеть, 401, 429, 5xx) — повтор на следующем тике.
- `timestamptz` в Exposed — через `OffsetDateTime` в UTC (`timestampWithTimeZone`), чтобы не зависеть от таймзоны JVM; в контейнерах дополнительно `-Duser.timezone=UTC`.
- Ошибки инструментов для модели и пользовательские шаблоны — в ресурсах (`texts/*.properties`, `mcp/*.md`, `mcp/*.schema.json`), не в коде.
- Ответ после успешного `create_reminder` — шаблон кодом («Поставил: «…» — завтра в 09:00»), дата словами считается в таймзоне пользователя. Ошибка инструмента возвращается модели; не больше 2 раундов инструментов на сообщение.
- Логи: уровень INFO (`logback.xml`, переопределение — `THESEUS_LOG_LEVEL`); SQL Exposed и внутренние логи ktgbotapi заглушены — они содержат тексты пользователей. Логгер ktgbotapi заменяется при старте (`TelegramLogging`): наружу только уровень и класс исключения.
- Агент при старте проверяет токен бота (`getMe`) и падает при ошибке: иначе long polling с неверным токеном крутится в плотном цикле ошибок 401 (найдено на локальном прогоне стенда).
- Healthcheck агента — без HTTP-сервера: пульс раз в 30 с вызывает `getMe` и обновляет файл; контейнер нездоров, если файл старше 120 с. Проверяет и живость процесса, и связь с Telegram, и валидность токена.

### Сборка и тесты
- Convention-плагин `theseus.serialization` (плагин компилятора kotlinx.serialization виден модулям только через build-logic).
- Интеграционные тесты (Testcontainers, `postgres:17-alpine`) — отдельный набор `integrationTest` в `:core`, входит в `check`; без Docker пропускается (`disabledWithoutDocker`), в CI Docker есть.
- detekt: свой `config/detekt/detekt.yml` поверх умолчаний — `MaxLineLength` 140 (как у ktlint, иначе инструменты спорят), `ReturnCount` не считает guard clauses.

### Деплой
- Образы — `deploy/Dockerfile` (`eclipse-temurin:21-jre`) из дистрибутива `installDist`: Gradle в образе и на VPS не запускается. Файлы копируются с явными правами (`COPY --chmod=755`, нужен BuildKit): jar из Gradle-кеша бывают `600`, и пользователь контейнера не смог бы их прочитать. JVM: `-XX:+UseSerialGC` (меньше RSS на маленькой куче), heap и `mem_limit` — из env стенда.
- Локальный замер (heap 128m, без нагрузки, arm64): core ~195–230 МБ RSS, agent ~160 МБ, Postgres ~40 МБ. Лимиты `mem_limit` теста (300m) — с запасом ~25 %; фактические цифры prod — на VPS при первом деплое.
- PostgreSQL 17 (`postgres:17-alpine`) — тот же образ в Testcontainers.
- Роли БД кластерные, поэтому имена с префиксом стенда: `theseus_<стенд>_core`, `theseus_<стенд>_agent`; у каждой — своя схема и `CONNECT` только к своей базе. Создаёт идемпотентный `deploy/vps/infra/initdb/10-theseus.sh`.
- Сеть `theseus-db` общая для стендов, поэтому core адресуется по имени контейнера `theseus-<стенд>-core`, а не по имени сервиса `core` (оно было бы неоднозначным, когда агент тоже подключится к `theseus-db`). Агент на этапе 2 к `theseus-db` не подключён.
- На VPS — каталог `/opt/theseus`: файлы из `deploy/vps/` копирует workflow при каждом деплое; секреты (`<стенд>/stand.env`, `infra/infra.env`) кладёт владелец; тег образа — `<стенд>/image.env` (пишет `deploy.sh`, прежний — `image.env.prev` для отката).
- Логин в ghcr.io на VPS — на время одного деплоя токеном `GITHUB_TOKEN` job'а: постоянных учётных данных реестра на сервере нет.
- «prod — только из `main`» проверяет сам workflow (`git merge-base --is-ancestor <sha> origin/main`): правило веток GitHub Environment смотрит на ветку запуска workflow, а не на параметр `ref`.
