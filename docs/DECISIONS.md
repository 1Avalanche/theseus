# Theseus — журнал решений

Статус: v1 = напоминания. Схемы БД и контракты v1 утверждены (§11), ходячий скелет — §13.

## 0. Название и язык
- Проект/платформа — **Theseus** (корабль из «Ложной слепоты»): репозиторий, сервисы `theseus-core`, `theseus-agent`, пакеты `…theseus`. Персона агента — **Сири**.
- Всё, кроме кода, — на русском: документация (`docs/`), KDoc, правила и скиллы Claude, промпты LLM, тексты для пользователя, описания PR. Идентификаторы — английский.
- Сообщения коммитов — **на английском**, формат `<scope>: <summary>` с указанием модуля/функционала (заменяет прежнее «коммиты на русском»).
- Документация обязательна и обновляется вместе с кодом.
- Правила и скиллы, выявленные в работе, сразу добавляются в `.claude/rules` / `.claude/skills`.
- Поиск по коду для Claude — через MCP-сервер индекса IDE (плагин IntelliJ), grep — запасной вариант.

## 1. Платформа и инфраструктура
- Язык: Kotlin. Один репозиторий, многомодульный Gradle. Юнит-тесты обязательны.
- VPS, Docker Compose, `restart: unless-stopped` + healthcheck.
- БД: PostgreSQL. Миграции — Flyway; перед миграцией — автодамп; изменения схемы аддитивные.
- LLM: OpenRouter (OpenAI-совместимый API, tool calling).
- Telegram: long polling (без webhook/домена/TLS).
- Масштаб: до 30 пользователей.
- VPS: 2 ГБ RAM (данные владельца, 2026-11-02). Порог объединения сервисов (< 1,5 ГБ) не достигнут — core и agent остаются отдельными процессами. Бюджет памяти (ориентир, проверяется на этапе 2):

  | Что | RSS |
  |---|---|
  | ОС + Docker | ~300 МБ |
  | PostgreSQL (`shared_buffers` 128 МБ) | ~200–250 МБ |
  | core (JVM, `-Xmx256m`) | ~400 МБ |
  | agent (JVM, `-Xmx256m`) | ~400 МБ |
  | запас (бэкап, пики, тестовый стенд по требованию — §12) | ~650 МБ |

  - Лимиты памяти — у каждого контейнера в compose (`mem_limit`), heap JVM — явно; swap-файл 1–2 ГБ как страховка от OOM.
  - Gradle на VPS не запускается: образы собираются вне сервера, VPS только скачивает и запускает их.

## 2. Архитектура
- Два сервиса:
  - **core** — домен, БД, планировщик, уведомления.
  - **agent** — Telegram-бот + LLM-пайплайн.
- core — гибрид:
  - **MCP** — только инструменты, видимые LLM (операции над напоминаниями и т.п.).
  - **REST (internal)** — системные вызовы агента (пользователи, доступ, инвайты, usage, квоты) и будущие не-ИИ клиенты.
  - Оба — тонкие адаптеры над общими application-сервисами.
- Контекст пользователя: агент передаёт `userId` + сервисный токен в заголовке/`_meta`, **никогда** через аргументы LLM.
- Планировщик — в core, корутина, опрос БД каждые 30–60 с; статус `PENDING → SENT`; при старте — досыл просроченных.
- Уведомления: интерфейс `Notifier` в core; v1 — `TelegramNotifier` (Bot API `sendMessage`).
- История диалога — в отдельной схеме агента в том же Postgres (миграции агента — свои).

## 3. Принцип
- **Всё, что можно сделать детерминированно (код, скрипты, пайплайны), делается кодом.**
- LLM: понимание естественного языка, извлечение сущностей, уточняющие вопросы, семантическое сопоставление, диалог.
- Код: даты/таймзоны/RRULE, валидация, кандидаты на дубли, рендер списков, онбординг, кнопки, snooze, права.

## 4. Доступ и пользователи
- Пользователь = Telegram chatId.
- Админ — chatId из конфига. Команды админа в боте: `/invite`, `/users`, `/revoke`, `/restore` (добавлена в §11), `/stats`.
- Инвайт: одноразовый код + TTL (~72 ч), ссылка `t.me/<bot>?start=<код>`; при активации — уведомление админу. **Без** подтверждения кнопкой.
- **При генерации инвайта админ указывает грамматический род пользователя** (м / ж / не указан). Не указан → агент избегает гендерно окрашенных форм. Менять позже — через профиль.
- Незарегистрированные chatId отсекаются без вызова LLM.
- Онбординг — детерминированный FSM: имя (кнопка с `first_name` или текст) → таймзона. Без онбординга агент не работает.
- Таймзоны по умолчанию (кнопки): **Москва, Екатеринбург, Другая** (геолокация или город → IANA, с подтверждением). Список — в конфиге.
- Хранение: таймзона — IANA-строка в профиле; время — `timestamptz` (UTC).

## 5. Учёт и квоты
- core хранит usage по каждому LLM-запросу (модель, токены in/out, стоимость из ответа OpenRouter).
- Квоты закладываются в модель данных и API, **в v1 выключены**.

## 6. Агент
- Пайплайн с швом под роутер-классификатор; **v1 — один агент с инструментами** (классификация и уточнения — внутри него). Роутер подключается с появлением второго домена.
- Мягкость: низкая уверенность → уточняющий вопрос; не по теме → вежливо + что умею; жёсткий отказ — только злоупотребление/квота.
- Диалог:
  - последние ~20 сообщений + скользящее саммари; новая «сессия» после паузы в несколько часов;
  - результаты инструментов в истории (сжато);
  - нумерация пунктов списков → `номер → reminderId` в состоянии сессии;
  - связь `telegram message_id → reminderId` (reply на уведомление);
  - `typing`, inline-кнопки для подтверждений, сериализация обработки по chatId.

## 7. Напоминания — сценарии
1. Создать (разовое / повторяющееся), проверка дублей в core → `possible_duplicate` → подтверждение → `force`.
2. Изменить / перенести (для серии: одно срабатывание или вся серия).
3. Удалить (подтверждение; для серии: одно или вся серия).
4. Показать все активные / за период (рендер кодом, нумерация).
5. Найти (core отдаёт кандидатов, LLM сопоставляет по смыслу; позже — pgvector).
6. Snooze с уведомления (+15 мин / +1 ч / завтра), без LLM.
7. Пропустить одно срабатывание серии.
8. Пауза / возобновление серии (в т.ч. «до даты») — **в v1**.
- Повторы: RRULE (RFC 5545) + IANA-таймзона + локальное время; следующее срабатывание считается библиотекой в локальной таймзоне. LLM заполняет структуру (freq, interval, byDay, time, until), RRULE собирает код.
- Время без указания часа → дефолт (напр. 09:00, конфиг).

## 8. Персона «Сири»
- Имя Сири, мужской род («я поставил»), общение на «ты».
- Прототип — Сири Китон («Ложная слепота», П. Уоттс). Берём наблюдательность, точность, сдержанную иронию; не берём холодность.
- Факты о себе — **только из карточки персонажа** (файл, составляет владелец); вне карточки — уклоняется в образе.
- **Спойлеры: говорит только о себе, финал не раскрывает.**
- Образ меняет тон, не поведение: функция важнее образа.
- Детерминированные ответы (онбординг, подтверждения, уведомления) — шаблоны в голосе Сири, в ресурсах.
- Карточка — короткая (~300–500 токенов), отдельный версионируемый файл; промпт собирается из блоков.

## 9. Выбор LLM
- Модель — параметр конфига (по ролям: `main`, `summary`, позже `router`); агент не завязан на провайдера.
- Критерии: русский язык, надёжный tool calling / structured output, низкая латентность, prompt caching. Без reasoning/thinking-моделей.
- В конфиге все три модели, порядок = приоритет (OpenRouter `models` fallback):
  1. `anthropic/claude-haiku-5.5` — **основная** (0.10/0.50 $/1M на 2026-11-02, перепроверить — похоже на промо);
  2. `google/gemini-3.1-flash-lite` (0.25/1.50);
  3. `openai/gpt-5.4-nano` (0.20/1.25).
- summary: самая дешёвая адекватная модель из списка.
- Eval-набор (50–100 русских запросов, детерминированная проверка аргументов tool calls) — подтверждает выбор и служит регрессией при смене модели/промпта.
- Приватность: в OpenRouter ограничить провайдеров / запретить data collection.
- Ответ после успешного tool call — шаблоном (кодом), второй вызов LLM только когда нужен диалог.

## 10. Бэкап
- Ночной `pg_dump` с ротацией; порт БД наружу не открыт.
- Доставка на QNAP: предварительно — шифрованный дамп (age/gpg) на Яндекс.Диск по WebDAV, QNAP забирает оттуда. Альтернатива — pull по SSH/rsync (уточняется).

## 11. Контракты v1 (этап 1, утверждено владельцем 2026-11-02)
Документы: схема БД — `docs/database.md`, MCP — `docs/api/mcp.md`, REST — `docs/api/rest.md`, eval — `docs/eval.md`.

### Данные
- `users.id` (bigint) — единственный `userId` между сервисами; chatId — атрибут пользователя. Роль `USER`/`ADMIN` хранится в core: админ создаётся core при старте из конфига; роль защищает админа от `/revoke`.
- Автор инвайта не хранится (решение владельца, 2026-11-02): админ один и задан конфигом, аудит ничего не даёт, а проверка «создаёт админ» в core опиралась бы на id, который подставляет сам агент. Права админа проверяет агент по chatId, core доверяет сервисному токену. При нескольких админах — добавить nullable-колонку новой миграцией.
- Инвайт: хранится SHA-256 кода, не код; состояние (`ACTIVE`/`USED`/`EXPIRED`/`REVOKED`) вычисляется из времён, а не хранится.
- Напоминание и серия — одна таблица: `start_local` + `timezone` + `recurrence_rule` (строка RRULE; null — разовое) + производное `next_fire_at` (UTC) для планировщика. Таймзона — снимок на момент создания.
- Статус напоминания `ACTIVE`/`PAUSED`/`DONE`/`DELETED` + журнал отправок `reminder_deliveries` (`SENT`/`FAILED`, unique по срабатыванию). **Уточняет** «`PENDING → SENT`» из §2: для серии статус «отправлено» имеет смысл только у срабатывания, поэтому он в журнале.
- Пропуск/перенос одного срабатывания серии: `excluded_occurrences` у серии + (для переноса) разовое напоминание с `parent_id`. Аналог EXDATE/RECURRENCE-ID из RFC 5545 без отдельной таблицы исключений.
- Snooze — поле `snoozed_until`, `next_fire_at = min(расписание, snooze)`; повторный snooze заменяет предыдущий.
- Маппинг `telegram message_id → reminderId` для reply хранит **core** (`reminder_deliveries.telegram_message_id`): уведомления отправляет core, агент этих id не видит. Уточняет §6; маппинг `номер пункта → id` остаётся в состоянии сессии агента.
- Агент: `dialog_sessions` (саммари, состояние сессии), `dialog_messages` (хранение 30 дней), `pending_actions` (подтверждения по кнопкам), `onboarding_state`. Каждый сервис — своя схема и своя роль БД.
- Отзыв доступа обратим (решение владельца, 2026-11-02): `REVOKED → ACTIVE` (или `ONBOARDING`, если онбординг не завершён) командой админа `/restore` — дополняет список команд §4. Во время отзыва срабатывания пропускаются, после восстановления не досылаются.
- Мягкое удаление напоминаний; тексты запросов к LLM в `llm_usage` не хранятся.

### MCP
- Транспорт Streamable HTTP без сессий; токен — заголовок, пользователь — `_meta["theseus/user_id"]`.
- Девять инструментов: `create_reminder`, `list_reminders`, `find_reminders`, `get_reminder`, `update_reminder`, `delete_reminder`, `snooze_reminder`, `pause_reminder`, `resume_reminder`. Пропуск срабатывания — `delete_reminder` с `scope=occurrence`, без отдельного инструмента: меньше инструментов — надёжнее выбор модели.
- Модель передаёт время «как сказал пользователь» (`When`: `date`/`time`/`after`), локальными строками; всё вычисление (ближайшее будущее, сдвиги, таймзона, DST, «в прошлом») — core. Повторение — структура `Recurrence`, RRULE собирает core. Частота чаще раза в день в v1 не поддерживается.
- Поля JSON — `snake_case` и в MCP, и в REST: одно соглашение на все внешние контракты.
- Дубли: кандидат = похожий текст **и** пересекающееся расписание; пороги в конфиге. `possible_duplicate` — успешный ответ, не ошибка.
- Подтверждение удаления — кодом агента: вызов `delete_reminder` от модели перехватывается, показывается карточка с кнопками (`pending_actions`), в core уходит только после нажатия.
- Ошибки — `isError` + JSON `{code, message}`; `message` по-русски для модели; чужие id неотличимы от несуществующих.

### REST
- `/internal/v1`, Bearer сервисный токен, `GET /health` без авторизации.
- Пользователи (поиск по chatId до LLM, активация инвайта, профиль/онбординг, список, отзыв), инвайты, usage + статистика, квота (в v1 всегда `enabled: false`), snooze по кнопке, поиск напоминания по reply.
- Кнопки уведомлений: `callback_data = snz:<delivery_id>:<15m|1h|tmr>`; нажатие → REST snooze без LLM.

### Eval
- 97 кейсов в `agent/eval/reminders.jsonl` + фикстуры. Время сравнивается после разрешения кодом core (`$resolves_to`), повторения — после нормализации (`$normalizes_to`): разные записи одного смысла равноценны.

### Открытые вопросы этапа 1
- Закрыто в §15: смена таймзоны пользователя не пересчитывает существующие напоминания; отличие зоны явно показывается.
- Закрыто в §15: «до 10-го» возобновляет 10-го, «по 10-е включительно» — 11-го; прежняя допустимость обоих вариантов в eval заменена этим правилом.
- Закрыто в §15: отдельные настраиваемые значения частей суток вместо одного времени 09:00 для всех.

## 12. Стенды, CI и деплой (решение владельца, 2026-11-02)

### Стенды
- Два стенда на одном VPS: **prod** и **test**. Каждый — свои процессы core и agent и свой Telegram-бот: тест проверяется «в бою» на реальном Telegram и OpenRouter, не трогая пользователей.
- Один `docker-compose.yml`, два compose-проекта с разными env-файлами: `theseus-prod`, `theseus-test`. Различия — только конфиг: токен бота, имя БД, роли БД, теги образов, chatId админа.
- **PostgreSQL — один на оба стенда**, в отдельном compose-проекте `theseus-infra`; базы `theseus_prod` и `theseus_test`, у каждого стенда свои роли без доступа к чужой базе. Второй контейнер Postgres стоил бы ~250 МБ из 2 ГБ.
- Ключ OpenRouter — **один** на оба стенда. Расходы стендов различаются по `llm_usage` в их базах.
- В тестовой базе — только тестовые данные, копия прода туда не заливается (приватность).
- Тестовый стенд поднимается **по требованию** (деплоем на тест) и гасится после проверки (`docker compose -p theseus-test down`): prod и test вместе занимают ~1,9 ГБ из 2 ГБ, без запаса на бэкап и пики. Swap 1–2 ГБ — обязательно. Нужен постоянный тест — VPS на 4 ГБ, а не урезание heap.

  | Что | МБ |
  |---|---|
  | ОС + Docker | ~300 |
  | PostgreSQL | ~280 |
  | prod core + agent (heap 256 МБ) | ~800 |
  | test core + agent (heap 128 МБ) | ~550 |

### Репозиторий и CI
- Репозиторий — **GitHub** (приватный до решения §20). Основная ветка — `main`, работа — в `develop`.
- CI (`./gradlew build`: тесты, ktlint, detekt) — автоматически на push и PR. Это только проверка, **не деплой**.
- Образы core и agent — GitHub Container Registry (`ghcr.io`), тег — SHA коммита. На VPS Gradle не запускается.

### Деплой
- **Только вручную**: GitHub Actions `workflow_dispatch`, параметры — стенд (`test` \| `prod`) и ref (по умолчанию `main`). Никакого автодеплоя при слиянии в ветку: деплой — осознанное действие, а не побочный эффект merge.
- Workflow: ref → SHA → если образа `:<sha>` нет в registry — сборка + тесты + push; затем SSH на VPS: дамп БД стенда → `docker compose pull` → `up -d` (Flyway мигрирует при старте) → ожидание healthcheck; не поднялся — workflow падает.
- **Продвижение, а не пересборка**: тест и прод из одного SHA получают один и тот же образ — на прод уходит ровно то, что проверено на тесте.
- prod деплоится только из `main` (правило GitHub Environment `prod`); test — из любой ветки (проверить ветку до слияния).
- Одновременно — не больше одного деплоя на стенд (`concurrency`).
- Секреты деплоя — в GitHub Environments `test`/`prod`: SSH-ключ отдельного пользователя `deploy` на VPS (только docker compose в каталоге проекта, без sudo). Секреты приложения (токены ботов, OpenRouter, сервисный токен) — только в env-файлах на VPS, в GitHub не хранятся.

### Код
- Доставка уведомлений — «как минимум один раз»: отправка, затем одной транзакцией запись в `reminder_deliveries` (`insert … on conflict do nothing`) и `DONE`. Падение между ними даёт повтор после рестарта — лучше дубль, чем потеря. Ошибки Telegram 400/403 — постоянные (`FAILED`, напоминание закрыто), остальные (сеть, 401, 429, 5xx) — повтор на следующем тике.
- `timestamptz` в Exposed — через `OffsetDateTime` в UTC (`timestampWithTimeZone`), чтобы не зависеть от таймзоны JVM; в контейнерах дополнительно `-Duser.timezone=UTC`.
- Ошибки инструментов для модели и пользовательские шаблоны — в ресурсах (`texts/*.properties`, `mcp/*.md`, `mcp/*.schema.json`), не в коде.
- Ответ после успешного `create_reminder` — шаблон кодом («Поставил: «…» — завтра в 09:00»), дата словами считается в таймзоне пользователя. Ошибка инструмента возвращается модели; не больше 2 раундов инструментов на сообщение.
- Логи: уровень INFO (`logback.xml`, переопределение — `THESEUS_LOG_LEVEL`); SQL Exposed и внутренние логи ktgbotapi заглушены — они содержат тексты пользователей. Логгер ktgbotapi заменяется при старте (`TelegramLogging`): наружу только уровень и класс исключения.
- Агент при старте проверяет токен бота (`getMe`) и падает при ошибке: иначе long polling с неверным токеном крутится в плотном цикле ошибок 401 (найдено на локальном прогоне стенда).
- Healthcheck агента — без HTTP-сервера: пульс раз в 30 с вызывает `getMe` и обновляет файл; контейнер нездоров, если файл старше 120 с. Проверяет и живость процесса, и связь с Telegram, и валидность токена.

Файлы копируются с явными правами (`COPY --chmod=755`, нужен BuildKit): jar из Gradle-кеша бывают `600`, и пользователь контейнера не смог бы их прочитать. ## 14. Дополнения после проектного ревью (2026-11-05)

Владелец принял дополнение контракта повторного выполнения и уточнение eval (пункты 2 и 8 ревью), потребовал ограничить контекст и защитить обработку от зацикливания (пункт 6). Ниже — целевые требования, **не реализованные на этапе 2**. Остальные предложения на момент этой записи не были утверждены; последующее согласование и численные значения — §15.

### Повторное выполнение
- Идентификатор операции назначает код агента, не LLM: UUID в `_meta["theseus/operation_id"]` для изменяющих MCP-инструментов и `Idempotency-Key` для POST/PATCH internal REST. Читающим запросам ключ не нужен.
- Агент долговечно сохраняет ключ и аргументы **до** обращения к core. Повтор того же входящего события, callback, сетевой повтор и восстановление после рестарта используют прежний ключ; новое намеренное действие — новый ключ.
- Физическое хранение общего журнала операций агента ещё предстоит спроектировать: `pending_actions` покрывает только подтверждения. Долговечное сохранение обычных аргументов не разрешает хранить открытые секреты (например, `invite_code` при активации); безопасное восстановление таких запросов нужно определить до реализации повторов соответствующих REST-операций.
- Core хранит результаты в плановом реестре `operation_results`. Ключ уникален в пределах базы стенда между MCP и REST; привязан к субъекту, операции и каноническим аргументам. Отсутствие поля и явный `null` различаются. Повтор с изменёнными параметрами — `idempotency_conflict`, без изменения данных и раскрытия чужого результата.
- Доменное изменение и сохранение результата — одна транзакция. Конкурентный повтор не выполняет изменение второй раз: ждёт результат либо получает повторяемый `operation_in_progress`. Откат транзакции откатывает и доменное изменение, и запись реестра.
- После коммита повтор возвращает сохранённый исходный результат без пересчёта относительного времени. Аутентификация и необходимые проверки доступа выполняются перед выдачей результата; отзыв доступа не обходится повтором старого ключа. Текущее состояние объекта получают отдельным читающим запросом.
- `possible_duplicate` — завершённый результат исходной операции; подтверждённое создание с `force` — новая операция. Подтверждённое действие получает один ключ: повтор callback не создаёт новую операцию, а незавершённую обработку можно довести до конца после рестарта.
- В v1 реестр автоматически не очищается: забытый ключ не должен позволять повторное изменение. Реестр содержит пользовательские данные и входит в область политики удаления данных пользователя; это не устанавливает новые сроки хранения остальных данных.
- Исключение для `POST /invites`: открытый инвайт-код не сохраняется в реестре, как и в основной таблице (§11). Повтор возвращает квитанцию о том же инвайте без кода (`code: null`, `code_unavailable: true`), не создаёт новый. Новый код — только новая операция по явному действию админа; прежний инвайт можно отозвать.
- Это гарантия повторного выполнения изменений внутри core, **не** «ровно одна доставка» в Telegram. Доставка уведомлений остаётся «как минимум один раз» (§13).

### Контекст и защита от циклов
- Общий входной контекст ограничивается вместе с системным промптом, схемами инструментов, историей и результатами инструментов; вывод ограничивается отдельно. Обязательные правила и контекст доступа не удаляются ради сокращения запроса.
- На одно сообщение задаются общий срок обработки, предел числа обращений к LLM (включая повторы) и вызовов инструментов. Повторяющиеся вызовы без прогресса останавливает код агента; промпт не является механизмом защиты от циклов.
- Численные значения на момент этой записи не утверждены; согласованные значения — §15. Предел двух раундов инструментов (§13) сохранён.

### Eval
- Уточняет §11 и прежний формат `docs/eval.md`: отсутствующее поле и явный `null` не равны. `$absent` проверяет строго отсутствие; буквальный `null` и `null` внутри `$one_of` — наличие явного `null`.
- Частичное сравнение не должно пропускать опасные сбросы полей при `update_reminder`: отсутствие неразрешённых изменений проверяется явно в соответствующих кейсах.
- `no_mutation` — только инвариант отсутствия изменений, не доказательство полезного ответа. Для таких сценариев нужны непустой ответ ожидаемого вида (уточнение, объяснение ограничения, ответ не по теме) и отдельная оценка содержания. Сбой обработки не считается успешным уточнением; полная семантическая проверка текста не объявляется детерминированной.
- При реализации раннера проверить существующие кейсы на новую семантику и добавить сценарии подмены пользователя, обхода подтверждений, инструкций в недоверенных текстах, повторных запросов и callback, таймаута/рестарта и различия `null`/отсутствия. Изменённые требования к раннеру не означают, что эти кейсы уже добавлены или пройдены.

## 15. Уточнение плана после ревью (2026-11-05)

Владелец утвердил обработчик деплоя, подтверждения на **1 час**, сроки саммари, бюджеты LLM, только текстовый ввод v1, минимальный мониторинг и дополнительные правила напоминаний. Это **целевое состояние, не реализация**: текущие возможности этапа 2 описаны в §13. Этот раздел заменяет противоречащие ему прежние положения; новые зависимости и изменения кода здесь не вводятся.

### Обработчик деплоя
- Вместо доступа пользователя `deploy` к rootful Docker (§12) — ограниченный серверный обработчик. У `deploy` нет членства в группе `docker`, доступа к Docker socket и произвольных привилегированных команд. SSH-ключ запускает только фиксированную команду, без интерактивной оболочки, PTY, туннелей и agent forwarding.
- Обработчик принимает только стенд и проверенный идентификатор разрешённого образа из фиксированного registry. Ограничение prod на утверждённый коммит `main` проверяется доверенной серверной логикой, а не флагом клиента. Обработчик, Compose, секреты и родительские каталоги защищены от записи пользователем деплоя; произвольные скрипты и Compose из ветки не исполняются с привилегиями.
- Разрешены только операции деплоя выбранного стенда: дамп его БД, загрузка разрешённых образов, обновление контейнеров и проверка состояния. Конкретный способ запуска привилегированной части (фиксированный сервис либо узкое правило на root-owned обработчик) предстоит выбрать при реализации. Версии конфигурации деплоя устанавливаются доверенным способом и учитываются вместе с версией приложения.
- Образ получает необходимые секреты своего приложения: ограничение полномочий обработчика не защищает данные стенда от заведомо вредоносного образа. Доверие к сборке и ограничения test/prod сохраняются.

### Подтверждения
- Срок жизни карточки — **1 час** с создания, без автоматического продления. Это заменяет прежние 24 часа в схеме и предложение 5 минут из ревью.
- Карточка фиксирует конкретное действие, напоминание, выбранное срабатывание и значимые показанные данные. Изменение значимых данных или прохождение целевого срабатывания делает карточку неактуальной; нужны актуальная карточка и новое подтверждение. Проверка предусловий и изменение в core должны быть атомарны; технический контракт такой проверки предстоит завершить до реализации. Проверка агентом перед отдельным запросом сама по себе не закрывает гонку.
- Повтор подтверждения использует один `operation_id` (§14). Модель не может выдать себе разрешение на удаление или `force`: подтверждение проверяет код.
- Истечение часа запрещает новое исполнение, но не сверку и получение результата уже закоммиченной операции с прежним ключом. Актуальность карточки проверяется перед первым изменением; повтор завершённой операции не должен пытаться заново выполнить её на изменившемся объекте.

### Саммари
- Открытая сессия использует собственное скользящее саммари. После закрытия саммари хранится **30 дней от `closed_at`**, затем удаляется фоновой очисткой. Срок сырых сообщений остаётся 30 дней от времени сообщения; это разные сроки.
- После паузы 4 часа начинается новая сессия, автоматически не наследующая старое саммари. Это заменяет разрешение переноса из §11 / прежней схемы. Постоянная память не вводится через бесконечное копирование саммари.

### Бюджеты LLM
- На входящий запрос: весь входной контекст не больше **16 000 токенов** (включая system, описания инструментов, историю и результаты), вывод одного обращения — до **2 000**, саммари в контексте — до **1 000**, последних сообщений — до **20** в общем бюджете.
- Эффективный бюджет дополнительно ограничен окном модели с резервом на вывод. При сокращении сохраняются системные правила и контекст доступа, история вызовов/результатов сокращается целыми связками.
- Не больше **3 обращений к OpenRouter**, включая технические повторы, **2 раундов инструментов**, **6 вызовов инструментов** суммарно; общий срок обработки — **90 секунд**. Повтор без новых данных и прогресса останавливает код; технический повтор изменения использует идемпотентность.
- Исчерпание бюджета завершается понятным ресурсным шаблоном. Неопределённый исход изменения сначала сверяется с core; нельзя объявлять его неисполненным только из-за таймаута. Восстановление исхода не даёт права повторно исполнить действие с новым ключом.

### Только текстовый ввод v1
- Пользовательский ввод — только текст личных чатов, включая Unicode-эмодзи. Голос, фото, видео, стикеры, документы, геолокация и медиа с подписью не анализируются и не скачиваются; разрешённому пользователю отвечают шаблоном без LLM. Доступ проверяется прежде обработки контента.
- Inline callback остаётся допустимым системным событием; ограничение контента не отключает кнопки. Telegram-реакция — отдельное событие, не текст сообщения. На момент этой записи правила эмодзи-подтверждений не выбраны; окончательное решение — §16: реакции игнорируются, критичные действия подтверждаются только кнопками.
- Онбординг использует кнопки и текст города / IANA-таймзоны; предложение геолокации из §4 для v1 заменено этим правилом.

### Минимальный мониторинг
- Проверка таймером VPS раз в минуту: последний успешный тик планировщика, живость long polling, возраст/количество просроченных доставок, ошибки Telegram/OpenRouter, свободное место и свежесть успешного бэкапа. Отсутствие пользовательских сообщений само по себе не означает зависание long polling.
- Начальные пороги оповещения: нет тика более **2 минут**, доставка просрочена более **5 минут**, нет успешного ночного бэкапа **26 часов** после включения регулярного бэкапа, диск занят на **80 %**. Повторяющиеся оповещения подавляются. Внешний независимый heartbeat обнаруживает потерю всего VPS; расширенный стек метрик в v1 не вводится.
- Зависшую внутреннюю задачу восстанавливает ограниченный перезапуск; недоступность внешнего сервиса — ожидание с увеличением интервала, без циклических рестартов. Telegram 429 учитывает `retry_after`, 401 требует оповещения о токене, 403 фиксирует недоступность получателя. Это уточняет целевую политику повторов; фактическое упрощение этапа 2 — §13.
- `unhealthy` сам по себе не запускает `unless-stopped`; наблюдение и механизм восстановления проектируются явно.

### Напоминания
- Изменение расписания серии сбрасывает исключения и отменяет ещё не выполненные дочерние переносы **одной транзакцией**. Если такие последствия есть, карточка показывает их количество и запрашивает подтверждение (`CONFIRM_SERIES_RESET`). Изменение только текста не сбрасывает исключения и переносы.
- Совпадение обычного и snooze-срабатывания одной серии в один момент даёт одно уведомление и погашает оба основания. В целевой схеме — одна строка доставки с `kind = SCHEDULED_AND_SNOOZED` и одним `telegram_message_id`; проверки обработанности обоих оснований учитывают этот вид. Запись результата и погашение оснований атомарны; внешняя доставка остаётся «как минимум один раз».
- Пауза отменяет ожидающий snooze серии; карточка сообщает об отмене, возобновление snooze не возвращает. Во время паузы snooze не отправляется.
- После простоя разовое напоминание досылается с отметкой опоздания; для серии досылается только последнее пропущенное обычное срабатывание, затем продолжается будущее расписание. Пауза и отзыв доступа досыла не создают. Пересечение простоя с отдельным ожидающим snooze требует дополнительного правила до реализации.
- Существующие напоминания сохраняют снимок таймзоны; новые используют профильную. Если зоны различаются, карточки и подтверждения явно показывают зону напоминания. Перенос существующих расписаний в другую зону — отдельное явное действие, не побочный эффект изменения профиля.
- Части суток разрешает код по конфигу: утро **09:00**, день **14:00**, вечер **19:00**, ночь без часа — уточнение. Модель распознаёт часть суток, а не назначает её время; контракт дополняется `part_of_day` в `When` / `Recurrence`.
- «До 10-го» — возобновление **10-го**, «по 10-е включительно» — **11-го**; конечный ответ показывает конкретную дату/время. Это закрывает прежнюю неоднозначность §11. Техническое представление включительной границы для расчёта кодом нужно определить до реализации.

### Откат приложения и восстановление БД
- Вопрос владельца о совместном откате не означает согласования автоматического восстановления БД. Прежнее утверждение «аддитивная миграция гарантирует работу старого кода» ошибочно: нужна проверка совместимости старых core и agent с обновлённой схемой и данными (включая новые значения статусов / видов доставки).
- Откат образов с сохранением БД и восстановление всей БД стенда из дампа — разные процедуры. Восстановление возвращает данные к снимку, теряет последующие изменения и может повторить уже отправленные уведомления; затрагивает обе схемы стенда и их журналы операций. На момент этой записи политика выбора процедур не согласована; последующее решение — §16. Автоматическое восстановление при ошибке healthcheck не вводится.

## 16. Простой откат и подтверждения только кнопками (2026-11-05)

Владелец уточнил масштаб: небольшой домашний сервис, редкие изменения полей и статусов. Сложная система совместимости релизов не нужна. Ниже — целевые требования; код в ходе ревью не изменяется.

### Откат и неизвестные значения
- Обычный откат — возврат предыдущих образов core / agent с сохранением текущей БД. Аддитивные миграции и дамп перед обновлением сохраняются. Восстановление дампа — отдельная аварийная процедура с явной оценкой потери новых данных, а не обязательный этап каждого отката.
- Новые неизвестные статусы и аналогичные значения из БД / API обрабатываются мягко на границе чтения: одна запись не обрушает процесс, список или весь тик планировщика. Неизвестное исходное значение сохраняется; его нельзя молча заменить на `ACTIVE`, `DONE` или другой известный статус и затем записать обратно.
- Неизвестный статус пользователя не даёт доступ и не разрешает LLM. Неизвестный статус напоминания не разрешает отправку или изменение; операция с такой записью возвращает `unsupported_state` и понятный ресурсный ответ. Остальные поддерживаемые записи продолжают обрабатываться. При обновлении других полей исходное неизвестное значение не затирается.
- Диагностика — идентификаторы и код ошибки без пользовательских текстов и секретов. Обработка неизвестного значения не означает проглатывания любых ошибок разбора, повреждения данных или сбоев инфраструктуры.
- При реализации нужна узкая регрессия: неизвестное значение не даёт действие / доступ, не изменяет запись и не мешает обработке поддерживаемых записей. Отдельная матрица совместимости всех релизов или сложный механизм переключения версий в v1 не вводятся.
- Граница гарантии: уже выпущенный образ без мягкого обработчика не получает его при откате. Базовая версия, на которую рассчитывают откатываться, должна содержать эту защиту. Она также не компенсирует произвольные несовместимые изменения схемы; правило аддитивных миграций остаётся обязательным.

### Реакции и текстовые эмодзи
- Telegram-реакции в v1 игнорируются: не меняют состояние, не попадают в историю диалога и не вызывают LLM.
- Unicode-эмодзи в текстовом сообщении остаются обычным текстом и могут выражать одобрение в диалоге. Они не заменяют подтверждение критичного действия, включая `👍` через reply на карточку.
- Удаление, создание поверх дубля (`force`) и сброс исключений / переносов серии подтверждаются **только inline-кнопками**. Сохраняются срок 1 час, проверка владельца, актуальности цели и идемпотентность. Текстовое «да» также не обходит кнопочное подтверждение; LLM не может подтвердить действие от имени пользователя.

## 17. Реализация ограниченного деплоя (2026-11-07)

Владелец поручил реализовать предложенный механизм §15. Детализация:

- Python 3 со стандартной библиотекой; два точных разрешения sudo на root-owned обработчик с `-I`, без shell и произвольных аргументов. SSH-ключи test/prod раздельные, forced command закрепляет стенд. `authorized_keys`, домашний каталог и startup-файлы `deploy` защищены root; SSH не принимает произвольные команды, PTY, forwarding и пользовательские rc.
- Протокол stdin: до 1024 байт JSON, чтение до EOF не более 10 секунд. Для деплоя — только `action=deploy` и полный SHA `release`; для выключения test — только `action=stop`. Стенд приходит из фиксированной команды ключа. Общий неблокирующий flock исключает одновременные операции test/prod; администратор меняет конфигурацию и разрешения под той же блокировкой.
- Разрешение релиза устанавливает владелец административным действием: `releases/<стенд>/<sha>.json` содержит SHA, версию конфигурации и два проверенных digest. Build release выдаёт только кандидата разрешения. Проверка происхождения доверенной сборки и соответствия digest — ответственность владельца при утверждении; SHA-тег и image label не считаются доказательством. Автоматическая инфраструктура подписей не вводится.
- Registry и репозиторий фиксированы в root-owned конфигурации. Prod дополнительно проверяет через HTTPS GitHub Compare API, что SHA — предок текущей `main` или сама вершина (`ahead`/`identical` и совпадающий merge base). Ошибка API блокирует запуск. Отдельный read-only credential GitHub хранится только на VPS; GHCR использует отдельную root-only конфигурацию Docker с доступом чтения пакетов.
- Compose запускает оба образа по digest. Конфигурацию и обработчик workflow не заменяет; версия комплекта сопоставляется с разрешением релиза. Приложения получают прежние необходимые секреты из VPS env-файлов. Обычный Deploy workflow отправляет только JSON по SSH.
- Последовательность: проверка разрешения и PostgreSQL → дамп выбранной БД → фиксация образов → pull/up → health. Последние 10 дампов сохраняются; общий prune не выполняется. Ошибка после переключения образов записывает `failed`, без восстановления БД. `image.env.prev` — предыдущая попытка, не гарантия последнего здорового релиза; для отката выбирается известный разрешённый релиз.
- На первом шаге сборка образов в GitHub — `linux/amd64`; перед установкой требуется подтвердить `uname -m=x86_64` на VPS. Поддержка ARM требует отдельной адаптации сборки. Локальная проверка SSH/sudo выполняется в Ubuntu 22.04 без подключения Docker socket хоста; отдельно проверяется настоящий Compose с фиктивными токенами. Реальный успешный Telegram-сценарий и проверка после перезагрузки остаются частью первого деплоя на VPS.

## 18. Fix 1.1: приветствие и ограниченный диалог перед мониторингом (2026-11-07)

Владелец выявил регрессию: вопрос «кто ты» получал отказ о несозданном напоминании, а прежний test-бот представлялся с неподдерживаемыми календарём, списком дел и проверкой конфликтов. Защитный фикс свободного текста перекрыл и обычный диалог; прежнее приветствие было генерацией модели, а не реализованным онбордингом.

- `/start` и `/help` — детерминированные ответы из ресурсов после проверки пользователя в core. Приветствие использует имя из профиля, повторяется по команде и одинаково работает на test/prod. Команда не создаёт и не меняет профиль; полноценный онбординг остаётся этапом 3.
- Для естественных вопросов агент добавляет локальный `assistant_reply` к инструментам MCP. LLM выбирает тему `greeting`, `about`, `capabilities`, `clarify` либо `unsupported`; код принимает только поле `topic` и выводит проверенный ресурсный текст. Свободный текст, подмена имени и новые темы не принимаются. Вопросы не сопоставляются регулярными выражениями: смысл определяет LLM; синтаксис Telegram-команд разбирает код.
- Локальный инструмент не обращается в core и не является новым MCP-контрактом. Создание разового напоминания по-прежнему выполняется `create_reminder`, а подтверждение — шаблоном по результату core. Защита от ложных подтверждений сохраняется.
- Текущие возможности описываются как создание разовых напоминаний; календарь, список дел, повторы и проверка конфликтов не обещаются. Уточнение просит полный запрос: истории между сообщениями ещё нет. Свободный диалог, история и полноценные уточнения остаются дальнейшей работой.
- Изменение проверяется регрессионными тестами и общей сборкой. Поддержка ресурса в коде не означает его развёртывание: перед продвижением в prod нужны проверки `/start`, `/help`, «кто ты», «что умеешь» и реального напоминания на test.

## 19. Автоматическое разрешение релиза и доступ владельца (2026-11-08)

Владелец согласовал отдельный `Authorize release` и потребовал сохранить исключительный доступ к деплою при публикации репозитория. Этот раздел заменяет ручное разрешение как основной процесс из §17; административная установка проверенного разрешения остаётся аварийным путём.

- `Build release`, `Authorize release` и `Deploy` запускаются вручную только владельцем личного репозитория `1Avalanche/theseus`, с workflow из `main`. Проверяются ID исходного автора, инициатор повторного запуска и исходный репозиторий. Форки, PR и другие авторы не получают задачи с SSH-секретами. Перенос репозитория или смена владельца требует явного обновления ограничений.
- Новый workflow принимает ID успешной сборки и стенд. Задача предпросмотра без SSH-секретов скачивает один `release-candidate`, проверяет происхождение и SHA-256 ZIP, показывает SHA, digest обоих образов и идентификатор артефакта. Следующая задача использует неизменяемые выходы предпросмотра после approval Environment; повторный поиск «последней» сборки после approval запрещён.
- Environments `test` и `prod`: единственный required reviewer — владелец, self-review разрешён для работы в одиночку, обход правил администраторами отключён, workflow допускается только из `main`. SSH-секреты хранятся только в Environment. Поддержка required reviewers зависит от тарифа и видимости; в публичном репозитории доступна на актуальных тарифах. Настройка и проверка правил обязательны при установке, наличие workflow не доказывает их включение.
- Отдельные test/prod-ключи authorizer вызывают только `python3 -I deploy_handler.py authorize <стенд>` через root-owned entry point и точные sudoers-команды. Ключи Deploy не принимают запрос разрешения; ключи authorizer не выполняют deploy/stop и не выбирают стенд из JSON. Общий Unix-пользователь сохраняется: разделение обеспечивают root-owned forced commands и отсутствие иных путей запуска произвольных команд.
- Запрос содержит только `action=authorize`, числовые `build_run_id`/`artifact_id`, `artifact_digest` и SHA `release`; прежний лимит 1024 байт и срок чтения 10 секунд сохраняются. Authorizer сам обращается к API фиксированного репозитория: успешный ручной запуск `.github/workflows/release.yml` из `main`, ID исходного/head-репозитория и оба автора сверяются с root-owned `authorization.json`. Токен VPS получает только чтение Contents и Actions.
- Сервер скачивает выбранный artifact ID, сверяет заявленный и вычисленный SHA-256 ZIP, принимает только небольшой `release.json` без извлечения файлов на диск. Токен не передаётся на signed URL хранилища; допускаются HTTPS-хранилища GitHub Actions/Azure Blob без дальнейших редиректов. Неизвестный формат, отсутствие digest и ошибки API дают отказ. Инфраструктура подписей не добавляется.
- Разрешение записывается атомарно под общей с Deploy блокировкой `/opt/theseus/deploy.lock`. Для prod сервер проверяет принадлежность коммита текущей `main`. Повтор той же записи идемпотентен; другой набор digest под уже разрешённым SHA запрещён. Authorizer не запускает контейнеры и не меняет Compose, обработчик или env-файлы. Deploy остаётся отдельным действием.
- Реализация в репозитории и локальные тесты не означают установку на VPS или настройку GitHub. До живой установки действует прежний ручной процесс; обычный откат образов и запрет автоматического восстановления БД сохраняются.

## 21. Минимальные сигналы работоспособности и интервалы 10 минут (2026-11-11)

Владелец одобрил реализацию минимального мониторинга и увеличение временных порогов и периода проверки до 10 минут. Этот раздел заменяет период в одну минуту и пороги 2/5 минут из §15. Порог заполнения диска 80 % и проверка ночного бэкапа через 26 часов после его включения сохраняются.

- Рабочий планировщик продолжает запускаться раз в 30 секунд; long polling использует штатный короткий таймаут. 10 минут — порог отсутствия их успешного прогресса и задержки доставки, период host-монитора, пауза между попытками автовосстановления. Из-за дискретной проверки обнаружение отсутствия пульса занимает примерно 10–20 минут.
- Сервисы публикуют атомарные диагностические JSON-файлы v1 в `/tmp/theseus-core.monitor.json` и `/tmp/theseus-agent.monitor.json` раз в 30 секунд. Это локальные данные эксплуатации, не новый публичный REST/MCP-контракт. Содержимое — время, состояние задач, агрегаты и коды ошибок; тексты, идентификаторы пользователей, токены и ответы провайдеров не включаются. Чтение с VPS — фиксированными `docker exec ... cat`.
- Пульс core обновляется после завершённого прохода, включая пустую очередь. Неудачная отдельная доставка не останавливает пульс: отказ виден в агрегате очереди и ошибках Telegram. Агрегат ожидающих доставок считает сам core одним запросом count/min без ограничения размером пачки планировщика; миграция не требуется.
- Пульс agent обновляется только успешным `getUpdates`, включая пустой ответ. `getMe` остаётся стартовой проверкой токена и не обновляет пульс. Ошибки polling, отправки Telegram и OpenRouter раздельны; отсутствие входящих сообщений не считается сбоем. Docker healthcheck agent использует время последнего успешного polling с порогом 600 секунд.
- Скрытые повторы Telegram-клиента отключены в точках сборки. Для polling — ограниченные по длительности запросы и экспоненциальная пауза до 10 минут; для доставки — отложенная повторная попытка планировщиком. Telegram `retry_after` имеет приоритет над локальной паузой. Отправка не повторяется внутри одного запроса; гарантия доставки остаётся «как минимум один раз» (§13). 400/403 закрывают конкретную доставку, 401 сохраняет её для повтора и отражается в диагностике.
- Root-owned скрипт VPS запускается `systemd.timer` раз в 10 минут. Проверяет prod всегда, test — после запуска до явного `stopped`. Использует общую блокировку с Deploy и не вмешивается в обновление. Неизвестная/устаревшая диагностика вызывает тревогу, но не даёт права рестарта. Для внутреннего отсутствия прогресса при доступных зависимостях допускаются два рестарта контейнера, не чаще раза в 10 минут; бюджет сохраняется до команды и сбрасывается только отдельной здоровой проверкой. БД, сеть и внешние API не лечатся циклическими рестартами.
- Изменение набора проблем и восстановление дают оповещение; одинаковые состояния не повторяются. Неуспешно доставленное локальное оповещение повторяется. Внешний сервис получает POST на отдельный URL успеха либо отказа; отсутствие запросов обнаруживает потерю VPS/проверяющего процесса. Период внешнего check — 10 минут, допуск задержки — 10 минут. Уведомления внешнего сервиса должны иметь независимый от Сири канал. Отдельный Telegram-бот локальных тревог необязателен. Конкретный сервис, получатель и секретные URL задаются при установке.
- Реализация и локальные проверки не означают установку systemd на VPS или проверку реального внешнего канала. Живой контур и проверка искусственных отказов на VPS отмечаются отдельно в roadmap.
