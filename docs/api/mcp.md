# MCP core: инструменты для LLM

Статус: утверждён владельцем 2026-11-02 (этап 1). Решения и причины — `docs/DECISIONS.md`, раздел 11. Схема данных — `docs/database.md`.

**Реализация (этап 2):** работает один инструмент — `create_reminder`, только разовые (`when`). `recurrence` → `invalid_recurrence`; проверки дублей нет (`possible_duplicate` не возвращается), `force` принимается и игнорируется; в схеме инструмента для модели поле `recurrence` не объявлено. Остальные восемь инструментов, повторяющиеся и дубли — этапы 4–5 (`docs/DECISIONS.md`, §13). Контракт ниже описывает целевое состояние.

MCP — только то, что может вызвать модель: операции над напоминаниями пользователя. Пользователи, инвайты, usage, квоты — **не здесь**, а в internal REST (`docs/api/rest.md`).

## Транспорт и контекст

- MCP Streamable HTTP, `POST /mcp` на внутреннем порту core (наружу не публикуется). Режим без сессий: каждый `tools/call` самодостаточен.
- Каждый запрос — с заголовком `Authorization: Bearer <THESEUS_SERVICE_TOKEN>`. Нет/неверный токен → HTTP 401.
- Пользователь — только в `_meta` запроса `tools/call`: `"_meta": {"theseus/user_id": 42}`. Выставляет **код агента**; в аргументах инструментов `user_id` нет и быть не может. core проверяет, что пользователь существует и `ACTIVE`, иначе ошибка `user_inactive`. Все запросы к данным фильтруются по этому `user_id`.
- «Сейчас» — `Clock` core, таймзона — из профиля пользователя в core. Агент кладёт в промпт то же локальное время, расхождение — секунды.
- Описания инструментов и полей (на русском) хранятся в ресурсах core и отдаются через `tools/list`. Агент передаёт их модели без изменений.
- Агент может вызывать инструменты и сам, без LLM: подтверждение по кнопке, рендер карточки перед подтверждением.

## Формат данных

- JSON, имена полей — `snake_case`, значения перечислений — `lower_snake`.
- Локальное время — строки без смещения, в таймзоне пользователя: дата `YYYY-MM-DD`, время `HH:MM`, момент `YYYY-MM-DDTHH:MM`. Модель **никогда** не считает смещения и UTC — это делает core.
- Точность — минута.
- Отсутствующее поле и `null` различаются только в `update_reminder` (см. там).

### `When` — момент срабатывания

Что сказал пользователь — то и передаётся; вычисляет core.

| Поле | Тип | Описание |
|---|---|---|
| `date` | `YYYY-MM-DD` | конкретная дата. «В пятницу», «15-го», «завтра» — модель переводит в дату по текущей дате из промпта |
| `time` | `HH:MM` | время суток |
| `after` | `{days?, hours?, minutes?}` | сдвиг от текущего момента: «через 5 минут», «через 2 часа», «через неделю» |

Правила (проверяет core):
- `time` без `date` и `after` — ближайшее будущее `HH:MM`: сегодня, если ещё не прошло, иначе завтра.
- `date` без `time` — время по умолчанию (конфиг, 09:00).
- `date` + `time` — ровно этот момент.
- `after` с `hours`/`minutes` — без `date`/`time`. `after` только с `days` можно сочетать с `time` («через неделю в 10» → `{"after":{"days":7},"time":"10:00"}`); без `time` — время по умолчанию.
- `after` и `date` вместе — ошибка `invalid_when`.
- Результат в прошлом → `time_in_past`; дальше 5 лет → `too_far`.
- Несуществующее локальное время (переход на летнее) сдвигается вперёд, неоднозначное — более раннее.

### `Recurrence` — повторение

Модель заполняет структуру, RRULE (RFC 5545) собирает core.

| Поле | Тип | По умолчанию | Описание |
|---|---|---|---|
| `freq` | `daily` \| `weekly` \| `monthly` \| `yearly` | — | обязательное |
| `interval` | int 1–365 | 1 | «каждые 2 недели» → `weekly`, 2 |
| `by_weekday` | список `MO`…`SU`; для `monthly`/`yearly` — с номером: `1MO`, `-1FR` | — | «по будням» → `MO…FR`; «первый понедельник месяца» → `monthly`, `["1MO"]` |
| `by_month_day` | список 1…31, −31…−1 | — | «15-го числа» → `[15]`; «последний день месяца» → `[-1]` |
| `by_month` | список 1…12 | — | для `yearly` |
| `time` | `HH:MM` | конфиг, 09:00 | одно время; «в 9 и в 21» — два напоминания |
| `start_date` | `YYYY-MM-DD` | сегодня | с какой даты |
| `until` | `YYYY-MM-DD` | — | последняя дата включительно |
| `count` | int ≥ 1 | — | сколько раз; вместе с `until` нельзя |

Правила:
- `weekly` без `by_weekday` — день недели `start_date`; `monthly` без `by_month_day`/`by_weekday` — число `start_date`; `yearly` без `by_month` — день и месяц `start_date`.
- Первое срабатывание — первое по правилу не раньше текущего момента.
- Чаще раза в день (`hourly`) в v1 не поддерживается → `invalid_recurrence`; модель объясняет ограничение.
- `by_month_day` 29–31 в `monthly`: короткие месяцы пропускаются (RFC 5545), в результате — предупреждение `short_months_skipped`.

### `ReminderView` — напоминание в ответах

```json
{
  "id": 17,
  "text": "Позвонить маме",
  "kind": "recurring",
  "status": "active",
  "schedule": {
    "recurrence": {"freq": "weekly", "interval": 1, "by_weekday": ["SU"], "time": "18:00", "start_date": "2026-11-08"}
  },
  "next_at_local": "2026-11-08T18:00",
  "paused_until_local": null,
  "snoozed_until_local": null
}
```

- `kind`: `one_time` \| `recurring`. Для `one_time` — `"schedule": {"at_local": "2026-11-03T15:00"}`.
- `status`: `active` \| `paused` \| `done` \| `deleted`.
- `recurrence` — нормализованная: заполнены все поля, значения по умолчанию раскрыты.
- `next_at_local` — ближайшее срабатывание с учётом snooze и исключений; `null` — срабатываний больше нет.

### Ошибки

Ошибка — результат с `isError: true`, в `content` один текстовый блок с JSON:

```json
{"error": {"code": "time_in_past", "message": "Время 2026-11-02T09:00 уже прошло, сейчас 10:15.", "details": {"now_local": "2026-11-02T10:15"}}}
```

`message` — по-русски, для модели: что не так и что можно сделать. Модель по нему решает, переспросить ли пользователя.

| Код | Когда |
|---|---|
| `invalid_arguments` | не прошла схема: нет обязательного поля, неверный формат, лишнее поле |
| `invalid_when` | противоречивые поля `When` |
| `time_in_past` | момент в прошлом |
| `too_far` | дальше 5 лет |
| `invalid_recurrence` | неподдерживаемое или противоречивое повторение |
| `not_found` | напоминания нет у этого пользователя (чужие id неотличимы от несуществующих) |
| `not_recurring` | операция только для серий (`scope=occurrence`, пауза) на разовом |
| `occurrence_not_found` | у серии нет срабатывания в указанный момент |
| `invalid_state` | операция невозможна в текущем статусе (возобновить активное, изменить удалённое) |
| `user_inactive` | пользователь из `_meta` не найден или не `ACTIVE` (ошибка интеграции, не модели) |
| `internal` | непредвиденная ошибка; подробности — только в логах core |

## Инструменты

Девять инструментов. Изменяющие — `create_reminder`, `update_reminder`, `delete_reminder`, `snooze_reminder`, `pause_reminder`, `resume_reminder`.

### `create_reminder`

Создать разовое или повторяющееся напоминание (сценарий 1).

| Аргумент | Тип | |
|---|---|---|
| `text` | string 1–1000 | что напомнить — коротко, своими словами пользователя, без слов «напомни», даты и времени |
| `when` | `When` | для разового |
| `recurrence` | `Recurrence` | для повторяющегося |
| `force` | bool, по умолчанию `false` | создать, даже если найдены возможные дубли; модель ставит только после подтверждения пользователя |

Ровно одно из `when` / `recurrence`, иначе `invalid_arguments`.

Результат:
```json
{"status": "created", "reminder": {…ReminderView}, "warnings": []}
```
или, если `force = false` и найдены похожие активные напоминания:
```json
{"status": "possible_duplicate", "candidates": [{…ReminderView}]}
```
`possible_duplicate` — не ошибка: ничего не создано, агент показывает кандидатов и кнопки «всё равно создать» / «не надо» (код, не модель).

Кандидат в дубли (детерминированно, в core): напоминание пользователя в статусе `active`/`paused`, у которого **одновременно**
- похожий текст: после нормализации (нижний регистр, `ё→е`, без пунктуации) совпадает или сходство множеств слов (Жаккар) ≥ 0,6;
- пересекается расписание: для разовых — моменты в пределах ±60 минут; для серий — одинаковые `freq` и `time`, пересекаются дни; разовое против серии — разовое попадает на срабатывание серии ±60 минут.
Пороги — в конфиге core.

### `list_reminders`

Показать напоминания (сценарий 4). Список пользователю рендерит **код агента** с нумерацией; модель получает сжатую сводку.

| Аргумент | Тип | |
|---|---|---|
| `from` | `YYYY-MM-DD` | начало периода включительно |
| `to` | `YYYY-MM-DD` | конец периода включительно; период не больше 92 дней |
| `include_paused` | bool, по умолчанию `true` | |

Без периода — все активные (и приостановленные) напоминания:
```json
{"reminders": [{…ReminderView}]}
```
сортировка по `next_at_local`, приостановленные — в конце.

С периодом (`from` и `to` оба) — срабатывания в периоде, серии раскрыты:
```json
{"occurrences": [{"reminder_id": 17, "at_local": "2026-11-08T18:00"}], "reminders": [{…ReminderView}]}
```
`reminders` — только упомянутые в `occurrences`. Не больше 200 срабатываний; при обрезке — `"truncated": true`.

### `find_reminders`

Найти напоминания по описанию (сценарий 5), чтобы получить `id` для изменения/удаления. Сопоставление по смыслу делает модель.

| Аргумент | Тип | |
|---|---|---|
| `query` | string | как пользователь назвал напоминание: «про маму», «таблетки» |

Результат: `{"candidates": [{…ReminderView}]}` — до 30 активных и приостановленных напоминаний пользователя, по убыванию текстового сходства с `query`; если всего ≤ 30 — все. Пустой список — напоминаний нет. Позже ранжирование заменит pgvector — контракт не изменится.

### `get_reminder`

Одно напоминание с ближайшими срабатываниями: «когда следующее?», карточка перед подтверждением.

| Аргумент | Тип | |
|---|---|---|
| `reminder_id` | int | |

Результат: `{"reminder": {…ReminderView}, "upcoming_local": ["2026-11-08T18:00", "2026-11-15T18:00"]}` — до 5 ближайших срабатываний.

### `update_reminder`

Изменить текст или перенести (сценарий 2).

| Аргумент | Тип | |
|---|---|---|
| `reminder_id` | int | |
| `scope` | `series` \| `occurrence` | для серий обязателен; для разовых не передаётся |
| `occurrence_local` | `YYYY-MM-DDTHH:MM` | для `scope=occurrence`: какое срабатывание; по умолчанию ближайшее |
| `text` | string | новый текст |
| `when` | `When` | новое время разового напоминания или одного срабатывания серии |
| `recurrence` | `Recurrence`, частично | для `scope=series`: переданные поля заменяют текущие, `null` — сбросить (`"until": null`) |

Нужно хотя бы одно из `text` / `when` / `recurrence`.
- Разовое + `recurrence` — превращается в серию (все поля `Recurrence`, кроме заданных, — по умолчанию; `freq` обязателен).
- Серия + `scope=series` + `when` — `invalid_arguments` (чтобы сделать серию разовой — удалить и создать).
- `scope=occurrence`: срабатывание исключается из серии, создаётся разовое напоминание с `parent_id` серии и новым временем/текстом.
- Изменение расписания серии сбрасывает её исключения (`excluded_occurrences`).
- Проверка дублей при изменении не выполняется.

Результат: `{"status": "updated", "reminder": {…ReminderView}, "warnings": []}`; для `scope=occurrence` `reminder` — новое разовое, плюс `"series": {…ReminderView}`.

### `delete_reminder`

Удалить напоминание, серию или одно срабатывание серии — «пропустить» (сценарии 3 и 7).

| Аргумент | Тип | |
|---|---|---|
| `reminder_id` | int | |
| `scope` | `series` \| `occurrence` | для серий обязателен |
| `occurrence_local` | `YYYY-MM-DDTHH:MM` | для `scope=occurrence`; по умолчанию ближайшее |

**Подтверждение — кодом агента.** Вызов `delete_reminder` от модели агент в core не передаёт: берёт карточку через `get_reminder`, показывает её с кнопками «удалить» / «оставить» и сохраняет `pending_action`. В core инструмент вызывается только после нажатия «удалить». Модель об этом знает из описания инструмента и сама не переспрашивает.

Результат: `{"status": "deleted", "reminder": {…}}` или `{"status": "occurrence_skipped", "reminder": {…}, "occurrence_local": "2026-11-08T18:00"}`.

### `snooze_reminder`

Отложить срабатывание (сценарий 6): «напомни ещё раз через час». Кнопки уведомления идут не сюда, а в REST (`POST /internal/v1/deliveries/{id}/snooze`) — тот же сервис.

| Аргумент | Тип | |
|---|---|---|
| `reminder_id` | int | |
| `when` | `When` | когда напомнить снова |

Для разового в статусе `done` — снова `active` с новым временем. Для серии — дополнительное срабатывание, расписание серии не меняется. Повторный snooze заменяет предыдущий.

Результат: `{"status": "snoozed", "reminder": {…ReminderView}}`.

### `pause_reminder`

Приостановить серию (сценарий 8): «не напоминай про спортзал до 10-го».

| Аргумент | Тип | |
|---|---|---|
| `reminder_id` | int | только серия, иначе `not_recurring` |
| `resume_on` | `YYYY-MM-DD` | дата, с которой серия снова работает; нет — бессрочно |

Срабатывания во время паузы не досылаются. В `resume_on` серия возобновляется автоматически (планировщик).

Результат: `{"status": "paused", "reminder": {…ReminderView}}`.

### `resume_reminder`

Возобновить приостановленную серию.

| Аргумент | Тип | |
|---|---|---|
| `reminder_id` | int | |

Следующее срабатывание — первое по расписанию после текущего момента. Не на паузе → `invalid_state`.

Результат: `{"status": "resumed", "reminder": {…ReminderView}}`.
