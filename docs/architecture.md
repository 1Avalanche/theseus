# Архитектура Theseus

Решения и их причины — `docs/DECISIONS.md`. Здесь — как система устроена сейчас.

## Сервисы

| Сервис | Gradle-модуль | Назначение | Статус |
|---|---|---|---|
| core | `:core` | домен, PostgreSQL, планировщик, уведомления; наружу MCP (инструменты LLM) и internal REST | разовые напоминания; пользователи, инвайты и usage |
| agent | `:agent` | Telegram-бот, LLM-пайплайн через OpenRouter | long polling, онбординг и журнал системных событий; истории диалога пока нет |

Описание модулей — `docs/modules/<модуль>.md`.

## Контракты и хранение

Контракты зафиксированы на этапе 1. Реализованы `create_reminder` для разовых напоминаний и системные REST-вызовы пользователей, инвайтов и usage. Изменяющие REST-запросы используют реестр результатов core и журнал агента. Статус и оставшиеся проверки этапа 3 — в `docs/roadmap.md`.

Идемпотентность изменяющих MCP-вызовов, часовые подтверждения с проверкой актуальности, ограничения контекста и вызовов, сроки саммари и правила серий остаются целевыми требованиями (`DECISIONS.md` §14–15). Подтверждения последствий должны появиться до включения изменения расписания серии.

- **БД:** один PostgreSQL, две схемы — `core` и `agent`; каждый сервис мигрирует только свою, agent схему `core` не читает. Таблицы и правила — `docs/database.md`.
- **MCP** (только инструменты для LLM, напоминания) — `docs/api/mcp.md`.
- **Internal REST** (пользователи, инвайты, usage, квоты, кнопки уведомлений, поиск по reply) — `docs/api/rest.md`.
- **Eval-набор LLM** (`agent/eval/`, не входит в `./gradlew build`) — `docs/eval.md`.

## Поток: «напомни через 5 минут»

1. Telegram → **agent** (long polling). Сообщения личных чатов; одного chatId — строго по очереди.
2. agent спрашивает core по REST (`GET /internal/v1/users/by-chat/{chat_id}`). Незнакомому пользователю предлагает инвайт, для `ONBOARDING` запускает сбор профиля; неактивный пользователь не вызывает LLM.
3. После проверки доступа `/start`, `/help` и `/version` отвечают ресурсами agent без LLM. Для обычного текста активного пользователя agent проверяет квоту и строит системный промпт (персона → факты → правила → контекст с текущим локальным временем пользователя), затем шлёт запрос в **OpenRouter** с инструментами MCP core (`tools/list`) и локальным `assistant_reply`. Последний выбирает готовый диалоговый ответ из ресурсов agent, не обращается в core и не изменяет данные; подтверждение создания напоминания остаётся результатом `create_reminder` из core. Usage записывается в core.
4. Модель вызывает `create_reminder` с `when.after = {minutes: 5}`. agent передаёт вызов в **MCP core** (`POST /mcp`, Bearer-токен), `userId` — в `_meta["theseus/user_id"]`.
5. core в таймзоне пользователя считает момент срабатывания (`WhenResolver`) и сохраняет напоминание в **PostgreSQL** (`next_fire_at`, UTC).
6. agent отвечает пользователю шаблоном по результату инструмента («Поставил: …»). Ошибку инструмента получает модель (не больше 2 раундов инструментов на сообщение).
7. **Планировщик** core раз в 30 с выбирает наступившие напоминания, отправляет уведомление через `Notifier` → **Telegram**, в одной транзакции пишет `reminder_deliveries` и переводит напоминание в `DONE`.

## Сборка

- Gradle Kotlin DSL, JVM 21 (toolchain; JDK скачивается через foojay при отсутствии).
- Версии всех зависимостей и плагинов — только в `gradle/libs.versions.toml`.
- Общие настройки модулей — convention-плагины в `build-logic/` (included build):

| Плагин | Что даёт |
|---|---|
| `theseus.kotlin-jvm` | Kotlin JVM 21, JUnit (BOM) + MockK для тестов, ktlint, detekt |
| `theseus.application` | `theseus.kotlin-jvm` + плагин `application` (запускаемый сервис) |
| `theseus.serialization` | плагин компилятора kotlinx.serialization (виден модулям только через build-logic) |

- Пакеты: `theseus.<модуль>…`, group `theseus`.
- Версия приложения задана `theseusVersion` в `gradle.properties`; convention-плагин включает её в ресурс обоих дистрибутивов. `/version` читает ресурс запущенного agent; сейчас версия сборки `0.3.0`.
- Включены Gradle build cache, configuration cache и параллельная сборка (`gradle.properties`).

### Новый модуль
1. Каталог `<модуль>/` с `build.gradle.kts`, применяющим `theseus.kotlin-jvm` или `theseus.application`.
2. `include(":<модуль>")` в `settings.gradle.kts`.
3. `README.md` модуля и `docs/modules/<модуль>.md`.

Пошаговая процедура для Claude — скилл `.claude/skills/add-module/`.

## Качество кода

- **ktlint** (плагин `org.jlleitschuh.gradle.ktlint`) — стиль; входит в `check`. Автоисправление: `./gradlew ktlintFormat`.
- **detekt** `2.0.0-alpha` (плагин `dev.detekt`) — статический анализ; свой `config/detekt/detekt.yml` поверх умолчаний (`MaxLineLength` 140 как у ktlint, `ReturnCount` не считает guard clauses), подключён в `theseus.kotlin-jvm`; входит в `check`. Стабильная ветка 1.23 не поддерживает Kotlin 2.4 — перейти на стабильный 2.x, когда выйдет.

## Тесты

- Юнит-тесты (`src/test`): без инфраструктуры, фиксированный `Clock`, фейки портов, LLM не вызывается. `./gradlew :<module>:test`.
- Интеграционные (`:core` и `:agent`, набор `integrationTest`): миграции и хранилища на реальном PostgreSQL 17 (Testcontainers). Входят в `check`/`build`; без Docker пропускаются. Отдельно: `./gradlew :core:integrationTest :agent:integrationTest`.
- Eval-набор LLM — не входит в сборку, `docs/eval.md`.

## Деплой

Два стенда (prod, test) на одном VPS, общий PostgreSQL; образы core и agent (`deploy/Dockerfile`) — в ghcr.io с тегом SHA коммита; деплой — вручную через GitHub Actions. CI (`.github/workflows/ci.yml`) на push и PR только проверяет. Настройка VPS, переменные окружения, откат — `docs/operations.md`.

Деплой выполняет ограниченный серверный обработчик: пользователь `deploy` без Docker socket/группы `docker`, отдельные forced-command ключи Authorize и Deploy для каждого стенда, root-owned обработчик и конфигурация. Build release создаёт кандидат, Authorize release показывает артефакт перед approval и после него проверяет и разрешает релиз на сервере; Deploy отдельно запускает разрешённые образы по digest. Для prod сервер проверяет принадлежность коммита `main`. Новый authorizer установлен на VPS; по сообщению владельца, кандидат продвинут через test в prod и напоминание получено. Итоговый prod `state.json` и runtime image IDs независимо не сверялись. Первичная установка — `docs/deploy-setup.md`.

Мониторинг v1: core и agent обновляют локальные диагностические снимки, а монитор VPS раз в 10 минут проверяет рабочие задачи, очередь, зависимости и диск и отправляет внешний heartbeat. Пульс polling отражает успешный `getUpdates`, включая пустой ответ; пульс планировщика — завершённый проход. Таймер активен; владелец подтвердил оповещения об остановке agent, пропуске пульса и восстановление. Живые проверки зависания задачи, лимита рестартов и порогов БД, очереди и диска ещё впереди; контроль бэкапа включается после запуска ночного расписания. Подробности — [monitoring.md](monitoring.md). Расширенный стек метрик не выбран.

Штатный откат домашнего v1 — возврат предыдущих образов с сохранением текущей БД. На границе БД/API неизвестные значения статусов и других enum-подобных полей обрабатываются мягко: не обрушивают процесс и не превращаются в разрешающий статус; исходные записи сохраняются без изменений, недоступная операция даёт `unsupported_state`, остальные записи обрабатываются. Это целевое требование, ещё не реализация. Восстановление дампа — отдельная аварийная процедура с потерей изменений после снимка и риском повторных Telegram-доставок; автоматически при сбое деплоя не выполняется. Аддитивные миграции и дамп перед деплоем сохраняются.
