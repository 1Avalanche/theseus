# Модуль agent

Telegram-бот (long polling) и LLM-пайплайн через OpenRouter. Архитектура — `docs/architecture.md`, решения — `docs/DECISIONS.md` (разделы 2, 6, 8, 9).

**Статус:** этап 4 реализован и проверен локально; текущая версия исходников с исправлениями после ручной проверки — `0.4.1`. Gradle-модуль `:agent`, плагины `theseus.application` + `theseus.serialization`, точка входа `theseus.agent.MainKt`. Проверки и их границы — `docs/roadmap.md`.

## Пакеты `theseus.agent`

| Пакет | Содержимое |
|---|---|
| `config` | `AgentConfig` из env, валидация при старте; переменные — `docs/operations.md` |
| `core` | порт `CoreClient` (`findUserByChat`, `listTools`, `callTool`); `HttpCoreClient` — REST + MCP-клиент (Streamable HTTP), Bearer-токен, `userId` в `_meta["theseus/user_id"]` |
| `llm` | порт `LlmClient`; `OpenRouterClient` — запрос с `models` (fallback по порядку из `THESEUS_LLM_MAIN_MODELS`) и `provider.data_collection = deny` |
| `prompt` | `PromptBuilder`: системный промпт из блоков `persona/siri.md` → `persona/siri-facts.md` → `prompts/rules.md` → `prompts/context.md` (имя, род, локальное время и таймзона пользователя; стабильные блоки первыми — для prompt caching) |
| `pipeline` | `MessageHandler` (обработка сообщения), `ReminderActions` (подтверждения), `ReplyRenderer` (ответ по результату core), `DialogReplies` (команды и готовые ответы локального диалога) |
| `system` | `SystemHandler`, `Onboarding`, `AdminCommands`, `McpOperations`, журнал операций и `UsageRecorder` |
| `storage` | `JdbcAgentStore`, Flyway и `JournalCipher`: отдельная схема agent и зашифрованное содержимое журнала |
| `telegram` | `TelegramBotRunner` — long polling, личные чаты, мьютекс на chatId; `MonitoredTelegramBot` наблюдает запросы Telegram и повторяет polling с паузой при ошибке |
| `monitoring` | `AgentMonitor` — локальный снимок состояния polling, ошибок Telegram/OpenRouter и пульс healthcheck от успешного `getUpdates` |
| `texts` | загрузка `texts/agent.properties` |

JSON-кодек `OpenRouterClient` использует `encodeDefaults = true`: обязательное протокольное поле `type: "function"` сохраняется в описаниях `tools` и истории `tool_calls`, даже когда это значение по умолчанию Kotlin-модели. HTTP-регрессии на Ktor `MockEngine` проверяют фактически сериализованное тело исходящего запроса для обоих случаев, включая связь `tool_call_id`. Это проверка границы HTTP-клиента без обращения к реальному OpenRouter. Схема инструментов MCP отдельно сериализуется SDK с обязательным `type: "object"`; обнаруженный дефект касается исходящего JSON OpenRouter.

Снимок `/tmp/theseus-agent.monitor.json` обновляется каждые 30 секунд и не содержит тексты сообщений. Успешный пустой ответ `getUpdates` тоже обновляет пульс; отсутствие пользовательских сообщений не считается отказом. Инструкция по мониторингу — [monitoring.md](../monitoring.md).

Исправление после сбоя prod 2026-11-12 добавляет к HTTP- и socket-таймаутам SDK для `getUpdates` запас 15 секунд: при ожидании Telegram 30 секунд сетевые таймауты составляют 45 секунд. Прочие запросы сохраняют свои таймауты, прежний Java-движок Ktor не менялся. Тест через настоящий SDK и задержанный `MockEngine` проверяет пустые ответы, сетевой отказ без пульса и таймауты `getMe`; до исправления воспроизведён сбой пустого ответа. Тест с настоящим Java HTTP-движком и локальным сервером подтвердил два пустых ответа. Полный `build` прошёл; исправление развёрнуто в prod релизом `338a2a3373cf9ccc2335327ef8b69ef588247308`, agent `healthy` и пульс есть.

## Поток сообщения

1. `findUserByChat` в core **до** команд и LLM. Незнакомый chatId получает приглашение ввести `/start <код>`; `ONBOARDING` проходит сбор имени и часового пояса, `REVOKED` не вызывает LLM.
2. `SystemHandler` обрабатывает `/start`, `/help`, `/version`, административные команды и кнопки кодом без LLM. Для активного профиля `/start` повторно приветствует пользователя, `/help` показывает возможности; `/version` сообщает версию дистрибутива. Админские команды доступны только chatId из конфига.
3. Остальные сообщения получают системный промпт, инструменты из MCP core (список кэшируется в процессе) и локальный `assistant_reply`. При однозначном намерении создать напоминание промпт требует вызвать `create_reminder`; даты и календарные вычисления остаются в core. MCP-вызовы уходят в core с `userId` в `_meta`; `assistant_reply` выполняется внутри agent и в core не передаётся. Подтверждение создания формирует только `ReplyRenderer` по успешному результату `created` из core; дату показывает словами в таймзоне пользователя. Текстовый ответ модели сам по себе не подтверждает создание и пользователю не передаётся.
4. Ответ модели без вызовов инструментов до первой попытки даёт ресурсный шаблон `reply.not_created`: «Напоминание не создано. Уточни, что и когда напомнить». После попыток без подтверждённого результата — `reply.unconfirmed`: «Не получил подтверждение выполнения. Проверь актуальный список напоминаний».
5. `find_reminders` возвращает кандидатов модели как промежуточный результат для выбора идентификатора и последующего вызова `update_reminder`, `delete_reminder` или `get_reminder`. Результат `list_reminders` агент сразу рендерит кодом.
6. Успешный `assistant_reply` возвращает проверенный ресурсный текст, который отображается кодом. Если пакет содержит готовые локальные ответы или подтверждённые результаты core, они сразу отображаются пользователю; при неподтверждённом остатке добавляется `reply.unconfirmed`. Такой пакет не отправляется модели для повторного создания уже созданных напоминаний. Известные коды ошибок, включая `invalid_date`, рендерятся ресурсами; остальные ошибки возвращаются модели для исправления аргументов. Не больше 2 раундов инструментов на сообщение; технический сбой — шаблон `reply.failure`.

`assistant_reply` принимает только `topic` из закрытого списка: `greeting`, `about`, `capabilities`, `clarify`, `unsupported`, `unsupported_recurrence`, `invalid_date`, `choose_reminder`, `missing_time`. Последние четыре темы дают конкретный ответ о частом повторе, неверной дате, выборе цели и недостающем времени. Вопросы «кто ты» и «ты ИИ» модель сопоставляет с `about`; ответ из ресурсов представляет Сири как ИИ-секретаря с доступным созданием разовых и повторяющихся напоминаний. Неизвестные темы, свободный текст и имя в аргументах отклоняются кодом. Имя для приветствия берётся только из core. Локальный инструмент не меняет данные и не подтверждает создание напоминания. Помимо локального инструмента агент получает из core девять инструментов напоминаний.

Это ограниченный диалог: модель выбирает смысловую тему, код подставляет ресурс. Произвольный текст модели остаётся под защитой `reply.not_created`/`reply.unconfirmed`. Полноценный диалог — этап 5. Пока нет истории, `clarify` просит повторить полный запрос с содержанием и временем; отдельное сообщение «через 5 минут» не продолжает предыдущий запрос автоматически. Успешный вызов `create_reminder` подтверждает создание в core; доставка уведомления в Telegram проверяется отдельно.

История диалога и кнопки snooze в уведомлениях остаются этапом 5. Из ролей моделей настроена только `main`.

Системные события и исходящие REST-операции записываются до исполнения; повтор использует исходный снимок и UUID. Содержимое событий, запросов и ответов хранится зашифрованным AES-256-GCM. Восстановление после рестарта повторяет незавершённые операции и доставку ответа. Telegram-доставка остаётся как минимум однократной.

Обычное диалоговое сообщение перед LLM получает маркер в `incoming_events` без исходного текста. Готовый ответ сохраняется зашифрованным и используется при повторе update без нового вызова LLM или MCP. Под блокировкой чата перед следующим событием агент восстанавливает все сохранённые результаты MCP и карточки сообщения с исходными ключами; если операций не сохранилось, используется `reply.unconfirmed`. Неопределённый исход не закрывает событие. Каждый фактический вызов LLM получает отдельную операцию usage, REST-повтор записи использует сохранённый UUID.

Онбординг начинается с представления Сири и перечисления доступных возможностей; в том же сообщении он спрашивает имя без персонального обращения. Имя можно ввести текстом либо выбрать кнопкой с Telegram `first_name`. При повторном `/start` с уже сохранённым именем продолжается шаг часового пояса. Часовой пояс выбирается кнопкой, текстовым названием из ресурсного справочника городов или IANA ID; перед сохранением показывается подтверждение кнопкой. Геолокация не используется. Неподдерживаемые медиа и подписи не скачиваются и не отправляются в LLM: после проверки доступа agent отвечает шаблоном. Текстовые Unicode-эмодзи поддерживаются; реакции игнорируются.

Команды администратора: `/invite male|female|unspecified [label]`, `/invites [active|used|expired|revoked|all]`, `/invite_revoke ID`, `/users`, `/revoke ID`, `/restore ID`, `/stats`. Успешный `/revoke` или `/restore` показывает имя и ID пользователя из ответа core; если имя отсутствует, показывает «пользователь №ID». Инвайт действует 72 часа по умолчанию, используется один раз; после активации администратор получает уведомление. Учёт записывает модель, токены, кэш, стоимость, идентификатор генерации и задержку, когда они доступны в ответе OpenRouter; запросы без usage или стоимости завершаются ошибкой обработки.

`/hard_delete ID` доступна только владельцу на test и включается в его `/help`. Удаляет второго пользователя и связанные данные в двух схемах; администратора и самого владельца удалить нельзя. Сначала core блокирует цель, затем агент под общей блокировкой её чата очищает собственные записи и связанные административные кэши, после чего core завершает удаление. Повтор и восстановление используют журнал операций; при потерянном ответе проверяется текущий `user_id` чата, чтобы не стереть новую регистрацию. Для повторного входа нужен новый инвайт, он создаёт новый `user_id`. Уже отправленные сообщения Telegram и старые бэкапы операция не удаляет.

## Целевые ограничения v1 после ревью 2026-11-05

Ниже — утверждённая спецификация. Текстовый ввод, онбординг и игнорирование реакций реализуются на этапе 3; история и бюджеты — последующие этапы; подтверждения критичных действий над напоминаниями реализуются на этапе 4.

- Вход — только текстовые сообщения разрешённых личных чатов, включая обычные Unicode-эмодзи в тексте. Фото, голос, видео, стикеры, документы, геолокация и другие медиа (включая подписи к ним) не скачиваются и не анализируются; LLM не вызывается, пользователь получает шаблон из ресурсов. Проверка доступа выполняется до этой обработки.
- Callback inline-кнопок остаётся системным событием и обрабатывается кодом. Telegram-реакции в v1 полностью игнорируются, не сохраняются в историю и не передаются LLM. Unicode-эмодзи в тексте сохраняются как обычный текст/одобрение, но критичные действия подтверждаются только inline-кнопками: даже `👍` через reply на карточку не заменяет кнопку.
- Онбординг принимает имя, название города / IANA-зону текстом и выбор кнопками; геолокация не требуется и не обрабатывается.
- На границе БД/API неизвестное значение статуса / enum-подобного поля не обрушает обработку остальных записей и не заменяется разрешающим значением. Неизвестный статус пользователя не допускает LLM; `unsupported_state` отображается понятным ресурсным шаблоном. Исходное неизвестное значение сохраняется, неожиданные ошибки не скрываются.
- Последние не более 20 сообщений плюс саммари открытой сессии. Через 4 часа бездействия начинается новая сессия без автоматического наследования саммари. Саммари закрытой сессии хранится 30 дней от `closed_at`, затем очищается; сырые сообщения — 30 дней от их создания.

| Вывод одного обращения | 2 000 токенов |
| Саммари внутри входного контекста | 1 000 токенов |
| Обращения к OpenRouter на входящее сообщение, включая технические повторы | 3 |

Эффективный вход дополнительно ограничен окном выбранной модели за вычетом резерва вывода. Системные правила и контекст доступа не удаляются; история сокращается целыми связками вызова и результата, результаты поиска ограничиваются до передачи модели. Значения — целевые настройки; существование соответствующих env-переменных не заявляется.

Бюджеты проверяет код, а не промпт. Повтор одного инструмента с теми же аргументами без новых данных / прогресса останавливает цикл; технический повтор операции использует прежний ключ идемпотентности и не считается новым намерением. Исчерпание бюджета даёт понятный шаблон ответа. Если исход изменения неизвестен, сначала выясняется результат операции по прежнему ключу; нельзя объявлять изменение неуспешным или запускать новое только из-за таймаута. Само восстановление неопределённого исхода не должно запускать новый цикл LLM; контракт восстановления после исчерпания срока предстоит определить при реализации журнала операций.

## Данные

Схема `agent` содержит `outgoing_operations`, `incoming_events`, `onboarding_state`, `erased_journal`, `pending_actions`; агент подключается отдельной ролью и применяет свои миграции Flyway. История остаётся будущей; `pending_actions` индексирует карточки, а их содержимое хранится зашифрованным в `outgoing_operations`. В схему `core` agent не ходит: только MCP и REST. Подробности — `docs/database.md`.

## Взаимодействие с core

- Инструменты для модели — MCP, `docs/api/mcp.md`; системные вызовы — REST, `docs/api/rest.md`.
- Для изменяющих REST-запросов агент до вызова сохраняет UUID, маршрут, зашифрованное тело и связь с событием, затем передаёт UUID в `Idempotency-Key`. Повтор и восстановление используют ту же запись; модель ключом не управляет. `invite_code` хранится только в зашифрованном содержимом журнала.
- Для изменяющего MCP-вызова `McpOperations` сохраняет UUID, имя инструмента и зашифрованные аргументы до запроса core; повтор и восстановление используют ту же запись и ключ. Журнал хранит карточки подтверждений как `CONFIRM` и сами вызовы как `MCP`.
- `ReminderActions` перехватывает удаление, создание поверх дубля и изменение расписания с исключениями или невыполненными дочерними переносами. Карточка показывает цель и последствия, хранит снимок и выдаёт inline-кнопки. Действие исполняется после нажатия владельца; модель не передаёт `force` или метаданные подтверждения.
- Карточка дубля показывает до двух похожих напоминаний; предлагаемый вариант выводится отдельно, если его отображение отличается от показанных кандидатов. Кнопки называют действие. Расписание с единичным интервалом отображается без «интервал 1», больший интервал — словами. Карточка изменения расписания с последствиями показывает новый час, переданный в `when.time`. Удаление всех текущих напоминаний подтверждается одной карточкой с количеством; снимок набора проверяет core. Несколько вызовов изменения существующих целей в одном ответе модели блокируются до исполнения, предлагается выбор; если есть кандидаты поиска, показываются до пяти с ID. Семантическое сопоставление цели остаётся у модели.
- Карточка действует 1 час, фиксирует цель и конкретное срабатывание. UUID будущего MCP-вызова назначается при создании карточки и хранится в `pending_actions` и зашифрованном содержимом. Агент передаёт отпечаток и время создания в `_meta["theseus/confirmation"]`; core атомарно проверяет актуальность вместе с изменением. При потере ответа повтор использует тот же UUID; относительное время создания поверх дубля фиксируется до карточки. Отмена после начатого исполнения сначала выясняет его исход.
- Кнопки snooze в уведомлениях и reply на уведомление — этап 5.
