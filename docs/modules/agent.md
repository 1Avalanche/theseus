# Модуль agent

Telegram-бот (long polling) и LLM-пайплайн через OpenRouter. Архитектура — `docs/architecture.md`, решения — `docs/DECISIONS.md` (разделы 2, 6, 8, 9).

**Статус:** этап 2 («ходячий скелет»). Gradle-модуль `:agent`, плагины `theseus.application` + `theseus.serialization`, точка входа `theseus.agent.MainKt`. Упрощения этапа 2 и причины — `docs/DECISIONS.md`, §13.

## Пакеты `theseus.agent`

| Пакет | Содержимое |
|---|---|
| `config` | `AgentConfig` из env, валидация при старте; переменные — `docs/operations.md` |
| `core` | порт `CoreClient` (`findUserByChat`, `listTools`, `callTool`); `HttpCoreClient` — REST + MCP-клиент (Streamable HTTP), Bearer-токен, `userId` в `_meta["theseus/user_id"]` |
| `llm` | порт `LlmClient`; `OpenRouterClient` — запрос с `models` (fallback по порядку из `THESEUS_LLM_MAIN_MODELS`) и `provider.data_collection = deny` |
| `prompt` | `PromptBuilder`: системный промпт из блоков `persona/siri.md` → `persona/siri-facts.md` → `prompts/rules.md` → `prompts/context.md` (имя, род, локальное время и таймзона пользователя; стабильные блоки первыми — для prompt caching) |
| `pipeline` | `MessageHandler` (обработка сообщения), `ReplyRenderer` (подтверждение по результату core), `DialogReplies` (команды и готовые ответы локального диалога) |
| `telegram` | `TelegramBotRunner` — long polling, личные чаты, мьютекс на chatId; `HealthHeartbeat` — пульс для healthcheck (`getMe` раз в 30 с, файл `THESEUS_HEALTH_FILE`) |
| `texts` | загрузка `texts/agent.properties` |

JSON-кодек `OpenRouterClient` использует `encodeDefaults = true`: обязательное протокольное поле `type: "function"` сохраняется в описаниях `tools` и истории `tool_calls`, даже когда это значение по умолчанию Kotlin-модели. HTTP-регрессии на Ktor `MockEngine` проверяют фактически сериализованное тело исходящего запроса для обоих случаев, включая связь `tool_call_id`. Это проверка границы HTTP-клиента без обращения к реальному OpenRouter. Схема инструментов MCP отдельно сериализуется SDK с обязательным `type: "object"`; обнаруженный дефект касается исходящего JSON OpenRouter.

## Поток сообщения (этап 2)

1. `findUserByChat` в core **до** команд и LLM; незнакомый или не `ACTIVE` chatId — без ответа и без вызова модели.
2. `DialogReplies` обрабатывает `/start` и `/help` кодом до LLM. Суффикс `@bot` и payload после команды поддерживаются без исполнения payload. `/start` всегда возвращает один и тот же ресурсный текст для текущего профиля: с именем из core, если оно непустое, иначе без имени. `/help` перечисляет реализованные возможности. Повторный `/start` безопасен; логика test/prod общая.
3. Остальные сообщения получают системный промпт, инструменты из MCP core (список кэшируется в процессе) и локальный `assistant_reply`. При однозначном намерении создать напоминание промпт требует вызвать `create_reminder`; даты и календарные вычисления остаются в core. MCP-вызовы уходят в core с `userId` в `_meta`; `assistant_reply` выполняется внутри agent и в core не передаётся. Подтверждение создания формирует только `ReplyRenderer` по успешному результату `created` из core; дату показывает словами в таймзоне пользователя. Текстовый ответ модели сам по себе не подтверждает создание и пользователю не передаётся.
4. Ответ модели без вызовов инструментов до первой попытки даёт ресурсный шаблон `reply.not_created`: «Напоминание не создано. Уточни, что и когда напомнить». После попыток без подтверждённого результата — `reply.unconfirmed`: «Не получил подтверждение выполнения. Не могу обещать, что напоминание создано».
5. Успешный `assistant_reply` возвращает проверенный ресурсный текст, который отображается кодом. Если пакет содержит готовые локальные ответы или подтверждённые результаты core, они сразу отображаются пользователю; при неподтверждённом остатке добавляется `reply.unconfirmed`. Такой пакет не отправляется модели для повторного создания уже созданных напоминаний. Если готовых ответов нет, ошибки инструментов возвращаются модели для исправления аргументов в прежнем цикле. Не больше 2 раундов инструментов на сообщение; технический сбой — шаблон `reply.failure`.

`assistant_reply` принимает только `topic` из закрытого списка: `greeting`, `about`, `capabilities`, `clarify`, `unsupported`. Вопросы «кто ты» и «ты ИИ» модель сопоставляет с `about`; ответ из ресурсов представляет Сири как ИИ-секретаря с доступным созданием разовых напоминаний. Новые темы, свободный текст и имя в аргументах отклоняются кодом, даже если модель игнорирует JSON Schema. Имя для приветствия берётся только из core. Локальный инструмент не меняет данные и не подтверждает создание напоминания. Его наличие не меняет контракт MCP core: там по-прежнему доступен `create_reminder`.

Это ограниченный диалог этапа 2: модель выбирает смысловую тему, код подставляет ресурс. Произвольный текст модели остаётся под защитой `reply.not_created`/`reply.unconfirmed`. Полноценный диалог — этап 5. Пока нет истории, `clarify` просит повторить полный запрос с содержанием и временем; отдельное сообщение «через 5 минут» не продолжает предыдущий запрос автоматически. Команда `/start` — приветствие, а не FSM онбординга: настройки имени и таймзоны она не меняет. Успешный вызов `create_reminder` подтверждает создание в core; доставка уведомления в Telegram проверяется отдельно.

Чего ещё нет: БД и истории диалога, `pending_actions`, подтверждения удаления и дублей, кнопки, онбординг и инвайты, учёт `llm_usage`, шаблон ответа незнакомому chatId (этапы 3–5). Из ролей моделей настроена только `main`.

Идемпотентность запросов и долговечная запись исходящих операций — также целевой контракт этапов 3–5, на этапе 2 не реализованы.

## Целевые ограничения v1 после ревью 2026-11-05

Ниже — утверждённая спецификация, не заявление о реализации этапа 2.

- Вход — только текстовые сообщения разрешённых личных чатов, включая обычные Unicode-эмодзи в тексте. Фото, голос, видео, стикеры, документы, геолокация и другие медиа (включая подписи к ним) не скачиваются и не анализируются; LLM не вызывается, пользователь получает шаблон из ресурсов. Проверка доступа выполняется до этой обработки.
- Callback inline-кнопок остаётся системным событием и обрабатывается кодом. Telegram-реакции в v1 полностью игнорируются, не сохраняются в историю и не передаются LLM. Unicode-эмодзи в тексте сохраняются как обычный текст/одобрение, но критичные действия подтверждаются только inline-кнопками: даже `👍` через reply на карточку не заменяет кнопку.
- Онбординг принимает имя, название города / IANA-зону текстом и выбор кнопками; геолокация не требуется и не обрабатывается.
- На границе БД/API неизвестное значение статуса / enum-подобного поля не обрушает обработку остальных записей и не заменяется разрешающим значением. Неизвестный статус пользователя не допускает LLM; `unsupported_state` отображается понятным ресурсным шаблоном. Исходное неизвестное значение сохраняется, неожиданные ошибки не скрываются.
- Последние не более 20 сообщений плюс саммари открытой сессии. Через 4 часа бездействия начинается новая сессия без автоматического наследования саммари. Саммари закрытой сессии хранится 30 дней от `closed_at`, затем очищается; сырые сообщения — 30 дней от их создания.

| Бюджет | Предел |
|---|---|
| Весь вход, включая системный промпт, схемы инструментов, историю и результаты | 16 000 токенов |
| Вывод одного обращения | 2 000 токенов |
| Саммари внутри входного контекста | 1 000 токенов |
| Обращения к OpenRouter на входящее сообщение, включая технические повторы | 3 |
| Раунды инструментов | 2 |
| Вызовы инструментов суммарно на сообщение | 6 |
| Общий срок обработки сообщения | 90 секунд |

Эффективный вход дополнительно ограничен окном выбранной модели за вычетом резерва вывода. Системные правила и контекст доступа не удаляются; история сокращается целыми связками вызова и результата, результаты поиска ограничиваются до передачи модели. Значения — целевые настройки; существование соответствующих env-переменных не заявляется.

Бюджеты проверяет код, а не промпт. Повтор одного инструмента с теми же аргументами без новых данных / прогресса останавливает цикл; технический повтор операции использует прежний ключ идемпотентности и не считается новым намерением. Исчерпание бюджета даёт понятный шаблон ответа. Если исход изменения неизвестен, сначала выясняется результат операции по прежнему ключу; нельзя объявлять изменение неуспешным или запускать новое только из-за таймаута. Само восстановление неопределённого исхода не должно запускать новый цикл LLM; контракт восстановления после исчерпания срока предстоит определить при реализации журнала операций.

## Ресурсы

| Путь | Назначение |
|---|---|
| `src/main/resources/persona/` | персона Сири и карточка фактов — см. `docs/persona.md` |
| `src/main/resources/prompts/rules.md` | блок «правила» системного промпта: поведение секретаря (черновик) |
| `src/main/resources/prompts/context.md` | шаблон блока «контекст» (подстановки `{name}`, `{gender}`, `{now_local}`, `{weekday}`, `{timezone}`) |
| `src/main/resources/llm/assistant_reply.schema.json` | локальный инструмент диалога: только `topic` из закрытого enum, без дополнительных полей |
| `src/main/resources/texts/agent.properties` | тексты ответов в голосе Сири |

Все промпты — на русском, хранятся в ресурсах, не в коде.

## Данные

На этапе 2 у agent нет БД. План: схема `agent` (отдельная от `core`; в `core` агент ходит только через MCP и REST): `dialog_sessions`, `dialog_messages`, `pending_actions`, `onboarding_state` — `docs/database.md`.

## Взаимодействие с core

- Инструменты для модели — MCP, `docs/api/mcp.md`; системные вызовы — REST, `docs/api/rest.md`.
- Вызов `delete_reminder` от модели агент в core не передаёт: показывает карточку с кнопками «удалить» / «оставить», сохраняет `pending_action` и вызывает инструмент только после подтверждения. Так же с кнопками обрабатывается `possible_duplicate` («всё равно создать»). Подробности — `docs/api/mcp.md`.
- Нажатия кнопок уведомлений (`snz:…`) агент обрабатывает без LLM через REST; reply на уведомление сопоставляет с напоминанием через REST.
- Перед первым изменяющим запросом код агента долговечно сохраняет UUID операции, её аргументы и связь с исходным update / callback. В MCP он передаётся через `_meta["theseus/operation_id"]`, в REST — `Idempotency-Key`; модель ключом не управляет. Технические повторы и восстановление после рестарта используют ту же запись. Подробности — разделы о повторном выполнении в контрактах MCP/REST.
- Физическое хранение общего журнала исходящих операций предстоит спроектировать до включения ретраев; `pending_actions` покрывает лишь подтверждения. Открытые `invite_code` и другие секреты в журнал не записываются; безопасное восстановление содержащих их запросов — отдельный открытый вопрос реализации.
- Для подтверждения ключ исполняемой операции сохраняется в `pending_action` до запроса core. Если core закоммитил действие, а агент не успел записать разрешение карточки, повтор с тем же ключом возвращает исходный результат; агент завершает разрешение без повторного изменения данных.
- Карточка подтверждения действует 1 час, фиксирует цель / срабатывание и снимок значимых данных. Изменение данных или прошедшее срабатывание требуют новой карточки; атомарное условие актуальности в core предстоит определить в техническом контракте. `force` задаёт только код после подтверждения.
- Обновление расписания серии с исключениями или невыполненными дочерними переносами перехватывается так же: карточка `CONFIRM_SERIES_RESET` показывает число последствий; после подтверждения core одной транзакцией меняет расписание, очищает исключения и отменяет невыполненные переносы. Только изменение текста сохраняет их.
