# Модуль agent

Telegram-бот (long polling) и LLM-пайплайн через OpenRouter. Архитектура — `docs/architecture.md`, решения — `docs/DECISIONS.md` (разделы 2, 6, 8, 9).

**Статус:** этап 4 завершён и принят владельцем после ручной проверки `0.4.1` на test-боте. Gradle-модуль `:agent`, плагины `theseus.application` + `theseus.serialization`, точка входа `theseus.agent.MainKt`. Проверки и их границы — `docs/roadmap.md`.

## Пакеты `theseus.agent`

| Пакет | Содержимое |
|---|---|
| `config` | `AgentConfig` из env, валидация при старте; переменные — `docs/operations.md` |
| `core` | порт `CoreClient` (`findUserByChat`, `listTools`, `callTool`); `HttpCoreClient` — REST + MCP-клиент (Streamable HTTP), Bearer-токен, `userId` в `_meta["theseus/user_id"]` |
| `llm` | порт `LlmClient`; `OpenRouterClient` — запрос с `models` (fallback по порядку из настроек) и `provider.data_collection = deny`; `ContextBudget` ограничивает размер входа |
| `dialog` | порт хранения сессий, сообщений и нумерации последнего списка |
| `prompt` | `PromptBuilder`: системный промпт из блоков `persona/siri.md` → `persona/siri-facts.md` → `prompts/rules.md` → `prompts/context.md` (имя, род, локальное время и таймзона пользователя; стабильные блоки первыми — для prompt caching) |
| `pipeline` | `MessageHandler` (обработка сообщения), `ConversationMemory` и `TurnBudget` (история и бюджет), `ReminderActions` (подтверждения), `ReplyRenderer` (ответ по результату core), `PersonaAnswers` (проверка ответа о себе), `DialogReplies` (команды и готовые ответы локального диалога) |
| `system` | `SystemHandler`, `Onboarding`, `AdminCommands`, `McpOperations`, журнал операций и `UsageRecorder` |
| `storage` | `JdbcAgentStore`, `JdbcDialogStore`, Flyway и `JournalCipher`: отдельная схема agent, история и зашифрованное содержимое журнала |
| `telegram` | `TelegramBotRunner` — long polling, личные чаты, мьютекс на chatId; `MonitoredTelegramBot` наблюдает запросы Telegram и повторяет polling с паузой при ошибке |
| `monitoring` | `AgentMonitor` — локальный снимок состояния polling, ошибок Telegram/OpenRouter и пульс healthcheck от успешного `getUpdates` |
| `texts` | загрузка `texts/agent.properties` |

JSON-кодек `OpenRouterClient` использует `encodeDefaults = true`: обязательное протокольное поле `type: "function"` сохраняется в описаниях `tools` и истории `tool_calls`, даже когда это значение по умолчанию Kotlin-модели. HTTP-регрессии на Ktor `MockEngine` проверяют фактически сериализованное тело исходящего запроса для обоих случаев, включая связь `tool_call_id`. Это проверка границы HTTP-клиента без обращения к реальному OpenRouter. Схема инструментов MCP отдельно сериализуется SDK с обязательным `type: "object"`; обнаруженный дефект касается исходящего JSON OpenRouter.

Снимок `/tmp/theseus-agent.monitor.json` обновляется каждые 30 секунд и не содержит тексты сообщений. Успешный пустой ответ `getUpdates` тоже обновляет пульс; отсутствие пользовательских сообщений не считается отказом. Инструкция по мониторингу — [monitoring.md](../monitoring.md).

Исправление после сбоя prod 2026-11-12 добавляет к HTTP- и socket-таймаутам SDK для `getUpdates` запас 15 секунд: при ожидании Telegram 30 секунд сетевые таймауты составляют 45 секунд. Прочие запросы сохраняют свои таймауты, прежний Java-движок Ktor не менялся. Тест через настоящий SDK и задержанный `MockEngine` проверяет пустые ответы, сетевой отказ без пульса и таймауты `getMe`; до исправления воспроизведён сбой пустого ответа. Тест с настоящим Java HTTP-движком и локальным сервером подтвердил два пустых ответа. Полный `build` прошёл; исправление развёрнуто в prod релизом `338a2a3373cf9ccc2335327ef8b69ef588247308`, agent `healthy` и пульс есть.

## Поток сообщения

1. `findUserByChat` в core **до** команд и LLM. Незнакомый chatId получает приглашение ввести `/start <код>`; `ONBOARDING` проходит сбор имени и часового пояса, `REVOKED` не вызывает LLM.
2. `SystemHandler` обрабатывает `/start`, `/help`, `/version`, административные команды и кнопки кодом без LLM. Для активного профиля `/start` повторно приветствует пользователя, `/help` показывает возможности; `/version` сообщает версию дистрибутива. Админские команды доступны только chatId из конфига.
3. Остальные сообщения получают системный промпт, историю открытой сессии, инструменты из MCP core (список кэшируется в процессе) и локальные `assistant_reply`, `resolve_reference`. При однозначном намерении создать напоминание промпт требует вызвать `create_reminder`; даты и календарные вычисления остаются в core. MCP-вызовы уходят в core с `userId` в `_meta`; локальные инструменты выполняются внутри agent. Подтверждение создания формирует только `ReplyRenderer` по успешному результату `created` из core; дату показывает словами в таймзоне пользователя.
4. Ответ модели без вызовов инструментов до первой попытки даёт ресурсный шаблон `reply.not_created`: «Напоминание не создано. Уточни, что и когда напомнить». После попыток без подтверждённого результата — `reply.unconfirmed`: «Не получил подтверждение выполнения. Проверь актуальный список напоминаний».
5. `find_reminders` возвращает кандидатов модели как промежуточный результат для выбора идентификатора и последующего вызова `update_reminder`, `delete_reminder` или `get_reminder`. Чтобы одинаковые поля не занимали бюджет многократно, агент может упаковать однообразные результаты поиска без потери полей и значений: общие значения — в `candidate_common`, имена остальных полей — в `candidate_fields`, строки `candidates` содержат соответствующие значения. Исходный JSON остаётся для рендера. Результат `list_reminders` агент сразу рендерит кодом.
6. `assistant_reply` возвращает ресурсный ответ, а для темы `about` запускает отдельный запрос без инструментов по карточке фактов. Если пакет содержит готовые локальные ответы или подтверждённые результаты core, они сразу отображаются пользователю; при неподтверждённом остатке добавляется `reply.unconfirmed`. Такой пакет не отправляется модели для повторного создания уже созданных напоминаний. Известные коды ошибок, включая `invalid_date`, рендерятся ресурсами; остальные ошибки возвращаются модели для исправления аргументов. Не больше 2 раундов инструментов на сообщение; технический сбой — шаблон `reply.failure`.

`assistant_reply` принимает только `topic` из закрытого списка: `greeting`, `about`, `capabilities`, `clarify`, `unsupported`, `unsupported_recurrence`, `invalid_date`, `choose_reminder`, `missing_time`. Последние четыре темы дают конкретный ответ о частом повторе, неверной дате, выборе цели и недостающем времени. Вопросы о Сири модель сопоставляет с `about`; отдельный промпт просит естественный ответ по карточке фактов. Если ответ ссылается на карточку, промпт или инструкции словами из ресурсного списка, `PersonaAnswers` заменяет его нейтральным ответом. Неизвестные темы, свободный текст и имя в аргументах отклоняются кодом. Имя для приветствия берётся только из core. Локальный инструмент не меняет данные и не подтверждает создание напоминания. Помимо локальных инструментов агент получает из core девять инструментов напоминаний.

В истории сохраняются пользовательские сообщения и итоговые ответы агента. При нажатии inline-кнопки в историю добавляются ресурсная отметка системного события и ответ на него. Если результат исходного диалога восстановлен после сбоя, ответ дописывается к исходному ходу без создания новой сессии. Ответ модели без инструмента не подтверждает создание. Нумерацию последнего выданного списка код сохраняет в сессии; `resolve_reference` принимает положительное целое число, а не строку, и возвращает модели соответствующий `reminder_id` и, если список содержит отдельные срабатывания, `occurrence_local`. Модель не определяет id по номеру самостоятельно.

Системные события и исходящие REST-операции записываются до исполнения; повтор использует исходный снимок и UUID. Содержимое событий, запросов и ответов хранится зашифрованным AES-256-GCM. Восстановление после рестарта повторяет незавершённые операции и доставку ответа. Telegram-доставка остаётся как минимум однократной.

Обычное диалоговое сообщение перед LLM получает маркер в `incoming_events` без исходного текста. Готовый ответ сохраняется зашифрованным и используется при повторе update без нового вызова LLM или MCP. Под блокировкой чата перед следующим событием агент восстанавливает все сохранённые результаты MCP и карточки сообщения с исходными ключами; если операций не сохранилось, используется `reply.unconfirmed`. Неопределённый исход не закрывает событие. Каждый фактический вызов LLM получает отдельную операцию usage, REST-повтор записи использует сохранённый UUID.

Онбординг начинается с представления Сири и перечисления доступных возможностей; в том же сообщении он спрашивает имя без персонального обращения. Имя можно ввести текстом либо выбрать кнопкой с Telegram `first_name`. При повторном `/start` с уже сохранённым именем продолжается шаг часового пояса. Часовой пояс выбирается кнопкой, текстовым названием из ресурсного справочника городов или IANA ID; перед сохранением показывается подтверждение кнопкой. Геолокация не используется. Неподдерживаемые медиа и подписи не скачиваются и не отправляются в LLM: после проверки доступа agent отвечает шаблоном. Текстовые Unicode-эмодзи поддерживаются; реакции игнорируются.

Команды администратора: `/invite male|female|unspecified [label]`, `/invites [active|used|expired|revoked|all]`, `/invite_revoke ID`, `/users`, `/revoke ID`, `/restore ID`, `/stats`. Успешный `/revoke` или `/restore` показывает имя и ID пользователя из ответа core; если имя отсутствует, показывает «пользователь №ID». Инвайт действует 72 часа по умолчанию, используется один раз; после активации администратор получает уведомление. Учёт записывает модель, токены, кэш, стоимость, идентификатор генерации и задержку, когда они доступны в ответе OpenRouter; запросы без usage или стоимости завершаются ошибкой обработки.

`/hard_delete ID` доступна только владельцу на test и включается в его `/help`. Удаляет второго пользователя и связанные данные в двух схемах; администратора и самого владельца удалить нельзя. Сначала core блокирует цель, затем агент под общей блокировкой её чата очищает собственные записи, историю сессий и связанные административные кэши, после чего core завершает удаление. Повтор и восстановление используют журнал операций; при потерянном ответе проверяется текущий `user_id` чата, чтобы не стереть новую регистрацию. Для повторного входа нужен новый инвайт, он создаёт новый `user_id`. Уже отправленные сообщения Telegram и старые бэкапы операция не удаляет.

## Ограничения v1 после ревью 2026-11-05

Ниже — ограничения ввода, подтверждений и бюджета. Статус этапов и проверок — в `docs/roadmap.md`.

- Вход — только текстовые сообщения разрешённых личных чатов, включая обычные Unicode-эмодзи в тексте. Фото, голос, видео, стикеры, документы, геолокация и другие медиа (включая подписи к ним) не скачиваются и не анализируются; LLM не вызывается, пользователь получает шаблон из ресурсов. Проверка доступа выполняется до этой обработки.
- Callback inline-кнопок остаётся системным событием и обрабатывается кодом. Telegram-реакции в v1 полностью игнорируются, не сохраняются в историю и не передаются LLM. Unicode-эмодзи в тексте сохраняются как обычный текст/одобрение, но критичные действия подтверждаются только inline-кнопками: даже `👍` через reply на карточку не заменяет кнопку.
- Онбординг принимает имя, название города / IANA-зону текстом и выбор кнопками; геолокация не требуется и не обрабатывается.
- На границе БД/API неизвестное значение статуса / enum-подобного поля не обрушает обработку остальных записей и не заменяется разрешающим значением. Неизвестный статус пользователя не допускает LLM; `unsupported_state` отображается понятным ресурсным шаблоном. Исходное неизвестное значение сохраняется, неожиданные ошибки не скрываются.
- Последние не более 19 предыдущих сообщений плюс текущий запрос; саммари добавляется отдельным блоком. Историческое окно начинается с сообщения пользователя, поэтому обычно содержит до 18 предыдущих сообщений, составляющих полные обмены. Через 4 часа бездействия начинается новая сессия без автоматического наследования саммари. Саммари закрытой сессии хранится 30 дней от `closed_at`, затем очищается; сырые сообщения — 30 дней от их создания.

| Бюджет | Предел |
|---|---|
| Весь вход, включая системный промпт, схемы инструментов, историю и результаты | 16 000 токенов |
| Вывод одного обращения | 2 000 токенов |
| Саммари внутри входного контекста | 1 000 токенов |
| Обращения к OpenRouter на входящее сообщение, включая технические повторы | 3 |
| Раунды инструментов | 2 |
| Вызовы инструментов суммарно на сообщение | 6 |
| Общий срок обработки сообщения в `MessageHandler`, включая проверку доступа и работу с сессией | 90 секунд |

Эффективный вход ограничивается также заданным окном модели за вычетом резерва вывода. `ContextBudget` оценивает вход по байтам UTF-8 с запасом на протокол; это консервативная оценка без токенизатора конкретной модели, поэтому доступный объём текста может оказаться меньше предела в токенах. Перед каждым основным обращением, включая обращение после результата инструмента, код при необходимости сокращает старую историю. Системный промпт, текущий запрос вместе с контекстом reply и пары вызовов инструментов с результатами сохраняются. `THESEUS_LLM_CONTEXT_TOKENS` задаёт размер окна; нужно выбрать значение, подходящее всем моделям fallback.

Запросы для саммари и ответа о себе получают актуальные имя, род, локальное время и зону профиля. На саммари приходится отдельное обращение с ограничением вывода 1000 токенов; оно входит в общий бюджет трёх обращений. При сетевом сбое или ошибке генерации саммари основной диалог может продолжиться в оставшемся бюджете. Ошибка записи usage не подавляется: дальнейшие действия не исполняются без учёта расхода.

Бюджеты проверяет код, а не промпт. Повтор одного инструмента с теми же аргументами останавливает цикл; технический повтор операции использует прежний ключ идемпотентности и не считается новым намерением. Исчерпание бюджета даёт ресурсный ответ без утверждения о выполненных действиях. Код причины остановки записывается в лог без текста сообщения пользователя. Если исход изменения неизвестен, восстановление сверяет результат операции по прежнему ключу без нового цикла LLM.

## Ресурсы

| Путь | Назначение |
|---|---|
| `src/main/resources/persona/` | персона Сири и карточка фактов — см. `docs/persona.md` |
| `src/main/resources/prompts/rules.md` | блок «правила» системного промпта: поведение секретаря (черновик) |
| `src/main/resources/prompts/context.md` | шаблон блока «контекст» (подстановки `{name}`, `{gender}`, `{now_local}`, `{weekday}`, `{timezone}`) |
| `src/main/resources/prompts/summary.md` и `persona-answer.md` | инструкции сжатия истории и ответа о себе |
| `src/main/resources/llm/assistant_reply.schema.json` | локальный инструмент диалога: только `topic` из закрытого enum, без дополнительных полей |
| `src/main/resources/llm/resolve_reference.schema.json` | локальный инструмент разрешения номера последнего списка |
| `src/main/resources/onboarding/cities.properties` | соответствия названий городов часовым поясам для онбординга |
| `src/main/resources/texts/agent.properties` | тексты ответов в голосе Сири |

Все промпты — на русском, хранятся в ресурсах, не в коде.

## Данные

Схема `agent` содержит `outgoing_operations`, `incoming_events`, `onboarding_state`, `erased_journal`, `pending_actions`, `dialog_sessions`, `dialog_messages` и `reminder_message_links`; агент подключается отдельной ролью и применяет свои миграции Flyway. `pending_actions` индексирует карточки, а их содержимое хранится зашифрованным в `outgoing_operations`. Тексты истории и саммари шифруются тем же ключом и хранятся отдельно; подробности и сроки — `docs/database.md`. В схему `core` agent не ходит: только MCP и REST.

## Взаимодействие с core

- Инструменты для модели — MCP, `docs/api/mcp.md`; системные вызовы — REST, `docs/api/rest.md`.
- Для изменяющих REST-запросов агент до вызова сохраняет UUID, маршрут, зашифрованное тело и связь с событием, затем передаёт UUID в `Idempotency-Key`. Повтор и восстановление используют ту же запись; модель ключом не управляет. `invite_code` хранится только в зашифрованном содержимом журнала.
- Для изменяющего MCP-вызова `McpOperations` сохраняет UUID, имя инструмента и зашифрованные аргументы до запроса core; повтор и восстановление используют ту же запись и ключ. Журнал хранит карточки подтверждений как `CONFIRM` и сами вызовы как `MCP`.
- `ReminderActions` перехватывает удаление, создание поверх дубля и изменение расписания с исключениями или невыполненными дочерними переносами. Карточка показывает цель и последствия, хранит снимок и выдаёт inline-кнопки. Действие исполняется после нажатия владельца; модель не передаёт `force` или метаданные подтверждения.
- Карточка дубля показывает до двух похожих напоминаний; предлагаемый вариант выводится отдельно, если его отображение отличается от показанных кандидатов. Кнопки называют действие. Расписание с единичным интервалом отображается без «интервал 1», больший интервал — словами. Карточка изменения расписания с последствиями показывает новый час, переданный в `when.time`. Удаление всех текущих напоминаний подтверждается одной карточкой с количеством; снимок набора проверяет core.
- Явную группу модель выбирает по смыслу и передаёт одним `delete_reminder` с `scope=selected` и `reminder_ids`. Agent получает предварительный полный снимок core и показывает одну карточку со всеми фактически удаляемыми напоминаниями и переносами. Кнопка запускает одну операцию с отдельным сохранённым UUID; снимок повторно проверяет core. Если любой результат текущего хода усечён, agent блокирует предпросмотр группы и предлагает показать полный список и указать номера нужных пунктов; явные ID можно передать в новом ходе. Несколько отдельных вызовов изменения существующих целей в одном ответе модели по-прежнему блокируются до исполнения; если есть кандидаты поиска, показываются до пяти с ID.
- Карточка действует 1 час, фиксирует цель и конкретное срабатывание. UUID будущего MCP-вызова назначается при создании карточки и хранится в `pending_actions` и зашифрованном содержимом. Агент передаёт отпечаток и время создания в `_meta["theseus/confirmation"]`; core атомарно проверяет актуальность вместе с изменением. При потере ответа повтор использует тот же UUID; относительное время создания поверх дубля фиксируется до карточки. Отмена после начатого исполнения сначала выясняет его исход.
- Кнопки snooze в уведомлениях обрабатываются системным REST с журналом и прежним ключом повтора. При reply на уведомление агент запрашивает связь Telegram message ID с доставкой в core и добавляет результат в контекст модели.
- После успешной отправки ответа о созданной, изменённой, отложенной, приостановленной или возобновлённой цели `ReminderReplyLinks` может сохранить связь Telegram message ID с единственным подтверждённым напоминанием из MCP-журнала. Для `rem:yes` используется подтверждённое исполнение карточки. Текст ответа не парсится; неоднозначные, незавершённые и ошибочные исходы и карточки с кнопками не связываются. При reply агент сначала ищет собственную связь по пользователю и message ID, затем — доставку в core через REST. Связь действует 30 дней и переживает закрытие сессии; старые ответы без ранее сохранённого ID автоматически не восстанавливаются.
- Данные цели извлекаются из существующего MCP-журнала; сериализованный формат `BotReply` не расширяется. Это сохраняет возможность читать ранее зашифрованные ответы. Регрессия транспорта использует отправку `TelegramBotRunner` с подменённым Telegram-ботом и проверяет сохранение `message_id`, возвращённого SDK; выбор модели для новой реплики остаётся отдельной проверкой.
- Контекст reply на собственный ответ относится к напоминанию или серии целиком. Промпт предписывает модели при изменении часа серии по умолчанию использовать `scope=series`; reply на уведомление core по-прежнему содержит конкретное срабатывание доставки. При отсутствии связи цель по reply не угадывается кодом.
