# Модуль core

Сервис данных и домена: напоминания, пользователи, доступ, учёт usage, планировщик, уведомления (`Notifier` → Telegram). Наружу — MCP (инструменты для LLM) и internal REST (системные вызовы агента, не-ИИ клиенты). Архитектура — `docs/architecture.md`, решения — `docs/DECISIONS.md` (разделы 2–5, 7).

**Статус:** этап 4 завершён и принят владельцем после ручной проверки `0.4.1` на test-боте. Gradle-модуль `:core`, плагины `theseus.application` + `theseus.serialization`, точка входа `theseus.core.MainKt`. Проверки и их границы — `docs/roadmap.md`.

## Пакеты `theseus.core`

| Пакет | Содержимое |
|---|---|
| `domain` | `reminder` (`Reminder`, `NewReminder`, `When`, `WhenResolver`, расписания и дубли), `user` (`User`, `AdminProfile`, статусы, `Gender`), `DomainException` + `ErrorCode`, `LocalFormats` |
| `application` | `ReminderService`, `DeliveryService`, `UserService`, `AccountsService`, `HardDeleteService`, `Operations`, `ReminderScheduler`; порты репозиториев, `Notifier`, `HealthProbe`; время — инжектируемый `Clock`. `HardDeleteService` создаётся только для test |
| `adapters.db` | Exposed + HikariCP + Flyway: `CoreDatabase`, `ExposedUserRepository`, `ExposedInviteRepository`, `ExposedUsageRepository`, `ExposedReminderRepository`, `DatabaseOperations` |
| `adapters.mcp` | `McpServerFactory`, `ReminderTools`, DTO инструментов |
| `adapters.http` | `HttpModule`: Bearer-авторизация, `/mcp`, `/health`, REST |
| `adapters.monitoring` | снимок состояния планировщика, БД, очереди доставок и ошибок Telegram |
| `adapters.telegram` | `TelegramNotifier` (реализация `Notifier`) |
| `config` | `CoreConfig` из env, валидация при старте; переменные — `docs/operations.md` |
| `texts` | загрузка `texts/core.properties` |

Старт (`Main.kt`): конфиг → миграции Flyway → админ из конфига (`ensureAdmin`) → планировщик → HTTP-сервер (Netty).

## Реализовано

- MCP: девять инструментов для создания, чтения, изменения, удаления, snooze, паузы и возобновления напоминаний. Создание проверяет дубли; критичные изменения требуют подтверждения. Изменяющие инструменты используют общий с REST реестр `operation_results`.
- `find_reminders` ранжирует активные и приостановленные напоминания по текстовому сходству, возвращает до 30 и сообщает `truncated=true`, когда записей больше. Пагинация не реализована.
- `delete_reminder` поддерживает удаление выбранной группы id или всех текущих напоминаний по подтверждённому снимку одной транзакцией. Для выбранной группы core сначала возвращает полный снимок с активными и приостановленными дочерними переносами; снимок и срок подтверждения проверяются повторно перед удалением. Остальные напоминания не затрагиваются. Перенос одного срабатывания принимает исходную дату без часа; смена часа серии сохраняет остальные поля расписания. Неверная дата возвращает `invalid_date`.
- REST: `GET /health`, пользователи, инвайты, usage, отключённые квоты, поиск доставки по Telegram message ID и snooze по кнопке; изменяющие запросы используют реестр `operation_results`.
- Планировщик: тик раз в `THESEUS_SCHEDULER_INTERVAL_SECONDS` (30 с), разовые и повторяющиеся напоминания. Доставка «как минимум один раз»; после простоя разовое досылается с пометкой об опоздании, серия — только последнее пропущенное плановое срабатывание и просроченный snooze. Совпавшие моменты дают одно уведомление; пауза и отзыв доступа не создают досыла.
- Уведомление содержит кнопки snooze. Планировщик резервирует идентификатор доставки до отправки, затем записывает исход и Telegram message ID; отправка по-прежнему как минимум однократная.
- Новый админ создаётся в `ONBOARDING`; существующий профиль сохраняется. Инвайт одноразовый, хранится хэш кода, срок задаёт конфиг. После заполнения имени и таймзоны профиль становится активным. Квоты выключены.
- Время: `WhenResolver` считает момент в таймзоне напоминания, лимит — 5 лет вперёд, точность — минута. `RecurrenceResolver` использует утверждённый `lib-recur`; части суток и пороги дублей задаёт конфиг core.

Планировщик отмечает успешное завершение каждого прохода, включая пустой. Снимок `/tmp/theseus-core.monitor.json` обновляется каждые 30 секунд; количество и время самого старого наступившего активного напоминания вычисляются агрегатно, без текстов и без ограничения размером пакета планировщика. Эксплуатация — [monitoring.md](../monitoring.md).

## Публичные интерфейсы (контракт целиком; реализованное — выше)

| Интерфейс | Назначение | Контракт |
|---|---|---|
| MCP (`POST /mcp`) | 9 инструментов напоминаний для LLM; пользователь — из `_meta`, не из аргументов | `docs/api/mcp.md` |
| Internal REST (`/internal/v1`, `GET /health`) | пользователи, инвайты, usage, квоты, snooze по кнопке, поиск уведомления по reply | `docs/api/rest.md` |

Оба интерфейса — тонкие адаптеры над application-сервисами; аутентификация — сервисный токен.

## Данные

Схема `core`: `users`, `invites`, `reminders`, `reminder_deliveries`, `llm_usage`, `operation_results`, `erased_operations` — `docs/database.md`. Core мигрирует только эту схему. `V1` создаёт пользователей и напоминания; `V2` — инвайты, usage и результаты операций; `V3` — идентификаторы удалённых операций; `V4` расширяет допустимые виды доставки объединённым плановым и отложенным срабатыванием.

## Уведомления

Core отправляет текстовое уведомление с кнопками snooze в Telegram (`Notifier` → `TelegramNotifier`). Системные REST-маршруты кнопок и поиска доставки по reply — `docs/api/rest.md`, раздел «Уведомления».
