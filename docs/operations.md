# Эксплуатация

Решения и причины — `docs/DECISIONS.md`, разделы 12–20. Первичная установка ограниченного обработчика и размещение секретов — [пошаговая инструкция](deploy-setup.md).

Статус: этап 2. Бэкап по расписанию, шифрование и проверка восстановления — этап 7 (впереди); сейчас есть только дамп БД стенда перед каждым деплоем.

**Деплой:** ограниченный обработчик заменяет прямой доступ GitHub Actions к Docker. Код и инструкция устанавливаются администратором на VPS; наличие файлов в репозитории не означает завершённую установку или проверку на сервере. Минимальный мониторинг пока не реализован.

## Стенды и раскладка

- Два стенда на одном VPS: **prod** и **test**. Каждый — свои core и agent, свой Telegram-бот; различаются только конфигом (`<стенд>/stand.env`). Compose-проекты: `theseus-prod`, `theseus-test`.
- **PostgreSQL один** на оба стенда — отдельный проект `theseus-infra`, контейнер `theseus-postgres` (`postgres:17-alpine`), том `theseus-pgdata`. Базы `theseus_prod`, `theseus_test`; роли `theseus_<стенд>_core` и `theseus_<стенд>_agent` с правом `CONNECT` только к своей базе и своими схемами `core` / `agent`. Порт наружу не публикуется.
- Сеть `theseus-db` (создаёт infra) общая для стендов; core подключён к ней и адресуется агентом по имени контейнера `theseus-<стенд>-core:8080`. Внутри стенда — своя сеть `stand`. Агент на этапе 2 к `theseus-db` не подключён.
- Порты core и PostgreSQL наружу не публикуются.
- Тестовый стенд поднимается по требованию и гасится после проверки (память, см. ниже).

Раскладка на VPS. Все показанные файлы и каталоги принадлежат `root`; пользователь `deploy` не может читать секреты или менять конфигурацию:

```text
/usr/local/lib/theseus/
├── deploy_handler.py          # привилегированный обработчик
├── ssh-entry                  # фиксированный вход Deploy
└── ssh-authorize-entry        # фиксированный вход Authorize
/opt/theseus/
├── config.json                # репозиторий, registry и версия конфигурации
├── authorization.json         # числовые ID репозитория и владельца
├── github.env                 # GITHUB_TOKEN для проверки сборки и main
├── docker/config.json         # авторизация чтения приватных образов GHCR
├── docker-compose.yml         # устанавливает администратор
├── infra/
│   ├── docker-compose.yml
│   ├── initdb/10-theseus.sh
│   └── infra.env              # секреты PostgreSQL
├── releases/<стенд>/<sha>.json # разрешённые релизы
├── prod/                      # аналогично test/
│   ├── stand.env              # конфигурация и секреты стенда
│   ├── image.env              # ссылки core/agent по digest
│   ├── image.env.prev         # предыдущая попытка, не обязательно healthy
│   └── state.json             # status, release, at последней операции
└── backups/<стенд>/           # дампы перед деплоем
```

`deploy` не входит в `sudo`/`docker`. Узкое правило `sudoers` разрешает только обработчик с фиксированным аргументом стенда. Для Authorize и Deploy используются отдельные ключи prod и test; привязка ключа к стенду задана в root-owned `authorized_keys` вне домашнего каталога `deploy`.

## GitHub

Обновлённый обработчик и SSH-вход Authorize установлены на VPS 2026-11-10; владелец сообщил о настройке Environments. Владелец сообщил об успешном продвижении кандидата через test в prod и получении напоминаний; итоговый prod `state.json` и runtime image IDs независимо не сверялись. Исторические проверки прежнего Deploy от 2026-11-07 описаны в [инструкции](deploy-setup.md).

Владелец вручную запускает **Build release** из workflow на `main`, указав `ref=main` или проверенный SHA. Сборка публикует образы и артефакт `release-candidate` с `release.json`; сам кандидат не разрешает деплой. Workflow ограничены исходным репозиторием `1Avalanche/theseus`, ручным запуском из `main`, совпадением числового ID инициатора с ID владельца и `triggering_actor` с именем владельца. При переносе репозитория или смене имени необходимо обновить привязки workflow и серверную конфигурацию.

Затем владелец запускает **Authorize release**, передав числовой `build_run_id` и `stand`. Preview без SSH-секретов показывает данные релиза, ID артефакта и SHA-256 ZIP до approval Environment. После approval отдельный ключ вызывает authorizer для фиксированного стенда. Сервер повторно проверяет успешный ручной запуск `release.yml` на `main`, ID репозитория и владельца, обоих авторов запуска, принадлежность артефакта сборке, digest скачанного ZIP и схему `release.json`. При переходе на ссылку скачивания токен не передаётся. Для prod дополнительно проверяется принадлежность коммита текущей `main`; существующую запись SHA с другими digest заменить нельзя. Проверка и запись выполняются под общей блокировкой, контейнеры не запускаются.

**Deploy** запускается отдельно с `stand`, `action` (`deploy` или `stop` только для test) и полным SHA для `deploy`. После проверки test остановить и продвинуть те же образы в prod. Ошибка GitHub или проверки блокирует разрешение и проверку prod.

Environments `test` и `prod` должны разрешать только `main`, иметь единственного reviewer — владельца, `Prevent self-review` выключен, административный обход выключен. SSH-секреты хранятся только в Environment: `VPS_HOST`, `VPS_USER=deploy`, `VPS_SSH_KEY`, `VPS_AUTHORIZE_SSH_KEY`, `VPS_KNOWN_HOSTS`; ключи различаются по операции и стенду. Доступность required reviewers для приватных репозиториев зависит от тарифа, для публичных поддерживается актуальными планами; проверить [условия GitHub](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments). Workflow не выполняют release, authorize и deploy при запуске другим аккаунтом, включая write collaborator; approval — отдельный барьер. Администратор репозитория или VPS может изменить политику.

## Ограниченный обработчик деплоя

Привилегированная часть: `/usr/bin/python3 -I /usr/local/lib/theseus/deploy_handler.py test` либо `prod`; authorizer вызывается с аргументами `authorize test` либо `authorize prod`. Аргумент выбирает фиксированная команда SSH-ключа, не содержимое запроса. Ключ не предоставляет оболочку, PTY, forwarding или доступ к Docker socket.

Запрос — одна строка JSON размером не более 1024 байт:

```json
{"action":"deploy","release":"0123456789abcdef0123456789abcdef01234567"}
```

`release` — полный SHA коммита, 40 строчных hex-символов. Произвольные поля, пути, ссылки на образы и shell-команды не принимаются. Для test также разрешён запрос `{"action":"stop"}`. Prod-ключ не выключает prod этим способом; test-ключ не управляет prod.

Authorizer принимает через stdin JSON до 1024 байт с ровно пятью полями: `action=authorize`, числовые `build_run_id` и `artifact_id`, `artifact_digest` в формате `sha256:…`, `release` с полным SHA. Стенд закреплён за ключом; произвольные поля и команды запрещены. Сервер скачивает зафиксированный артефакт повторно после approval. Подробности API — [GitHub Actions artifacts](https://docs.github.com/en/rest/actions/artifacts).

Релиз разрешён при наличии root-owned `releases/<стенд>/<sha>.json` с SHA коммита, digest core и agent и совместимой версией конфигурации. Registry и имена репозиториев фиксированы сервером. Образы запускаются по digest. Для prod сервер проверяет, что утверждённый коммит входит в текущую `main`; флага клиента недостаточно.

Порядок деплоя:

1. Проверить запрос и защищённые пути, получить общую блокировку операций test/prod и изменения конфигурации.
2. Проверить разрешённый релиз, а для prod — принадлежность коммита `main` через GitHub API.
3. Убедиться, что общий PostgreSQL здоров; сохранить дамп БД выбранного стенда до миграций.
4. Загрузить разрешённые образы и обновить только Compose-проект выбранного стенда. Миграции Flyway выполняет core при старте.
5. Дождаться `healthy` у core и agent в течение 240 секунд. Неуспех завершает запрос ошибкой; дамп автоматически не восстанавливается.

Обработчик сохраняет последние 10 преддеплойных дампов каждого стенда. Он не удаляет общие Docker-образы через `prune`. `state.json` отражает последнюю попытку (`deploying`, `failed`, `healthy`) либо остановку test (`stopped`); файл не является полным аудит-журналом. `image.env.prev` содержит предыдущую попытку запуска, а не гарантированно последний здоровый релиз. Для отката выбирать известный проверенный релиз из разрешённого реестра.

Изменение обработчика, Compose и env — административная операция под общей блокировкой; authorizer записывает проверенные разрешения под той же блокировкой. Обычный деплой не заменяет эти файлы. Диагностика содержит идентификаторы и результат; значения секретов и полные логи контейнеров в ответ SSH не выводятся.

Ограничение: приложение получает секреты своего стенда. Вредоносный разрешённый образ может их прочитать, поэтому проверка сборки владельцем остаётся обязательной.

## Healthcheck'и

- **core:** `curl -fsS http://localhost:8080/health` каждые 15 с. `200 {"status":"ok"}` — БД доступна, иначе `503`. Эндпоинт без авторизации.
- **agent:** HTTP-сервера нет. Раз в 30 с агент вызывает Telegram `getMe` и при успехе обновляет файл `THESEUS_HEALTH_FILE`; контейнер нездоров, если файл старше 120 с. Так проверяются и процесс, и связь с Telegram, и валидность токена.
- agent стартует после того, как core стал `healthy`.

Эти проверки не подтверждают работу планировщика или задачи long polling. `restart: unless-stopped` перезапускает завершившийся контейнер, но сам по себе не перезапускает работающий контейнер со статусом `unhealthy`.

## Минимальный мониторинг — целевой контракт

**Утверждено, не реализовано.** Для v1 — таймер на VPS раз в минуту и независимый внешний heartbeat; отдельный расширенный стек метрик не требуется.

| Сигнал | Начальный порог оповещения |
|---|---|
| Последний успешный тик планировщика | старше 2 минут |
| Количество и возраст просроченных доставок | самая старая просрочена больше чем на 5 минут |
| Последний успешный ночной бэкап | старше 26 часов; проверка включается после запуска расписания бэкапов |
| Заполнение диска | 80 % |

- Отдельно проверяется живость задачи long polling, а не время последнего пользовательского сообщения: отсутствие входящих сообщений нормально. Регистрируются ошибки Telegram/OpenRouter без текстов пользователей и секретов.
- Независимый внешний heartbeat обнаруживает отключение всего VPS; локальная проверка не может надёжно сообщить о потере самого сервера. Канал оповещений и получатель задаются при внедрении.
- Зависшую внутреннюю задачу восстанавливают ограниченным числом перезапусков с оповещением. Недоступность внешнего Telegram/OpenRouter вызывает ожидание с увеличением интервала, а не непрерывные рестарты процессов.
- Telegram 429 обрабатывается с учётом `retry_after`; 401 вызывает оповещение о проблеме токена, 403 — фиксацию недоступности получателя. Одинаковые повторяющиеся оповещения подавляются; изменение состояния и восстановление видны отдельно.
- Пороги, период таймера, восстановление внутренних задач и отсутствие шквала оповещений проверяются на тестовом стенде до пилота. Это дополнение к healthcheck, а не утверждение готовности текущего `getMe`-пульса.

## Память

Бюджет 2 ГБ RAM: ОС + Docker ~300 МБ, PostgreSQL ~280, prod (core + agent, heap 256m) ~800, test (heap 128m) ~550. Prod и test вместе — ~1,9 ГБ без запаса, поэтому тест гасится после проверки. Проверка фактического потребления:

```
docker stats --no-stream
free -m
```

Нужен постоянный тест — VPS на 4 ГБ, а не урезание heap.

Снимок VPS после успешного реального сценария test на релизе `04b995c` (2026-11-07):

| Контейнер | `docker stats`: использование / лимит |
|---|---|
| PostgreSQL | 50,68 МиБ / 320 МиБ |
| test core | 166,3 МиБ / 300 МиБ |
| test agent | 133 МиБ / 300 МиБ |

На хосте: RAM 1,9 ГиБ, занято 867 МиБ, доступно 1,0 ГиБ; swap 2,0 ГиБ, использовано 0. Диск: всего 30 ГБ, занято 17 ГБ, доступно 14 ГБ, заполнение 55 %. Это снимок после одного сценария, не нагрузочный тест и не пиковый RSS. Prod в этот момент ещё не был развёрнут. После проверки test остановлен с сохранением БД перед продвижением того же релиза в prod.

| prod core | 154,2 МиБ / 400 МиБ | 3,33 % |
| prod agent | 125,8 МиБ / 400 МиБ | 0,11 % |

Сумма памяти трёх контейнеров — около 338 МиБ. На хосте: RAM 1,9 ГиБ, занято 864 МиБ, доступно 1,0 ГиБ; swap 2,0 ГиБ, использовано 0. Это также снимок после сценария, не пиковый RSS и не нагрузочный тест. Измерения test и prod выполнены по отдельности; работа обоих стендов одновременно под нагрузкой не проверена. После перезагрузки подтверждён автозапуск Docker: через 45 секунд PostgreSQL и оба prod-контейнера healthy; test не запущен. Swap 2,0 ГиБ активен и не используется. Сквозной пользовательский запрос после перезагрузки ещё не повторён; отдельные проверки планировщика и long polling после загрузки не заявляются.

## Тестовый стенд: выключение

С test-ключом отправить обработчику `{"action":"stop"}`. Обработчик останавливает только сервисы тестового стенда. PostgreSQL, prod и данные БД сохраняются. Следующий разрешённый деплой test поднимет его снова. Вызов SSH — в [инструкции](deploy-setup.md).

## Откат

Для домашнего v1 выбран простой штатный откат: предыдущие образы core и agent запускаются с текущей БД. Восстановление дампа — отдельная аварийная процедура, не обязательная часть отката приложения; автоматически при неудачном healthcheck не выполняется. Это целевая политика, мягкое чтение новых значений ещё предстоит реализовать.

### Откат образов с сохранением текущей БД

Для отката отправить Deploy workflow идентификатор предыдущего разрешённого релиза. Его запись должна оставаться в `releases/<стенд>/`, а версия установленной конфигурации должна совпадать. Для prod повторяется серверная проверка принадлежности коммита `main`. Меняются образы; БД остаётся текущей. Удалённые из GHCR образы и несовместимая конфигурация могут сделать старый релиз недоступным.

Миграции остаются только вперёд и аддитивными, перед деплоем снимается дамп. Новые значения статусов и других enum-подобных полей читаются мягко на границе БД/API: неизвестная запись не обрушает процесс, весь список или тик планировщика, не получает действующий статус по умолчанию и не перезаписывается. Для неизвестного статуса пользователя доступ и LLM запрещены; неизвестное состояние напоминания не допускает отправку или изменение. Операция с такой записью возвращает `unsupported_state`, остальные записи продолжают обрабатываться. В логах — идентификатор и код ошибки, без текста пользователя и секретов.

Достаточна целевая регрессионная проверка: неизвестное значение безопасно пропускается, процесс продолжает работать, исходная запись не изменяется. Матрица многоверсионных прогонов и отдельный сложный механизм отката для v1 не вводятся. Такая обработка не исправляет уже выпущенные старые образы без неё и не гарантирует совместимость произвольных изменений схемы; неожиданные ошибки и повреждение данных нельзя скрывать как неизвестный статус.

### Аварийное восстановление БД и соответствующих образов

Восстановление дампа возвращает весь стенд к снимку: записи и изменения после снятия дампа теряются. Отправленные в Telegram сообщения не отменяются; после восстановления старого журнала доставок возможна повторная отправка. Нужны явное решение владельца и согласованный момент восстановления.

Целевая процедура, которую ещё предстоит отработать на этапе 7:

1. Остановить обработку входящих событий, планировщик и все записи обоих сервисов выбранного стенда; соседний стенд не затрагивать.
2. Сохранить отдельный дамп текущего аварийного состояния и идентичность образов/конфигурации для разбора и возможного возврата.
3. Выбрать согласованный дамп, содержащий схемы `core` и `agent` одного стенда из одного согласованного снимка. Отдельные несогласованные снимки схем не использовать.
4. Восстановить в изолированную чистую БД, проверить роли, владельцев, права, миграционные истории и целостность данных. `pg_restore --clean` поверх существующей БД не считать универсальной очисткой: объекты, отсутствующие в старом дампе, могут остаться.
5. Проверить совместимые образы и конфигурацию на восстановленной БД, затем выполнить контролируемое переключение и проверку основных сценариев. Сопоставить внешние Telegram-доставки с восстановленным журналом до возобновления отправок.

Исполняемый runbook, допустимая потеря данных и время восстановления должны быть определены и проверены до использования процедуры с реальными данными. Обратные миграции Flyway этим не вводятся.

## Обновление без потери данных

Данные живут в томе `theseus-pgdata`, который не затрагивается деплоем (`up -d` пересоздаёт только контейнеры core и agent). Схема меняется только новыми миграциями Flyway при старте core, перед каждым деплоем снимается дамп. Проект `theseus-infra` деплоем не перезапускается; обновление версии PostgreSQL — отдельная ручная процедура.

## Что нужно от владельца

Чек-лист того, что должен предоставить владелец, чтобы стенды заработали:

- [ ] **Telegram-боты:** два бота у BotFather — для prod и для test; токены в `stand.env` соответствующих стендов.
- [ ] **OpenRouter:** один ключ на оба стенда; в настройках аккаунта запрещён сбор данных провайдерами (data collection), задан лимит расходов; ключ — в `THESEUS_OPENROUTER_API_KEY`.
- [ ] **GitHub:** Environments `test` и `prod` с защитой и секретами `VPS_HOST`, `VPS_USER`, `VPS_SSH_KEY`, `VPS_AUTHORIZE_SSH_KEY`, `VPS_KNOWN_HOSTS`; разрешены GitHub Actions и запись в ghcr.io (пакеты).
- [ ] **VPS:** пользователь `deploy` без группы `docker` и Docker socket; отдельные ограниченные SSH-ключи Deploy и Authorize для каждого стенда, swap 1–2 ГБ, защищённый каталог конфигурации. Обновлённый обработчик и ключи установлены; проверка релиза и её границы описаны в `deploy-setup.md`.
- [ ] **Секреты на VPS:** `infra/infra.env`, `prod/stand.env`, `test/stand.env` (права 600); пароли и сервисные токены генерируются `openssl rand -hex 32` (сервисный токен) и `openssl rand -hex 24` (пароли).
- [ ] **Данные админа:** chatId владельца в Telegram (число), имя, обращение (`male` / `female` / `unspecified`), таймзона IANA.
- [ ] **Реестр образов:** фиксированный registry `ghcr.io/<владелец строчными>` в `config.json`; серверная авторизация только на чтение пакетов.
- [ ] **Проверка main:** отдельный серверный fine-grained GitHub token с правами Contents read и Actions read нужного репозитория, в `github.env`.
- [ ] **Релизы:** проверка доверенной сборки и digest обоих образов, разрешение отдельно для test и prod.
