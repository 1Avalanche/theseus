# Эксплуатация

Решения и причины — `docs/DECISIONS.md`, разделы 12 (стенды, CI, деплой), 13 (этап 2) и 15 (уточнения после ревью). Здесь — фактическая эксплуатация этапа 2 и отдельно утверждённые требования к следующей реализации.

Статус: этап 2. Бэкап по расписанию, шифрование и проверка восстановления — этап 7 (впереди); сейчас есть только дамп БД стенда перед каждым деплоем.

**Переход после ревью:** ограниченный обработчик деплоя и минимальный мониторинг утверждены, но ещё не реализованы. Описанный ниже `deploy.sh` и копирование файлов через workflow относятся к прежней реализации этапа 2. Пользователь из группы `docker` не ограничен каталогом проекта; эту настройку нельзя считать безопасной целевой моделью. Новые инструкции настройки и workflow должны быть подготовлены вместе с обработчиком, до его использования.

## Стенды и раскладка

- Два стенда на одном VPS: **prod** и **test**. Каждый — свои core и agent, свой Telegram-бот; различаются только конфигом (`<стенд>/stand.env`). Compose-проекты: `theseus-prod`, `theseus-test`.
- **PostgreSQL один** на оба стенда — отдельный проект `theseus-infra`, контейнер `theseus-postgres` (`postgres:17-alpine`), том `theseus-pgdata`. Базы `theseus_prod`, `theseus_test`; роли `theseus_<стенд>_core` и `theseus_<стенд>_agent` с правом `CONNECT` только к своей базе и своими схемами `core` / `agent`. Порт наружу не публикуется.
- Сеть `theseus-db` (создаёт infra) общая для стендов; core подключён к ней и адресуется агентом по имени контейнера `theseus-<стенд>-core:8080`. Внутри стенда — своя сеть `stand`. Агент на этапе 2 к `theseus-db` не подключён.
- Порты core и PostgreSQL наружу не публикуются.
- Тестовый стенд поднимается по требованию и гасится после проверки (память, см. ниже).

Прежняя раскладка этапа 2 в `/opt/theseus` (файлы из `deploy/vps/` копирует workflow при каждом деплое, секреты кладёт владелец; целевая схема ниже заменяет прямую перезапись привилегированных файлов):

```
/opt/theseus/
├── deploy.sh                  # из репозитория
├── docker-compose.yml         # стенд (из репозитория)
├── infra/
│   ├── docker-compose.yml     # общий PostgreSQL (из репозитория)
│   ├── initdb/10-theseus.sh   # базы и роли (из репозитория)
│   └── infra.env              # секреты, права 600 (владелец)
├── prod/                      # и аналогично test/
│   ├── stand.env              # секреты и конфиг стенда, права 600 (владелец)
│   ├── image.env              # THESEUS_IMAGE_TAG=<sha> (пишет deploy.sh)
│   └── image.env.prev         # предыдущий тег (для отката)
└── backups/<стенд>/pre-deploy-<UTC-время>-<sha12>.dump
```

## Переменные окружения

Все секреты — только в env-файлах на VPS (права 600), в git лежат шаблоны `deploy/env/stand.env.example`, `deploy/env/infra.env.example` со значениями `TODO`. Некорректный конфиг — core и agent падают при старте и перечисляют все ошибки разом (значения секретов в сообщения не попадают).

Compose стенда передаёт core только `THESEUS_HTTP_PORT`, `THESEUS_DB_*` (кроме пула), токены, данные админа и `THESEUS_DEFAULT_TIME`. `THESEUS_DB_POOL_SIZE`, `THESEUS_SCHEDULER_INTERVAL_SECONDS`, `THESEUS_LATE_THRESHOLD_MINUTES` работают на значениях по умолчанию; чтобы их менять, добавь строки в `environment` core в `deploy/vps/docker-compose.yml`.

## Прежняя первичная настройка VPS (этап 2)

Историческое описание действующего механизма, **не инструкция настройки утверждённого ограниченного деплоя**. Шаги с группой `docker`, владельцем `deploy` у привилегированных файлов и произвольным копированием скриптов должны быть заменены при реализации обработчика.

1. Пользователь `deploy` в группе `docker`, без sudo. Для него — SSH-ключ (публичная часть в `~/.ssh/authorized_keys`).
2. Swap 1–2 ГБ — обязательно (на 2 ГБ RAM нет запаса на дамп и пики).
3. Каталог `/opt/theseus`, владелец `deploy`.
4. Положить файлы деплоя вручную: `scp -r deploy/vps/. deploy@<VPS>:/opt/theseus/`, затем `chmod +x deploy.sh infra/initdb/*.sh`. (Deploy workflow копирует их сам, но `deploy.sh` без поднятого PostgreSQL завершится ошибкой, а `infra.env` нужен до первого запуска.)
5. Создать `/opt/theseus/infra/infra.env` по `deploy/env/infra.env.example`, `chmod 600`.
6. Поднять PostgreSQL (сеть `theseus-db` создаётся этим же проектом):
   ```
   cd /opt/theseus
   docker compose -p theseus-infra -f infra/docker-compose.yml --env-file infra/infra.env up -d
   ```
   При первой инициализации тома `initdb/10-theseus.sh` создаёт базы и роли обоих стендов. Скрипт идемпотентен; повторно (например, после смены паролей в `infra.env` — пароли ролей обновляются):
   `docker exec theseus-postgres bash /docker-entrypoint-initdb.d/10-theseus.sh`
7. Проверить роли и базы:
   ```
   docker exec theseus-postgres psql -U postgres -c '\du'
   docker exec theseus-postgres psql -U postgres -c '\l'
   ```
   Ожидается: роли `theseus_{prod,test}_{core,agent}`, базы `theseus_prod`, `theseus_test`.
8. Создать `/opt/theseus/<стенд>/stand.env` по `deploy/env/stand.env.example` (`chmod 600`): `THESEUS_STAND`, реестр, токены, данные админа, модели. Каталог `<стенд>/` — создать.
9. Первый деплой — через GitHub Actions (ниже).

## GitHub

- Репозиторий приватный; основная ветка `main`, работа в `develop`.
- **Environments** `test` и `prod`. Секреты в каждом: `VPS_HOST`, `VPS_USER` (`deploy`), `VPS_SSH_KEY` (приватный ключ), `VPS_KNOWN_HOSTS` (результат `ssh-keyscan <host>`). Секреты приложения (токены ботов, OpenRouter, сервисный токен) в GitHub **не хранятся**.
- **CI** (`.github/workflows/ci.yml`) — на каждый push и PR: `./gradlew build` (юнит- и интеграционные тесты, ktlint, detekt). Только проверка, не деплой.
- **Deploy** (`.github/workflows/deploy.yml`) — только вручную: Actions → Deploy → Run workflow; параметры `stand` (`test` / `prod`) и `ref` (ветка, тег или SHA, по умолчанию `main`). Не больше одного деплоя на стенд одновременно.
  1. `ref` → SHA. Для `prod` коммит должен входить в `main`, иначе workflow падает.
  2. Если образов `ghcr.io/<владелец>/theseus-{core,agent}:<sha>` нет — сборка, тесты, `docker build`, push. Есть — образ продвигается без пересборки.
  3. На VPS копируются файлы `deploy/vps/`, затем по SSH выполняется `deploy.sh <стенд> <sha>` (логин в ghcr.io — токеном job'а, только на время деплоя).

## Ограниченный обработчик деплоя — целевой контракт

**Утверждено, не реализовано; заменяет прежнюю модель доступа из §12–13 `DECISIONS.md`.**

- Пользователь `deploy` не входит в группу `docker`, не имеет доступа к Docker socket и общего права `sudo`.
- SSH-ключ привязан к фиксированному обработчику (`ForceCommand` либо ограничение ключа): без интерактивной оболочки, PTY, туннелей и перенаправления SSH-агента. Переданные клиентом строки не исполняются как команды оболочки.
- Обработчик принимает только стенд и идентификатор разрешённого образа из фиксированного реестра и набора репозиториев. Проверки выполняются на сервере. Для prod сервер должен проверять разрешённое происхождение релиза из `main`; утверждение клиента «это main» и одна проверка формата SHA недостаточны. Механизм доказательства происхождения нужно выбрать до реализации.
- Привилегированная часть — фиксированный серверный сервис либо единственный строго ограниченный root-owned helper через `sudo`. Конкретный механизм ещё предстоит выбрать; свободные Docker-команды через `sudo` не разрешаются.
- Обработчик, helper, Compose, env-файлы и содержащие их каталоги защищены от изменения пользователем `deploy`, принадлежат root. Изменяемые рабочие файлы отделены от исполняемой конфигурации. Нельзя подменить обработчик, Compose или env через запись в родительский каталог, симлинк либо дополнительные параметры.
- Разрешённые действия ограничены выбранным стендом: дамп его БД, загрузка заданных образов, запуск его Compose-проекта и проверка здоровья. Доступ к произвольным контейнерам, томам, хостовым путям и Docker API не предоставляется.
- Конфигурация деплоя версионируется с релизом и устанавливается контролируемым административным действием. Обычный деплой приложения не может заменить её произвольными файлами из ветки. Изменения общей конфигурации блокируются на время конкурирующих операций test/prod.
- Test не получает возможность изменять конфигурацию и секреты prod. Каждый образ приложения всё равно получает необходимые ему секреты своего стенда: доверие к происхождению образа остаётся обязательным.
- Точный формат запроса, проверка происхождения образов, установка конфигурации и ограниченный путь выключения тестового стенда должны быть описаны и проверены вместе с новым workflow. Существующие команды `deploy.sh` нельзя объявлять командами нового обработчика.

## Прежний `deploy.sh <prod|test> <sha>` (этап 2)

Проверяет аргументы (тег — SHA коммита, 7–40 hex), наличие `<стенд>/stand.env` и здоровье `theseus-postgres`. Затем:

1. Дамп БД стенда: `pg_dump -Fc theseus_<стенд>` → `backups/<стенд>/pre-deploy-….dump`; хранятся 10 последних (`KEEP_DUMPS`).
2. Новый тег в `<стенд>/image.env`; прежний — в `image.env.prev`.
3. `docker compose pull` и `up -d --remove-orphans`. **Миграции Flyway** выполняет core при старте (`classpath:db/migration/core`, схема `core`).
4. Ожидание `healthy` у core и agent до `HEALTH_TIMEOUT_SECONDS` (240 с). Не поднялись — выход с кодом 1 и хвост логов, workflow падает.
5. Очистка образов старше 7 суток, вывод `docker stats` по контейнерам Theseus.

## Healthcheck'и

- **core:** `curl -fsS http://localhost:8080/health` каждые 15 с. `200 {"status":"ok"}` — БД доступна, иначе `503`. Эндпоинт без авторизации.
- **agent:** HTTP-сервера нет. Раз в 30 с агент вызывает Telegram `getMe` и при успехе обновляет файл `THESEUS_HEALTH_FILE`; контейнер нездоров, если файл старше 120 с. Так проверяются и процесс, и связь с Telegram, и валидность токена.
- agent стартует после того, как core стал `healthy`.

Эти проверки не подтверждают работу планировщика или задачи long polling. `restart: unless-stopped` перезапускает завершившийся контейнер, но сам по себе не перезапускает работающий контейнер со статусом `unhealthy`.

## Минимальный мониторинг — целевой контракт

**Утверждено, не реализовано.** Для v1 — таймер на VPS раз в минуту и независимый внешний heartbeat; отдельный расширенный стек метрик не требуется.

| Сигнал | Начальный порог оповещения |
|---|---|
| Последний успешный тик планировщика | старше 2 минут |
| Количество и возраст просроченных доставок | самая старая просрочена больше чем на 5 минут |
| Последний успешный ночной бэкап | старше 26 часов; проверка включается после запуска расписания бэкапов |
| Заполнение диска | 80 % |

- Отдельно проверяется живость задачи long polling, а не время последнего пользовательского сообщения: отсутствие входящих сообщений нормально. Регистрируются ошибки Telegram/OpenRouter без текстов пользователей и секретов.
- Независимый внешний heartbeat обнаруживает отключение всего VPS; локальная проверка не может надёжно сообщить о потере самого сервера. Канал оповещений и получатель задаются при внедрении.
- Зависшую внутреннюю задачу восстанавливают ограниченным числом перезапусков с оповещением. Недоступность внешнего Telegram/OpenRouter вызывает ожидание с увеличением интервала, а не непрерывные рестарты процессов.
- Telegram 429 обрабатывается с учётом `retry_after`; 401 вызывает оповещение о проблеме токена, 403 — фиксацию недоступности получателя. Одинаковые повторяющиеся оповещения подавляются; изменение состояния и восстановление видны отдельно.
- Пороги, период таймера, восстановление внутренних задач и отсутствие шквала оповещений проверяются на тестовом стенде до пилота. Это дополнение к healthcheck, а не утверждение готовности текущего `getMe`-пульса.

## Память

Бюджет 2 ГБ RAM: ОС + Docker ~300 МБ, PostgreSQL ~280, prod (core + agent, heap 256m) ~800, test (heap 128m) ~550. Prod и test вместе — ~1,9 ГБ без запаса, поэтому тест гасится после проверки. Проверка фактического потребления:

```
docker stats --no-stream
free -m
```

Нужен постоянный тест — VPS на 4 ГБ, а не урезание heap.

## Тестовый стенд: выключение

Ниже — прежняя административная команда этапа 2. В целевой модели пользователь `deploy` не выполняет произвольный `docker compose`; ограниченный путь выключения стенда требуется реализовать отдельно.

```
cd /opt/theseus
docker compose -p theseus-test -f docker-compose.yml \
  --env-file test/stand.env --env-file test/image.env down
```

База `theseus_test` и данные в ней сохраняются; следующий деплой на test поднимет стенд снова.

## Откат

Для домашнего v1 выбран простой штатный откат: предыдущие образы core и agent запускаются с текущей БД. Восстановление дампа — отдельная аварийная процедура, не обязательная часть отката приложения; автоматически при неудачном healthcheck не выполняется. Это целевая политика, мягкое чтение новых значений ещё предстоит реализовать.

### Откат образов с сохранением текущей БД

Прежний тег этапа 2 лежит в `<стенд>/image.env.prev`; действующий механизм позволяет запустить Deploy workflow на предыдущий SHA либо прежний `deploy.sh`. Это меняет образы, но не возвращает БД к прошлому состоянию.

Миграции остаются только вперёд и аддитивными, перед деплоем снимается дамп. Новые значения статусов и других enum-подобных полей читаются мягко на границе БД/API: неизвестная запись не обрушает процесс, весь список или тик планировщика, не получает действующий статус по умолчанию и не перезаписывается. Для неизвестного статуса пользователя доступ и LLM запрещены; неизвестное состояние напоминания не допускает отправку или изменение. Операция с такой записью возвращает `unsupported_state`, остальные записи продолжают обрабатываться. В логах — идентификатор и код ошибки, без текста пользователя и секретов.

Достаточна целевая регрессионная проверка: неизвестное значение безопасно пропускается, процесс продолжает работать, исходная запись не изменяется. Матрица многоверсионных прогонов и отдельный сложный механизм отката для v1 не вводятся. Такая обработка не исправляет уже выпущенные старые образы без неё и не гарантирует совместимость произвольных изменений схемы; неожиданные ошибки и повреждение данных нельзя скрывать как неизвестный статус.

### Аварийное восстановление БД и соответствующих образов

Восстановление дампа возвращает весь стенд к снимку: записи и изменения после снятия дампа теряются. Отправленные в Telegram сообщения не отменяются; после восстановления старого журнала доставок возможна повторная отправка. Нужны явное решение владельца и согласованный момент восстановления.

Целевая процедура, которую ещё предстоит отработать на этапе 7:

1. Остановить обработку входящих событий, планировщик и все записи обоих сервисов выбранного стенда; соседний стенд не затрагивать.
2. Сохранить отдельный дамп текущего аварийного состояния и идентичность образов/конфигурации для разбора и возможного возврата.
3. Выбрать согласованный дамп, содержащий схемы `core` и `agent` одного стенда из одного согласованного снимка. Отдельные несогласованные снимки схем не использовать.
4. Восстановить в изолированную чистую БД, проверить роли, владельцев, права, миграционные истории и целостность данных. `pg_restore --clean` поверх существующей БД не считать универсальной очисткой: объекты, отсутствующие в старом дампе, могут остаться.
5. Проверить совместимые образы и конфигурацию на восстановленной БД, затем выполнить контролируемое переключение и проверку основных сценариев. Сопоставить внешние Telegram-доставки с восстановленным журналом до возобновления отправок.

Исполняемый runbook, допустимая потеря данных и время восстановления должны быть определены и проверены до использования процедуры с реальными данными. Обратные миграции Flyway этим не вводятся.

## Обновление без потери данных

Данные живут в томе `theseus-pgdata`, который не затрагивается деплоем (`up -d` пересоздаёт только контейнеры core и agent). Схема меняется только новыми миграциями Flyway при старте core, перед каждым деплоем снимается дамп. Проект `theseus-infra` деплоем не перезапускается; обновление версии PostgreSQL — отдельная ручная процедура.

## Что нужно от владельца

Чек-лист того, что должен предоставить владелец, чтобы стенды заработали:

- [ ] **Telegram-боты:** два бота у BotFather — для prod и для test; токены в `stand.env` соответствующих стендов.
- [ ] **OpenRouter:** один ключ на оба стенда; в настройках аккаунта запрещён сбор данных провайдерами (data collection), задан лимит расходов; ключ — в `THESEUS_OPENROUTER_API_KEY`.
- [ ] **GitHub:** приватный репозиторий; Environments `test` и `prod` с секретами `VPS_HOST`, `VPS_USER`, `VPS_SSH_KEY`, `VPS_KNOWN_HOSTS`; разрешены GitHub Actions и запись в ghcr.io (пакеты).
- [ ] **VPS:** пользователь `deploy` без группы `docker` и Docker socket; ограниченный SSH-ключ для целевого обработчика, swap 1–2 ГБ, защищённый каталог конфигурации. Сам обработчик, root-owned конфигурацию и новый workflow ещё требуется реализовать; прежняя настройка этапа 2 целевое ограничение не обеспечивает.
- [ ] **Секреты на VPS:** `infra/infra.env`, `prod/stand.env`, `test/stand.env` (права 600); пароли и сервисные токены генерируются `openssl rand -hex 32` (сервисный токен) и `openssl rand -hex 24` (пароли).
- [ ] **Данные админа:** chatId владельца в Telegram (число), имя, обращение (`male` / `female` / `unspecified`), таймзона IANA.
- [ ] **Реестр образов:** значение `THESEUS_IMAGE_REGISTRY` (`ghcr.io/<владелец строчными>`).
