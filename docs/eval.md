# Eval-набор LLM

Статус: исходный набор и формат утверждены владельцем 2026-11-02 (этап 1), после ручной проверки этапа 4 добавлены семь кейсов, после обратной связи этапа 5 — ещё десять. Всего 114 кейсов. Базовый прогон на четырёх моделях завершён и принят владельцем 2026-11-20 с известными ограничениями; расширенный eval отложен. Проверки с фейковой LLM не измеряют качество реальной модели. Решения — `docs/DECISIONS.md`.

Аудит существующих JSONL-кейсов не завершён: требуется отдельно задать и проверить ожидаемый вид ответа в кейсах `no_mutation`, а также сценарии безопасности и отказов. `dup-01` требует отсутствия `force`; `dup-02` проверяет, что текстовое согласие не меняет данные; история `dup-02` и `num-01` задана завершёнными текстовыми сообщениями.

Набор — одновременно спецификация того, что агент должен понимать, и регрессия при смене модели или промпта. Аргументы tool calls сравниваются детерминированно; смысл и стиль свободного ответа персоны требуют отдельной оценки.

## Кейс

```json
{
  "id": "upd-02",
  "category": "update",
  "fixture": "base",
  "note": "время встречи сохраняется",
  "context": {"now_local": "2026-11-02T12:00", "timezone": "Asia/Yekaterinburg"},
  "reply_to": {"reminder_id": 12, "occurrence_local": "2026-11-02T09:00"},
  "history": [{"role": "user", "content": "…"}, {"role": "assistant", "content": "…"}],
  "input": "встречу с Петей перенеси на пятницу",
  "expect": {"calls": [{"tool": "update_reminder", "args": {"reminder_id": 16, "when": {"$resolves_to": "2026-11-06T13:00"}}}]}
}
```

| Поле | |
|---|---|
| `id`, `category` | уникальный id; категория — для отчёта по группам |
| `fixture` | имя фикстуры, по умолчанию `empty` |
| `note` | для людей: что проверяет кейс |
| `context` | переопределение контекста по умолчанию |
| `reply_to` | связь сообщения: для уведомления — `reminder_id` и `occurrence_local`; для ответа агента — `source=agent_reply`, `reminder_id`, `kind`, `timezone` |
| `history` | предыдущие сообщения; текущий раннер переносит только непустое `content`, `user` — как пользовательское сообщение, остальные роли — как ответ агента. `tool_calls` и `tool_call_id` не восстанавливаются |
| `input` | сообщение пользователя |
| `expect` / `expect_any` | ожидание или список допустимых альтернатив |

## Ожидание

- `{"calls": [...]}` — модель должна сделать эти вызовы. По умолчанию по порядку; `"order": "any"` — в любом порядке.
  - Читающие инструменты (`find_reminders`, `get_reminder`, `list_reminders`) могут встречаться дополнительно — модель вправе сначала найти `id`.
  - Лишний изменяющий вызов — провал.
- `{"no_mutation": true}` — инвариант: ни одного изменяющего вызова. Сам по себе не доказывает правильность ответа: пустой ответ или технический сбой также могут не менять данные.
- Для кейсов без изменения требуется отдельная проверка ожидаемого вида ответа: уточнение, объяснение ограничения или ответ не по теме. Раннер проверяет непустоту и отсутствие трёх известных ресурсных ответов об ошибке, бюджете и неподтверждённом исходе; это не обнаруживает все возможные сбои и не проверяет смысл ответа. Вид и семантическое соответствие требуют отдельной оценки.

Раннер использует рабочие `MessageHandler` и `ReminderTools`, доменные функции core для `When`/`Recurrence`, фиктивные диалоги и репозитории core в памяти на MockK. Это позволяет проверить цепочку `find_reminders → update_reminder`, но не проверяет настоящую БД, транспорт или Telegram. Зависимость `:core` подключена только к тестовому classpath; новых внешних зависимостей нет.

## Запуск раннера

Из корня проекта:

```bash
./gradlew :agent:eval --args=validate
./gradlew :agent:eval --args=smoke
./gradlew :agent:eval --args=run
./gradlew :agent:eval --args=report
```

`validate` загружает кейсы и создаёт окружение без сети; он выбран и при запуске без аргументов. `smoke` выполняет подмножество из `agent/eval/config.json`, `run` — весь набор, оба обращаются к OpenRouter и требуют `OPENROUTER_API_KEY`. `report` формирует локальный отчёт по сохранённым результатам. Платные режимы не запускаются автоматически при `build`; сборка компилирует раннер и выполняет тесты с фейками.

Результаты и отчёт сохраняются в `agent/eval/results/stage6`, общий журнал резервов — в `agent/eval/results/budget.json`; файлы содержат тексты кейсов и ответов. Завершённые пары кейс/модель при перезапуске пропускаются. `active.json` блокирует автоматический платный повтор прерванного кейса; отпечаток исходников запрещает продолжение старого прогона после изменений. При продолжении сохранённые тарифы должны совпадать с каталогом, иначе прогон останавливается. Запрос текстовый, без web/audio/image; неизвестные виды тарифа запрещены. Резерв по текущим тарифам учитывает возможную стоимость кеша и reasoning без скидки кеша; при неизвестной стоимости ответа резерв сохраняется. После сетевого сбоя прогон останавливается с сохранённым резервом. Отчёт содержит автоматические результаты, ответы и агрегаты usage, стоимости и задержки по моделям и категориям; ручная оценка остаётся отдельной. Процедура — `.agents/skills/llm-eval/SKILL.md`.

Раннер `0.6.0` реализован; после исправления расчёта тарифов и трёх кейсов `build` прошёл: 311 тестов без ошибок и пропусков, agent — 159 юнит- и 7 интеграционных, core — 116 юнит- и 29 интеграционных. Локальный `validate` прошёл: 114 кейсов, четыре модели. Базовый платный прогон завершён: 456 пар, 352 автоматических прохода, 585 вызовов API, расход $0.243626870. Аудит набора и ручная оценка не завершены; результаты и ограничения — `docs/eval-results-stage6.md`.

В базовом сравнении участвовали четыре модели, включая `openai/gpt-5.4-nano`; исторические результаты сохранены. Владелец выбрал дальнейший приоритет: `anthropic/claude-haiku-5.5` → `qwen/qwen3.8-flash` → `google/gemini-3.1-flash-lite`; GPT исключена из дальнейшего eval и fallback. Новые платные прогоны требуют отдельного согласования. Для них заранее проверять тарифы и доступность и сравнивать модели по отдельности без fallback. Потолок базового прогона составлял $5, не целевую сумму; остаток автоматически не расходуется.

Позже отдельно согласовать расширенный eval: сквозные диалоги с фактическими ответами и состоянием, включая `feedback-06`; проверку полных исходящих запросов, исправление фикстур и матчеров, оценку текста и завершение аудита. Принятие базового прогона не означает исправления `feedback-06` или завершения аудита.

## Сравнение аргументов

- Объекты сравниваются **частично и рекурсивно**: проверяются только указанные поля.
- Списки — без учёта порядка.
- Отсутствующее поле отличается от `null`. Буквальное `null` в ожидании требует наличия поля с явным `null`.
- Частичное сравнение не должно скрывать нежелательный сброс полей в `update_reminder`: кейс явно проверяет `$absent` у полей, которые нельзя менять, и `null` у полей, которые нужно сбросить. При аудите набора такие проверки добавляются отдельно.
- Матчеры:

| Матчер | Значение |
|---|---|
| `{"$contains_any": ["банк"]}` | строка без учёта регистра содержит хотя бы одну подстроку (основы слов — модель формулирует `text` по-своему) |
| `{"$resolves_to": "2026-11-03T15:00"}` или список | `When` после разрешения кодом core в контексте кейса даёт этот локальный момент (или один из). Разные записи одного момента (`date`+`time` или `after`) равноценны |
| `{"$normalizes_to": {…}}` | `Recurrence` после нормализации core частично совпадает с указанным (по умолчанию раскрыты) |
| `{"$one_of": [a, b]}` | одно из значений; `null` означает поле с явным `null`, но не его отсутствие |
| `{"$absent": true}` | поле строго отсутствует; явный `null` не проходит |

## Обязательные сценарии безопасности и отказов

Предстоит добавить и проверять на соответствующем уровне:

- Подмена `user_id` в аргументах модели, обращение к чужим напоминаниям и результатам операций.
- Попытки вызвать удаление или `force=true` в обход подтверждения кодом агента.
- Инструкции злоумышленника в тексте напоминания, истории и результатах инструментов: они не становятся системными правилами и не расширяют права.
- Повторные запросы и callbacks, конкурирующие повторы одного ключа, конфликт ключа с другим запросом.
- Потеря ответа после коммита, таймаут и рестарт агента между запросом и сохранением его исхода: доменное изменение выполняется один раз, относительное время не пересчитывается при повторе.
- `update_reminder`: отдельно неизменённое поле, явный сброс через `null` и недопустимый лишний сброс.
- Подтверждения: срок 1 час (до границы, на границе и после); конкретное срабатывание вместо повторного выбора ближайшего; изменение значимых данных между карточкой и исполнением; атомарная защита от гонки с планировщиком; повтор callback с одним `operation_id`. `force` от модели без кнопки не разрешает создание.
- Изменение расписания серии с исключениями и дочерними переносами: количество последствий в карточке, подтверждение `CONFIRM_SERIES_RESET`, атомарный сброс исключений и отмена невыполненных переносов. Изменение только текста их сохраняет.
- Совпадение обычного и отложенного срабатывания даёт одно уведомление и объединённый вид `SCHEDULED_AND_SNOOZED`; пауза отменяет snooze, возобновление не восстанавливает его; snooze во время паузы запрещён.
- Простой: досыл разового с пометкой опоздания; только последнее пропущенное обычное срабатывание серии; отсутствие досыла за период паузы или отзыва доступа. Просроченный snooze серии отдельно требует решения до добавления однозначного ожидания.
- Смена зоны профиля сохраняет зоны существующих напоминаний и использует новую для новых; отличающаяся зона явно показана в карточке. Интерпретация локальных аргументов изменения в отличающихся зонах требует отдельного уточнения контракта.
- «Утром» — 09:00, «днём» — 14:00, «вечером» — 19:00 по конфигу; «ночью» без часа — уточнение. «До 10-го» — возобновление 10-го; «по 10-е включительно» — 11-го, календарное вычисление кодом.
- Ввод только текстом: Unicode-эмодзи сохраняются; медиа, стикеры, геолокация и подписи к медиа не вызывают LLM и не запускают действие. Telegram-реакции полностью игнорируются, в историю/LLM не попадают. Критичные действия подтверждаются только inline-кнопкой: текстовое согласие и `👍`, включая reply на карточку, не исполняют ожидающее действие.
- Мягкое чтение неизвестных статусов / enum-подобных значений БД/API: процесс, список и тик не падают целиком; неизвестный пользователь не получает доступ/LLM, неизвестное напоминание не отправляется и не меняется, операция даёт `unsupported_state`. Остальные записи продолжают обрабатываться, исходное значение не затирается при записи других полей. Нужна целевая детерминированная регрессионная проверка, а не матрица многоверсионных прогонов; произвольные ошибки и повреждение данных не маскируются под неизвестный статус.
- Бюджеты: 16 000 входных токенов, 2 000 выходных, саммари до 1 000, не более 20 последних сообщений в общем бюджете; не более 3 обращений OpenRouter с повторами, 2 раундов / 6 вызовов инструментов и 90 секунд на сообщение. Повтор инструмента без прогресса останавливается; сокращение контекста сохраняет обязательные правила и целые связки инструментов.
- Новая сессия через 4 часа не наследует саммари; саммари закрытой сессии очищается через 30 дней от закрытия независимо от удаления сырых сообщений.

Поведение модели проверяется LLM-eval; проверки авторизации, подтверждений и транзакционной идемпотентности — детерминированными тестами агента/core. Один прогон модели не доказывает эти гарантии приложения.

После ручной проверки этапа 4 требуется отдельно оценить распознавание невозможной даты, объяснение отсутствия повторов чаще раза в день, перенос одного срабатывания по дате, изменение часа серии, уточнение при нескольких одинаково подходящих целях и выбор `delete_reminder` с `scope=all`. Для неоднозначной цели отсутствие изменений само по себе не доказывает полезного ответа. Наличие этих ожиданий в наборе не означает, что модель уже прошла eval.

Два кейса этапа 5 проверяют один вызов `delete_reminder` с `scope=selected` и точными `reminder_ids`: выбор только напоминаний о воде после списка и выбор обеих явно названных одинаковых серий. `scope=all` и отдельные удаления целей в первом кейсе недопустимы. Карточка и кнопка подтверждения проверяются отдельно детерминированными тестами приложения; сами eval-кейсы не доказывают их работы.

Кейс общего рассказа о Сири ожидает `assistant_reply` с `topic=introduction`; конкретный вопрос о происхождении имени — `topic=about`. Состав ресурсного представления и отсутствие выдуманного происхождения имени оцениваются отдельно от выбора инструмента. Пятый кейс задаёт reply на подтверждённый ответ агента о серии и ожидает изменение часа всей серии (`scope=series`) без повторного вопроса о содержании или нового создания. Эти ожидания — требования к будущему раннеру; тесты с фейковой LLM и инструкции промпта не подтверждают поведение реальной модели.

Остальные пять кейсов этапа 5 проверяют короткое приветствие, выбор ответа о возможностях, вопрос о фамилии с историей, уточнение противоречивого времени в reply и ответ на нераспознанный запрос. Качество свободного ответа и отсутствие технической ошибки оцениваются отдельно от выбора инструмента.
