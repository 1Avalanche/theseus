# Eval-набор LLM

Статус: набор кейсов и формат утверждены владельцем 2026-11-02 (этап 1). Раннер появится на этапе 6 (выбор модели), не входит в `./gradlew build`. Решение — `docs/DECISIONS.md` §9.

Уточнения после ревью (2026-11-05) ниже — требования к будущему раннеру и пополнению набора. Раннер и новые сценарии пока не реализованы; существующие JSONL-кейсы при его создании нужно проверить на соответствие уточнённой семантике.

Набор — одновременно спецификация того, что агент должен понимать, и регрессия при смене модели или промпта. Проверка детерминированная: сравниваются аргументы tool calls, а не текст ответа.

Контекст по умолчанию: сейчас `2026-11-02T10:00` (понедельник), `Europe/Moscow`, пользователь «Аня», род женский. Фикстура `base` — шесть напоминаний (мама по воскресеньям, таблетки ежедневно, интернет 10-го, посылка завтра, спортзал пн/ср/пт, встреча с Петей в четверг); `base_paused` — то же, спортзал на паузе.

## Кейс

```json
{
  "id": "upd-02",
  "category": "update",
  "fixture": "base",
  "note": "время встречи сохраняется",
  "context": {"now_local": "2026-11-02T12:00", "timezone": "Asia/Yekaterinburg"},
  "reply_to": {"reminder_id": 12, "occurrence_local": "2026-11-02T09:00"},
  "history": [{"role": "user", "content": "…"}, {"role": "assistant", "content": "…"}],
  "input": "встречу с Петей перенеси на пятницу",
  "expect": {"calls": [{"tool": "update_reminder", "args": {"reminder_id": 16, "when": {"$resolves_to": "2026-11-06T13:00"}}}]}
}
```

| Поле | |
|---|---|
| `id`, `category` | уникальный id; категория — для отчёта по группам |
| `fixture` | имя фикстуры, по умолчанию `empty` |
| `note` | для людей: что проверяет кейс |
| `context` | переопределение контекста по умолчанию |
| `reply_to` | сообщение — reply на уведомление об этом срабатывании |
| `history` | предыдущие сообщения в формате истории агента (`role`: `user` \| `assistant` \| `tool`, `tool_calls`, `tool_call_id`) |
| `input` | сообщение пользователя |
| `expect` / `expect_any` | ожидание или список допустимых альтернатив |

## Ожидание

- `{"calls": [...]}` — модель должна сделать эти вызовы. По умолчанию по порядку; `"order": "any"` — в любом порядке.
  - Читающие инструменты (`find_reminders`, `get_reminder`, `list_reminders`) могут встречаться дополнительно — модель вправе сначала найти `id`.
  - Лишний изменяющий вызов — провал.
- `{"no_mutation": true}` — инвариант: ни одного изменяющего вызова. Сам по себе не доказывает правильность ответа: пустой ответ или технический сбой также могут не менять данные.
- Для кейсов без изменения требуется отдельная проверка ожидаемого вида ответа: уточнение, объяснение ограничения или ответ не по теме. Ответ должен быть непустым; технический сбой вместо ожидаемого полезного ответа — провал. Формат этой проверки уточняется при создании раннера. Непустота и отсутствие сбоя проверяются кодом; семантическое соответствие требует отдельной оценки и не объявляется полностью детерминированной проверкой качества текста.

Раннер моделирует core: инструменты отвечают по фикстуре, используя настоящие функции core для `When`/`Recurrence`, так что модель может пройти цепочку `find_reminders → update_reminder`.

## Сравнение аргументов

- Объекты сравниваются **частично и рекурсивно**: проверяются только указанные поля.
- Списки — без учёта порядка.
- Отсутствующее поле отличается от `null`. Буквальное `null` в ожидании требует наличия поля с явным `null`.
- Частичное сравнение не должно скрывать нежелательный сброс полей в `update_reminder`: кейс явно проверяет `$absent` у полей, которые нельзя менять, и `null` у полей, которые нужно сбросить. При аудите набора такие проверки добавляются отдельно.
- Матчеры:

| Матчер | Значение |
|---|---|
| `{"$contains_any": ["банк"]}` | строка без учёта регистра содержит хотя бы одну подстроку (основы слов — модель формулирует `text` по-своему) |
| `{"$resolves_to": "2026-11-03T15:00"}` или список | `When` после разрешения кодом core в контексте кейса даёт этот локальный момент (или один из). Разные записи одного момента (`date`+`time` или `after`) равноценны |
| `{"$normalizes_to": {…}}` | `Recurrence` после нормализации core частично совпадает с указанным (по умолчанию раскрыты) |
| `{"$one_of": [a, b]}` | одно из значений; `null` означает поле с явным `null`, но не его отсутствие |
| `{"$absent": true}` | поле строго отсутствует; явный `null` не проходит |

## Обязательные сценарии безопасности и отказов

Предстоит добавить и проверять на соответствующем уровне:

- Подмена `user_id` в аргументах модели, обращение к чужим напоминаниям и результатам операций.
- Попытки вызвать удаление или `force=true` в обход подтверждения кодом агента.
- Инструкции злоумышленника в тексте напоминания, истории и результатах инструментов: они не становятся системными правилами и не расширяют права.
- Повторные запросы и callbacks, конкурирующие повторы одного ключа, конфликт ключа с другим запросом.
- Потеря ответа после коммита, таймаут и рестарт агента между запросом и сохранением его исхода: доменное изменение выполняется один раз, относительное время не пересчитывается при повторе.
- `update_reminder`: отдельно неизменённое поле, явный сброс через `null` и недопустимый лишний сброс.
- Подтверждения: срок 1 час (до границы, на границе и после); конкретное срабатывание вместо повторного выбора ближайшего; изменение значимых данных между карточкой и исполнением; атомарная защита от гонки с планировщиком; повтор callback с одним `operation_id`. `force` от модели без кнопки не разрешает создание.
- Изменение расписания серии с исключениями и дочерними переносами: количество последствий в карточке, подтверждение `CONFIRM_SERIES_RESET`, атомарный сброс исключений и отмена невыполненных переносов. Изменение только текста их сохраняет.
- Совпадение обычного и отложенного срабатывания даёт одно уведомление и объединённый вид `SCHEDULED_AND_SNOOZED`; пауза отменяет snooze, возобновление не восстанавливает его; snooze во время паузы запрещён.
- Простой: досыл разового с пометкой опоздания; только последнее пропущенное обычное срабатывание серии; отсутствие досыла за период паузы или отзыва доступа. Просроченный snooze серии отдельно требует решения до добавления однозначного ожидания.
- Смена зоны профиля сохраняет зоны существующих напоминаний и использует новую для новых; отличающаяся зона явно показана в карточке. Интерпретация локальных аргументов изменения в отличающихся зонах требует отдельного уточнения контракта.
- «Утром» — 09:00, «днём» — 14:00, «вечером» — 19:00 по конфигу; «ночью» без часа — уточнение. «До 10-го» — возобновление 10-го; «по 10-е включительно» — 11-го, календарное вычисление кодом.
- Ввод только текстом: Unicode-эмодзи сохраняются; медиа, стикеры, геолокация и подписи к медиа не вызывают LLM и не запускают действие. Telegram-реакции полностью игнорируются, в историю/LLM не попадают. Критичные действия подтверждаются только inline-кнопкой: текстовое согласие и `👍`, включая reply на карточку, не исполняют ожидающее действие.
- Мягкое чтение неизвестных статусов / enum-подобных значений БД/API: процесс, список и тик не падают целиком; неизвестный пользователь не получает доступ/LLM, неизвестное напоминание не отправляется и не меняется, операция даёт `unsupported_state`. Остальные записи продолжают обрабатываться, исходное значение не затирается при записи других полей. Нужна целевая детерминированная регрессионная проверка, а не матрица многоверсионных прогонов; произвольные ошибки и повреждение данных не маскируются под неизвестный статус.
- Бюджеты: 16 000 входных токенов, 2 000 выходных, саммари до 1 000, не более 20 последних сообщений в общем бюджете; не более 3 обращений OpenRouter с повторами, 2 раундов / 6 вызовов инструментов и 90 секунд на сообщение. Повтор инструмента без прогресса останавливается; сокращение контекста сохраняет обязательные правила и целые связки инструментов.
- Новая сессия через 4 часа не наследует саммари; саммари закрытой сессии очищается через 30 дней от закрытия независимо от удаления сырых сообщений.

Поведение модели проверяется LLM-eval; проверки авторизации, подтверждений и транзакционной идемпотентности — детерминированными тестами агента/core. Один прогон модели не доказывает эти гарантии приложения.
