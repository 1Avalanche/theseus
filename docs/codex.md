# Codex в Theseus

Инструкции проекта — в `AGENTS.md`, правила — в `.codex/rules/`, навыки — в `.agents/skills/`, субагент — в `.codex/agents/`, хуки — в `.codex/hooks.json`. Настройка Claude Code в `.claude/` сохранена отдельно.

## Соответствие файлов Claude и Codex

| Источник | Для Codex | Адаптация |
|---|---|---|
| `CLAUDE.md` | `AGENTS.md` | Явные ссылки и таблица применимости правил |
| `.claude/rules/*.md` | `.codex/rules/*.md` | Перенесены все 11 правил; область действия вынесена из `paths:` в `AGENTS.md` |
| `.claude/skills/add-module/SKILL.md` | `.agents/skills/add-module/SKILL.md` | Ссылки на правила Codex |
| `.claude/skills/local-stand-check/SKILL.md` | `.agents/skills/local-stand-check/SKILL.md` | Временный каталог через `mktemp -d`, правки проекта через `apply_patch`; нет зависимости от `CLAUDE_JOB_DIR` |
| `.claude/agents/docs-writer.md` | `.codex/agents/docs-writer.toml` | Инструкции роли в `developer_instructions`, модель — `gpt-6.1-terra`; права и инструменты наследуются от родителя, Claude-поля `tools` и `model: sonnet` не переносятся |
| `.claude/settings.json`: `hooks` | `.codex/hooks.json` | Те же события `PreToolUse` и `Stop`; команды находят скрипты от корня Git |
| `.claude/hooks/*.py`, `hooks/tests/` | `.codex/hooks/`, `.codex/hooks/tests/` | Протокол Codex, определение корня из `cwd`, отдельные файлы состояния, проверки внешних процессов Codex |
| `.claude/settings.json`: `worktree.bgIsolation` | Правило `.codex/rules/git-commits.md` | Работа в текущей копии на `develop`, без отдельных веток и worktree; Claude-настройка не используется |
| `.claude/worktrees/` | Не требуется | Пустой служебный каталог, настроек не содержит |

Используется строчный путь `.codex/`: `.Codex/` на файловой системе с учётом регистра — другой каталог. Дополнительное правило `codex.md` фиксирует размещение настроек и отличия форматов.

## Правила, навыки и документация

Codex читает `AGENTS.md`, но не подключает Markdown-файлы `.codex/rules/` автоматически. В `AGENTS.md` указано, какие общие правила прочитать перед работой и какие тематические правила — до изменений в `agent/`, `core/`, ресурсах, миграциях и деплое. Фронтматтер Claude `paths:` эту маршрутизацию не заменяет.

Навык `add-module` описывает добавление Gradle-модуля; `local-stand-check` — проверку Docker-стенда перед деплоем. Для проверки отсутствия контрольного текста в логах последний использует скрипт, который отдельно читает stdout и stderr каждого контейнера и не выводит сами логи. Ошибка Docker или таймаут означают неуспешную проверку. Навыки находятся в каталоге обнаружения Codex `.agents/skills/`.

Для сверки описательной документации основной агент передаёт `docs-writer` список изменённых файлов и краткий бриф «что и зачем». Роль меняет только `docs/` и README, не меняет `docs/DECISIONS.md`, код, тесты и настройки. Это ограничения инструкций роли: отдельную песочницу или права на файлы TOML не создаёт. Причины архитектурных решений записывает основной агент.

Если клиент не поддерживает именованную роль, обычному субагенту передают `.codex/agents/docs-writer.toml` и явно задают модель из него (`gpt-6.1-terra`) в параметре `model` при запуске: чтение файла само по себе модель не переключает. Если субагенты недоступны, основной агент выполняет ту же процедуру самостоятельно.

## Подключение хуков

Нужны Git и Python 3.9+; внешних Python-зависимостей нет. Команды в `.codex/hooks.json` используют `git rev-parse --show-toplevel`, поэтому не зависят от имени пользователя и расположения рабочей копии, включая запуск Codex из подкаталога.

Проектный слой `.codex/` должен быть доверенным. Дополнительно Codex требует просмотра и доверия к текущему определению каждого хука: в CLI — `/hooks`, в приложении — `Review hooks` или `Settings > Hooks`. Новые и изменённые определения пропускаются до подтверждения доверия. Подробнее — [официальная документация OpenAI о хуках](https://learn.chatgpt.com/docs/hooks).

`hook_context.py` определяет корень Git по `cwd` события; вне Git использует корень репозитория со скриптами. Переменные `CLAUDE_PROJECT_DIR` для выбора проекта не используются. Несколько обработчиков одного события могут запускаться одновременно: `doc_guard` не управляет запуском `test_guard`.

### `bash_guard`

`PreToolUse` с `matcher: "Bash"` проверяет shell-команды, включая `exec_command`: Codex передаёт их под именем `Bash`, команда — в `tool_input.command`. При нарушении возвращается `hookSpecificOutput.permissionDecision: "deny"` с причиной.

Сохранены защиты от деструктивных операций Git, Docker, БД и системы, рекурсивного удаления и записи в файлы проекта через shell. Дополнительно к Claude блокируются внешние процессы Codex: прямой запуск, пакетные обёртки вроде `npx @openai/codex`, запуск CLI через Node. Разрешены только точные диагностические вызовы `codex --version`, `codex -V`, `codex --help`, `codex -h` и `codex features list`, без дополнительных аргументов и динамических подстановок; соседние команды и редиректы проверяются отдельно. Упоминание команды внутри строки или поискового шаблона разрешено. Штатное делегирование субагентам не является shell-запуском Codex и этим хуком не блокируется. Для правок проекта используется `apply_patch`.

Лексер, разрешённые каталоги и ограничения анализа описаны в [документе о хуках Claude](claude-hooks.md#bash_guard--защита-команд-bash): механика сохранена. Ошибка разбора или внутренняя ошибка блокирует команду — fail-closed. Хук не анализирует содержимое запускаемых скриптов, не заменяет песочницу и не гарантирует запрета всех способов записи файлов.

### `doc_guard`

`Stop`-хук сопоставляет изменённые файлы документам по таблице `RULES`. При изменении `.codex/hooks/**`, `.codex/hooks.json` или `.codex/config.toml` предлагает сверить этот документ; изменения `.claude/hooks/**` и `.claude/settings.json` по-прежнему ведут к `docs/claude-hooks.md`. Остальные соответствия — код модулей, MCP/REST, миграции, ресурсы, сборка и эксплуатация — сохранены.

Инструкции `AGENTS.md`/`CLAUDE.md`, правила, определения агентов, навыки, тесты хуков, сами документы и README не вызывают напоминание. Эти исключения не отменяют обновление документации вместе с изменением поведения.

Отпечаток набора изменений хранится в Git-каталоге как `codex-doc-guard.json`, отдельно от `claude-doc-guard.json`. Хук напоминает один раз на набор изменений; при `stop_hook_active` или если все предложенные документы уже изменены — не блокирует. При ошибке самого хука завершение разрешено — fail-open. Качество документации хук не оценивает.

### `test_guard`

`Stop`-хук запускает `./gradlew check --console=plain --continue`, если отпечаток файлов сборки отличается от последнего зелёного прогона. Учитываются отслеживаемые и новые `*.kt`, `*.kts`, `*.sql`, `gradle.properties`, TOML в `gradle/`, все файлы в `src/*/resources/` и YAML в `config/`, кроме игнорируемых Git. TOML ролей Codex и правки только Markdown вне ресурсов не запускают Gradle.

Независимо запускаются Python-тесты `unittest discover -s .codex/hooks/tests`: их отпечаток включает Python-файлы хуков, `.codex/hooks.json` и Python-скрипты `local-stand-check`. Обе проверки выполняются даже при падении, ошибке запуска или таймауте одной из них. Успешные отпечатки хранятся отдельно в Git-каталоге: `codex-test-guard.json` для Gradle и `codex-hooks-test-guard.json` для Python, отдельно от состояния Claude; неуспешный запуск зелёное состояние не записывает. Упавшая проверка возвращает блокировку и выжимку ошибок, включая ошибки Python и пути traceback; повторное падение при `stop_hook_active` — предупреждение без новой блокировки. Неожиданная внутренняя ошибка самого хука завершение не блокирует. Таймаут Gradle — 540 секунд, Python — 45 секунд, обработчика — 600 секунд.

`check` покрывает юнит-тесты, ktlint, detekt и интеграционные тесты core (`integrationTest` подключён через `dependsOn`). Без Docker интеграционные тесты пропускаются (`disabledWithoutDocker`). Реальные LLM-eval запускаются отдельно. Перед завершением задачи правило проекта дополнительно требует зелёный `./gradlew build`.

## Проверка

```bash
python3 -m unittest discover -s .codex/hooks/tests
python3 -m unittest discover -s .claude/hooks/tests
./gradlew build
```

Тесты хуков запускаются независимо от Gradle, в том числе автоматически через `test_guard` при изменении их отпечатка. При изменении защиты нужны проверки блокировки и разрешённого упоминания в строке; при изменении `RULES` — проверка классификации пути. Протокол событий, запуск из подкаталога, переносимость команд `hooks.json` и независимость состояния проверяются без реальных вызовов LLM.

Форматы навыков и ролей — [навыки Codex](https://learn.chatgpt.com/docs/build-skills) и [субагенты Codex](https://learn.chatgpt.com/docs/agent-configuration/subagents).
