# Минимальный мониторинг

Файлы монитора и обновлённый Compose установлены на VPS, исправление polling развёрнуто в prod, таймер включён. Владелец подтвердил проверки остановки agent, пропуска внешнего пульса и восстановления. Живые проверки зависания задачи, лимита авторестартов и порогов БД, очереди и диска остаются этапом 7. Ночной бэкап пока не настроен. Общая эксплуатация и деплой — [operations.md](operations.md), установка обработчика — [deploy-setup.md](deploy-setup.md).

## Что проверяется

Процессы core и agent раз в 30 секунд атомарно записывают снимки JSON v1 в `/tmp/theseus-core.monitor.json` и `/tmp/theseus-agent.monitor.json` своих контейнеров. Снимки содержат состояние задач, времена, коды и счётчики ошибок; текстов пользователей и токенов в них нет. Счётчики хранятся в памяти процесса и сбрасываются при его перезапуске.

Монитор VPS запускается через `systemd` раз в 10 минут и читает снимки фиксированных контейнеров через Docker:

| Проверка | Условие сбоя |
|---|---|
| core / планировщик | нет завершённого прохода 10 минут; пустой проход тоже подтверждает работу |
| agent / long polling | нет успешного `getUpdates` 10 минут; пустой ответ считается успехом |
| Диагностика и контейнеры | контейнер не запущен, снимок отсутствует, повреждён или не обновлялся 10 минут |
| PostgreSQL | диагностика core сообщает о недоступности БД |
| Очередь | самое старое активное напоминание ожидает отправки от 10 минут; core считает число и время старейшего агрегатно, без ограничения размером пакета планировщика |
| Telegram / OpenRouter | продолжительный ряд ошибок в течение 10 минут; коды и счётчики отражены в снимках |
| Диск | заполнено 80 % или больше либо не удалось получить сведения о файловой системе |
| Бэкап | отметка успешного ночного бэкапа отсутствует или устарела на 26 часов; проверка включается отдельно после настройки регулярного бэкапа |

Рабочий период планировщика остаётся 30 секунд. Проверка раз в 10 минут означает обнаружение нарушения временного порога примерно через 10–20 минут с начала сбоя, без учёта недоступности сети или монитора. Для остановленного или ещё не развёрнутого test-стенда проверки test пропускаются; prod проверяется всегда.

Healthcheck core проверяет БД; healthcheck agent использует время успешного `getUpdates` и порог 10 минут. `getMe` при старте agent по-прежнему проверяет токен. Healthcheck и диагностика не проверяют полный путь Telegram → LLM → напоминание → Telegram. Сквозной запрос на test перед пилотом остаётся необходимым.

## Восстановление и оповещение

При отсутствии пульса рабочей задачи и отсутствии признаков сбоя связанной внешней зависимости монитор перезапускает соответствующий контейнер. Доступно не больше двух попыток, между попытками — не менее 10 минут; лимит сбрасывается только после отдельной здоровой проверки с пульсом после последнего рестарта. Сбой БД или отправки Telegram блокирует перезапуск core, ошибка `getUpdates` — перезапуск agent. Отсутствующий, устаревший или некорректный диагностический снимок и неизвестное состояние стенда не дают оснований для перезапуска. Повреждение состояния монитора или бюджета попыток останавливает проверку без отправки внешнего пульса. Состояние и попытки сохраняются в `/opt/theseus/monitor-state.json`.

Polling повторяется с увеличением паузы; для Telegram `429` учитывается `retry_after`. Для временных ошибок отправки напоминания core также увеличивает паузу, а постоянные `400`/`403` фиксируются как неуспешная доставка. `401` не закрывает напоминание как доставленное. Отправка сообщений не повторяется внутри одного сетевого запроса; гарантия доставки напоминаний остаётся «как минимум один раз».

Изменение набора проблем и восстановление записываются в журнал и, при настройке, отправляются отдельным Telegram-ботом. Одинаковые состояния повторно не отправляются. Если отправка не удалась, монитор повторит её при следующем запуске. Этот бот не должен использовать токен Сири.

Независимому сервису монитор отправляет HTTPS POST на URL успеха, если проблем нет, или на URL отказа с перечнем проблем. При сбое отправки Telegram уведомления также используется URL отказа. Внешний сервис оповещает получателя при отказе или отсутствии heartbeat; отсутствие сети, работы VPS либо самого монитора выявляется по пропущенному пульсу. URL должны принимать POST без перенаправлений и отвечать кодом 2xx. Ожидаемый период — 10 минут; рекомендуемая допустимая задержка — 10 минут, при ней тревога по отсутствию пульса приходит примерно через 20 минут после последнего успешного запроса. Фактическая задержка Better Stack отдельно не подтверждена. Секретные URL не выводятся в журнал.

Запуск монитора использует общую с деплоем блокировку `/opt/theseus/deploy.lock`. Если идёт деплой или плановая остановка test, проверка откладывается до следующего запуска; внешний сервис при слишком долгом обслуживании может сообщить о пропуске пульса.

## Настройка

Монитор устанавливается администратором через отдельный SSH-доступ. Нужен внешний сервис с независимым оповещением получателя и двумя секретными URL для успеха и отказа. При необходимости отдельного Telegram-канала понадобятся токен отдельного бота и chat ID получателя. Секреты вводятся только на VPS.

Владелец выбрал Better Stack и создал check `Theseus VPS` с периодом **10 минут**. Допустимая задержка в 10 минут рекомендована, но на скриншоте не видна и отдельно не подтверждена. Владелец сообщил, что получил письмо после `Send test alert`, а затем подтвердил проверки реальных тревог и восстановления. После запуска монитора VPS первый реальный пульс получил ответ 2xx. Интерфейс Better Stack и почту независимо не проверяли.

### Сбой prod 2026-11-12

Deploy релиза `5d45abbf5d7f8dbbccc1b65fc41d195e8e7a9b4f` завершился сообщением «Контейнер не стал healthy». Проверка SSH только на чтение: PostgreSQL и core `healthy`, пульс планировщика свежий, очередь пуста; prod-agent работает, но `unhealthy`, успешного `getUpdates` не зафиксировано. Снимок показал пять сетевых ошибок, отдельно извлечены шесть ошибок класса `HttpRequestTimeoutException`. Test оставался остановлен. Мы не выполняли перезапуск или откат на VPS.

Причина найдена в SDK ktgbotapi 37.1.0: HTTP-таймаут запроса и сокета равнялся 30-секундному ожиданию `getUpdates`, поэтому при отсутствии обновлений сетевой таймаут мог оборвать пустой ответ. В исправлении для `getUpdates` добавлен запас 15 секунд: Telegram ждёт до 30 секунд, HTTP и сокет — до 45 секунд. Настройки остальных запросов не меняются, используется прежний Java-движок Ktor. Регрессионный тест через настоящий SDK и задержанный `MockEngine` воспроизвёл сбой до исправления и прошёл после; он также проверяет три пустых ответа, сетевой отказ без пульса и прежние таймауты `getMe`. Дополнительный тест с настоящим Java HTTP-движком и локальным HTTP-сервером подтвердил два пустых ответа после ожидания.

Откат на ранее разрешённый prod-релиз `aa578d6a5d8944984d7d362a7b523227162b07e5` предлагался для быстрого восстановления, но не выполнялся.

### Установка файлов

Инструкция для первичной установки или обновления. Текущее состояние VPS описано выше: файлы монитора и Compose установлены, таймер активен. Передать проверенный каталог `deploy/` административным способом, как в [deploy-setup.md](deploy-setup.md). Ниже `INSTALL_DIR` — абсолютный путь к переданному каталогу на VPS. До запуска таймера установить и запустить на test/prod образы с диагностикой и соответствующий Compose: прежние образы не создают нужные снимки. Compose обновляется администратором под общей блокировкой; обычный Deploy его не заменяет.

Для изменения установленного комплекта открыть root-оболочку под существующей блокировкой, как описано в [инструкции деплоя](deploy-setup.md); файл блокировки не удалять и не пересоздавать. В ней заменить `INSTALL_DIR` на проверенный путь и выполнить:

```bash
install -d -o root -g root -m 700 /opt/theseus/monitor
install -o root -g root -m 600 INSTALL_DIR/monitor/monitor.py /opt/theseus/monitor/monitor.py
install -o root -g root -m 600 INSTALL_DIR/monitor/messages.json /opt/theseus/monitor/messages.json
install -o root -g root -m 644 INSTALL_DIR/monitor/theseus-monitor.service /etc/systemd/system/theseus-monitor.service
install -o root -g root -m 644 INSTALL_DIR/monitor/theseus-monitor.timer /etc/systemd/system/theseus-monitor.timer
```

При первой установке скопировать `INSTALL_DIR/env/monitor.env.example` в `/opt/theseus/monitor.env` с владельцем root и правами `600`, затем заполнить через `sudoedit` или другой защищённый способ. Существующий заполненный env при обновлении не перезаписывать. Выйти из root-оболочки, освободив `deploy.lock`. Не запускать таймер с примерами URL или до настройки получателя у внешнего сервиса.

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now theseus-monitor.timer
sudo systemctl start theseus-monitor.service
sudo systemctl status theseus-monitor.timer
sudo journalctl -u theseus-monitor.service -n 50 --no-pager
```

Ручной запуск выполняет реальные проверки и может вызвать ограниченный перезапуск зависшего контейнера и внешние оповещения. Проверить, что внешний сервис получил успех и сможет сообщить о пропущенном heartbeat. Плановая остановка таймера потребует отключить или временно приостановить внешний check, иначе сервис сообщит о потере пульса.

### Повторение проверок внешнего контура

Проверка на prod временно останавливает приём сообщений. Команды остановки и запуска контейнера выполняются под существующим `deploy.lock`; service монитора запускается после освобождения блокировки, иначе он отложит проверку. Остановленный вручную контейнер монитор автоматически не запускает.

1. Остановить agent и запустить проверку:

   ```bash
   sudo flock -x /opt/theseus/deploy.lock /usr/bin/docker stop theseus-prod-agent
   sudo systemctl start theseus-monitor.service
   ```

   Дождаться сигнала отказа и письма. Затем запустить agent, дождаться `healthy` и свежего пульса `getUpdates` и снова запустить монитор:

   ```bash
   sudo flock -x /opt/theseus/deploy.lock /usr/bin/docker start theseus-prod-agent
   sudo docker inspect --format '{{.State.Health.Status}}' theseus-prod-agent
   sudo systemctl start theseus-monitor.service
   ```

   Проверить восстановление во внешнем сервисе. Если agent ещё не `healthy` или свежего пульса нет, дождаться их до повторного запуска монитора.

2. Остановить таймер, выполнить последнюю успешную проверку и дождаться письма о пропущенном пульсе:

   ```bash
   sudo systemctl stop theseus-monitor.timer
   sudo systemctl start theseus-monitor.service
   ```

   При настроенных Period 10 минут и Grace 10 минут ожидание составляет примерно 20 минут от последнего успешного пульса; фактическая задержка зависит от настроек внешнего сервиса. Вернуть таймер и вручную отправить успешную проверку:

   ```bash
   sudo systemctl start theseus-monitor.timer
   sudo systemctl start theseus-monitor.service
   ```

   Проверить восстановление во внешнем сервисе и `active`/`enabled` таймера.

### Оставшиеся проверки перед пилотом

На VPS отдельно проверить зависание внутренней задачи, ограничение автоматических перезапусков, пороги недоступности БД, просроченных доставок и заполнения диска, а также отсутствие шквала повторов. Эти живые сценарии не заявляются пройденными. После настройки ночного бэкапа проверить свежую и устаревшую отметки. Не использовать реальные тексты пользователей в диагностических проверках.
